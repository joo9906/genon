# onprem/preprocessor — hwpx 전용 GenOS 전처리기(area 05)

> **등록 단위는 소스 파일 하나다.** GenOS 전처리기는 MCP 와 같은 방식으로 소스 파일
> 하나를 그대로 받아 실행한다(`docs/GENOS_RULES.md` §C — "전처리기 | 생성·수정 화면의
> 환경 변수" 는 코드서빙의 Git 저장소 방식이 아니라 파일 단위 등록임을 가리킨다).
> 그래서 `hwpx_preprocessor.py` 는 **다른 파일을 import 하지 않는다**(표준 라이브러리 +
> `lxml` 만).

> ⚠ **여기는 외부 개발 환경이고, 폐쇄망으로는 파일이 아니라 사람이 옮긴다.**
> 화면을 보며 타이핑한다. 그래서 아래 생성물들은 **이관 산출물이 아니라 외부 검증물**
> 이다 — 실제로 무엇을 얼마나 치는지는 "온프레미스 이관" 절.

```
preprocessor/
  hwpx_preprocessor.py          ⭐ hwpx 규칙의 **정본** — 파싱 + 청킹 + VDB 레코드 + DocumentProcessor
  router_template.py             라우팅·폴백·스키마 정렬 (여기서 고친다)
  __init__.py                    로컬 테스트가 `import preprocessor` 로 쓰기 위한 얇은 재노출

  build_final_preprocessor.py    합친 검증물 생성 스크립트
  final_preprocessor.py         ⚙ **생성물 · 외부 검증용** — hwpx 는 위 파서로, 나머지는
                                 GenOS **첨부용** 전처리기로. 직접 고치지 말 것
                                 (지능형은 2026-09-01 에 걷어냈다 — 아래 절)

  build_transfer_kit.py          이관 자료 생성 스크립트
  transfer/                     ⚙ **생성물 · 타이핑용** — 주석·docstring 을 걷어낸 판본 +
                                 오타 검출 스니펫 + 절차 문서. 직접 고치지 말 것
```

> **등록 방식은 둘 중 하나다.** 확장자별로 매핑을 나눌 수 있으면 `hwpx_preprocessor.py`
> 단독이 단순하고(타이핑 1,172줄), 등록을 하나로 유지해야 하면 벤더 파일에 이어 붙인다
> (타이핑 1,711줄 + 벤더 1줄 수정). 근거와 대가는 아래 "한 등록으로 합치는 길도 있다" 절.

## 온프레미스 이관 — **파일이 아니라 사람이 건넌다**

```
python onprem/preprocessor/build_transfer_kit.py
```

절차서는 `transfer/00_이관절차.md` 가 **자동 생성**한다(숫자가 매번 다시 계산되므로
손으로 고치지 않는다). 요점만:

- **벤더 절반은 이미 그쪽에 있다.** `attach_processor.py` 는 온프레미스에서 긁어온 참조
  사본이고 원본은 첨부용 전처리기로 등록돼 있다. 그 사본을 떠서 우리 코드를 이어 붙인다.
- **벤더에 손대는 것은 1줄** — `class DocumentProcessor:` → `AttachDocumentProcessor`.
  안 고치면 GenOS 가 벤더 것을 실행해 **라우팅이 통째로 사라지는데 적재는 성공으로 보인다.**
- **주석·docstring 을 걷어내 3,145줄 → 1,711줄**(54%)로 줄인다. `__doc__` 를 읽는 코드가
  없어 동작이 같고, 걷어낸 판본이 원본과 같다는 것은 **AST 대조 + 실물 hwpx 5벌**로
  확인한다. **설명은 이 저장소가 갖는다.**
- **`ast.unparse` 로 다시 찍지 않는다.** 그러면 한 줄이 451자까지 늘어나는데, 손으로 칠
  때는 **긴 줄이 주석보다 나쁘다**(자리를 놓치고 틀려도 눈에 안 띈다). 원본 줄바꿈을
  살려 최장 100자로 둔다.
- **오타는 해시로 잡는다.** 11줄짜리 `30_verify.py` 를 쳐서 돌리면 최상위 정의마다
  해시가 나오고, `40_expect.txt`(**치지 않는다 — 외부 화면에 띄워 놓고 눈으로 본다**)와
  대조한다. 어긋난 줄의 이름이 곧 오타가 있는 함수다. **타이핑은 비싸고 보는 것은 공짜다.**
  숫자 한 글자를 바꿔 실제로 잡히는 것을 확인했다(151개 중 1개만 어긋난다).
- **가드 한 자리가 외부와 다르다.** `final_preprocessor.py` 는 벤더 절반을 `try:` 안에
  넣는데 그건 **우리 사정**이다(로컬에 docling 이 없어도 점검이 돌아야 한다). 온프레미스
  에서는 벤더 스택이 이미 있고 2,558줄을 통째로 들여쓰는 것은 손으로 할 일이 아니라,
  `_FP_ATTACH_IMPORT_ERROR = None` 두 줄이 그 자리를 메운다.

```python
from preprocessor import DocumentProcessor, annotate_outline, chunk_blocks, parse, to_records

# 부품만 쓰고 싶을 때
document = parse(hwpx_bytes)
blocks = annotate_outline(document.blocks)      # 조문 위계 (조문 문서일 때만 켜진다)
chunks = chunk_blocks(blocks)
records = to_records(chunks, file_name="사업계획서.hwpx",
                     section_count=document.section_count)

# GenOS 가 실제로 부르는 모양
processor = DocumentProcessor()
records = await processor(request, file_path, chunk_size=1000, chunk_overlap=100)
```

## 왜 만들었나 — 기존 경로로는 표가 깨진다

지금 hwpx 가 RAG 로 들어가려면 전처리기를 지나는데, **지능형 전처리기는 무조건 PDF 로
변환**한다. 그 과정에서 표 안 수치가 깨진다(요구사항 §5). 반대로 hwpx 를 직접 파싱하면
수치는 살지만 지금까지는 **마크다운 표로 내느라 병합·중첩이 사라졌다.**

```
| 구분 | 2025년 실적 |   | 비고 |   ← colSpan 사라짐 → 3열이 빈칸
|   | 상반기 | 하반기 | - |        ← rowSpan 사라짐 → 1열이 빈칸
| 세부 | 소분류<br>값 |   |   |     ← 중첩표가 텍스트로 뭉개짐
```

**수치는 남는데 그 수치가 무엇의 값인지가 사라진다.** RAG 에서는 이게 치명적이다 —
검색은 되는데 답이 틀린다. 그래서 표는 HTML 로 낸다.

**표는 언제나 HTML 이다** (2026-08-13 변경. 그전에는 병합·중첩이 있을 때만 HTML 이었다).
실제 검색 결과를 받아 보고 뒤집었다 — **결과가 LLM 에게 갈 때 개행이 공백으로 뭉개진다:**

```
| 순번 | … | 수용<br>여부 | |---|---|---| | 3 | 차기 변제금 …
```

마크다운 표는 **행 경계가 개행뿐**이라 이 한 줄에서 표가 아니게 된다(구분선이 본문 줄에
붙고 7열이 뒤섞인다). 위의 병합 손실과 **같은 실패**다. HTML 은 행·칸 경계가 태그라
개행 없이도 구조가 남고, 새 형식도 아니다 — 지능형 전처리기가 이미 한 줄 HTML 표
(`<table><tbody><tr><th …`)를 내므로 검색·프롬프트 경로가 그 형태를 이미 받는다.
대가는 토큰 증가(실물에서 약 10%)이고, 표가 아니게 되는 것보다 낫다는 판단이다.
**첫 행은 `<th>`** 다 — 마크다운 구분선이 하던 머리행 표시를 태그가 맡는다(조각마다
머리행을 반복하는 것이 분할의 요점인데, 표시가 없으면 그 반복이 데이터로 읽힌다).

## 글자는 하나도 버리지 않는다 (2026-08-19)

표를 지키려고 만든 파서인데, **표가 아닌 글자를 네 자리에서 잃고 있었다.** 표가 깨지는
것과 달리 이 손실은 **없어진 자리에 아무 흔적도 남기지 않는다** — 남은 문장이 멀쩡해
보이니, 그 문장을 물어봤을 때 검색이 아무것도 못 찾을 때까지 드러나지 않는다.

### 1) 탭·강제 줄바꿈 뒤의 글자

`hp:t` 는 **혼합 내용**이다. 탭(`hp:tab`)·강제 줄바꿈(`hp:lineBreak`)·묶음 빈칸이
자식 원소로 들어가고, **그 뒤에 오는 글자는 자식의 `tail`** 에 담긴다.

```xml
<hp:t>가.<hp:tab/>지원 대상</hp:t>
```

`node.text` 만 읽던 예전 코드는 여기서 `가.` 만 가져갔다 — 항목 이름표만 남고 내용이
사라진다. 조판 문자 자체도 글자로 되살린다(탭·줄바꿈 → 공백). 없애면 `1.지원대상`
처럼 이름표와 내용이 붙는다.

### 2) 상자 안 글 — 글상자·도형·각주·머리말·캡션·메모

hwpx 에서 글자를 담는 곳은 표 셀만이 아니다. 위의 것들이 전부 자기 안에
`hp:subList > hp:p` 를 갖는데, 예전 `parse()` 는 **중첩 문단을 통째로 건너뛰었다**
("본문 흐름이 아니다"). 공공 문서에서 제목·요약 상자는 흔하고, 그게 통째로 없어졌다.

지금은 전부 낸다. 어디서 온 글인지 헷갈리지 않게 라벨을 붙이되, **글상자·캡션은 본문과
같은 글이라 라벨이 없다** — 라벨은 원문에 없던 글자를 더하는 것이므로, 출처를 모르면
뜻이 달라지는 자리(각주·머리말·꼬리말·숨은 설명·메모)에만 쓴다.

- **표 캡션은 표 앞에 낸다.** 그러면 `_table_title_of` 가 그것을 표 제목으로 집어
  조각마다 앞에 붙인다 — 쪼갠 표의 3번째 조각이 무엇의 표인지 알게 되는 자리다.
- **셀 안 상자는 셀 안에 남긴다.** 밖으로 내면 그 글이 어느 칸의 것인지 사라진다.
- **상자 안 표는 표로 남긴다.** 글자로 펴면 그 수치가 무엇의 값인지 사라진다 —
  이 전처리기를 만든 이유 그대로다.
- **상자인지는 이름 목록이 아니라 생김새로 판정한다**(`hp:subList` 를 직접 자식으로
  두는가). 목록으로 두면 거기 안 적힌 상자가 예전처럼 조용히 버려지고, 이름을 빠뜨렸다는
  사실을 아무도 모른 채로 남는다. `_BOX_LABELS` 는 "뭐라고 부를까" 만 정한다.

### 3) 개요 번호와 글머리표 — 보이는데 본문 XML 에는 없다

한/글의 개요 번호(`1.`, `가.`, `(1)`)와 글머리표(`-`, `●`)는 문단 텍스트가 아니라
**문단 모양(`hh:paraPr > hh:heading`)이 가리키는 `Contents/header.xml` 의 정의**에서
나온다. 그래서 `hp:t` 만 읽으면 화면의

```
- 사용자가 문서를 업로드한다
- 시스템이 문서보안을 해제한다
```

이 적재 후에는 앞의 `-` 가 없는 두 문장이 되고, **목록이라는 사실과 항목의 층위가 함께
없어진다.** 조문 위계 판정(`_match_statute`)도 그 표기를 보고 하는 일이라, 번호가 없으면
항·호가 본문 문단으로 떨어져 **청크 경계까지 달라진다.**

**지어내는 것이 아니다.** 문서가 정의와 참조를 둘 다 갖고 있어 결정적으로 복원된다 —
한/글이 화면에 그리는 계산을 그대로 다시 하는 것이다. 다만:

- **`@idRef` 는 id 로도 인덱스로도 온다** — id 로 먼저 찾고, 없으면 문서 순서
  **0-based 인덱스**로 본다. 아래 "참조를 못 이어 번호가 통째로 빠지고 있었다" 참고.
- **복원할 수 없는 단계는 비워 둔다**(정의에 표시 문자열이 없는 경우). 틀린 번호를
  붙이는 것보다 낫다. **정의 자체를 못 찾은 것과 다른 경우다** — 표시 문자열이 비면
  한/글도 아무것도 그리지 않으므로 비우는 것이 원문에 맞고, 정의를 못 찾은 것은
  무언가 그려지는데 무엇인지 모르는 것이라 비우면 그 자리가 통째로 사라진다.
  후자는 숫자(`1.`)로, `@char` 없는 글머리표는 `-` 로 낸다.
- **번호는 누적 상태다.** 글자가 없는 문단에서도 진행시킨다 — 건너뛰면 그 뒤 번호가
  전부 하나씩 밀린다(한/글도 빈 문단에 번호를 매긴다). 누적 카운터는 **해석된 정의**를
  키로 든다 — 원본 `@idRef` 로 들면 id 와 인덱스로 같은 정의에 닿은 두 문단 모양이
  따로 세어져 한 목록이 `1. 1. 2. 2.` 로 나온다.
- **`4294967295`(한/글의 "없음" sentinel)는 인덱스로 읽지 않는다.** 읽으면 한/글이
  아무것도 그리지 않는 자리에 번호가 생긴다.
- **`Contents/header.xml` 이 없거나 깨져도 본문 적재를 막지 않는다.** 번호만 빠진다.

#### 참조를 못 이어 번호가 통째로 빠지고 있었다 (2026-08-20)

`1. 사업 개요` 에서 **글자는 나오는데 `1.` 만 사라졌다.** 실물 한/글이 내는 모양이
이렇다 — 개요 번호 문단은 `idRef="0"` 을 쓰는데 번호 정의의 `@id` 는 **1 부터**
시작한다:

```xml
<hh:numbering id="1" start="0"><hh:paraHead level="1" numFormat="DIGIT">^1.</hh:paraHead>
<hh:heading type="OUTLINE" idRef="0" level="0"/>     <!-- id 로는 찾을 수 없다 -->
```

id 로만 찾으면 `get("0")` 이 `None` 이라 **개요 번호가 붙은 모든 문단에서 번호만
사라진다.** 저장소 실물 4벌이 전부 이 모양이었다(`idRef="0"` × 7단계, 번호 정의는
`id="1"`·`id="2"`). 텍스트는 `_own_text` 가 따로 뽑으므로 문장은 멀쩡히 남고, 표가
깨지는 것과 달리 **없어진 자리에 흔적이 남지 않는다.**

**id 매치를 앞에 두는 이유**는 `type="NUMBER"`(문단 번호)가 id 를 그대로 참조하는
경우를 지키기 위해서다. 한/글이 `@idRef` 를 언제나 0-based 로 쓴다면 인덱스만으로도
되지만, 그것을 확정할 실물(번호 정의가 둘 이상이면서 둘 다 참조되는 문서)이 아직 없다.

**어긋남의 대가는 크지 않다.** 자동 번호가 만드는 표기는 `_STATUTE_RULES` 에서 항·호·목
(레벨 6·7·8)에만 걸리고, 그 레벨은 `outline_break_level`(기본 5)에서 청크를 끊지도
`_LEVEL_PATH_MAX`(5) 로 제목 줄기에 들지도 않는다. 청킹까지 흔드는 레벨 1~5(`제5조`)는
본문 글자에서 나온다. 그래서 **번호가 없는 것이 어긋난 번호보다 나쁘다** — 적재 경로는
아무도 눈으로 보지 않으므로, 유실은 그 문장을 물어봤을 때까지 드러나지 않는다.

**그물이 못 잡은 이유**도 같은 자리에 있었다. `AutoNumberTest` 의 픽스처는 손으로 지은
것이라 `id="1"` ↔ `idRef="1"` 로 맞춰져 있어서, 실물에서 100% 실패하는 코드가 9건 전부
통과했다. 이제 **실물 모양(`idRef="0"`) 픽스처를 따로 둔다.**

**실물 4벌의 출력은 변경 전후가 해시까지 같다** — 그 문서들은 개요 번호를 쓰지 않고
번호를 본문에 직접 적어 뒀다(그래서 증상이 이 문서들에서는 안 보였다).

### 4) 수식

`hp:equation > hp:script` 에 원본 문자열로 들어 있어 `hp:t` 만 보면 안 잡힌다. 수식
하나가 통째로 빠지면 그 문단의 뜻이 바뀐다.

**실물 대조**: 기술협상서 두 벌·FAQ·파워 hwpx 네 벌의 출력은 이 변경 **전후가 바이트까지
같다**(그 문서들에는 위 네 가지가 없다). 즉 되살린 경로가 기존 문서를 건드리지 않는다.

## 다섯 가지 설계 결정

### 0. 파일 하나로 끝낸다 — 등록 방식이 그렇게 정해져 있다

`onprem/mcp/*.py` 와 같은 이유다: GenOS 전처리기는 코드서빙(Git 저장소)이 아니라
**소스 파일 한 개**를 생성·수정 화면에 올려 실행한다. 그래서 예전에 `hwpx.py`
(파싱) / `chunking.py`(청킹) / `vector_meta.py`(레코드)로 나눠 뒀던 것을
`hwpx_preprocessor.py` 하나로 합쳤다 — 등록 화면에 셋 중 하나만 올리면 나머지가
빠진 채로 배포되는 실수를 구조적으로 없앤다. 로컬에서 부품 단위로 테스트하고
싶을 때만 `__init__.py` 가 같은 코드를 패키지처럼 재노출한다.

### 1. 표는 쪼개지 않는다

문자 수만 보는 청커에 넣으면 표 한가운데가 잘리고, **뒤 조각은 머리행이 없어 검색돼도
쓸모가 없다.** 그래서:

- 표가 상한을 넘으면 **머리행을 반복하며** 행 단위로 나눈다 — 조각마다 스스로 해석
  가능해야 한다.
- 표를 만나면 쌓아 둔 문단을 **먼저 끊는다.** 표가 문단 꼬리에 붙으면 검색 결과가
  읽기 어렵다.
- 쪼갰다는 사실을 `i_table_part`/`n_table_part` 로 **노출한다.** 조각만 보고
  "표가 이게 전부" 로 읽으면 안 된다.
- **칸이 하나뿐인 표는 표가 아니다** (2026-08-13, 실물에서 확인). hwpx 는 제목상자·박스형
  강조를 1칸 표로 만드는 일이 흔한데, 그대로 내면 본문 행이 0개인 퇴화된 표가 된다
  (`<table><tbody><tr><th>『…』 사업 기술협상서</th></tr></tbody></table>`). 글자를 잃지는
  않지만 표 아닌 것이 표로 검색되고, 표 골격이 노이즈로 임베딩되며, 조문 위계 판정도
  지나쳐 간다. 문단으로 낸다 —
  다만 **중첩 표가 들어 있으면 그대로 표로 둔다**(펴면 안쪽 표를 통째로 잃는다).
- **구역(`Contents/sectionN.xml`)이 바뀌면 끊는다.** 걸치는 청크는 `i_section` 이 둘 중
  하나만 가리켜 출처가 틀린다. 예전에는 구역 경계에 표가 있어 **우연히** 끊겼을 뿐이고,
  1칸 표를 문단으로 내면서 그 우연이 사라졌다 — 실물에서 뒤 구역의 제목상자가 앞 구역
  청크 꼬리에 흡수되는 것으로 드러났다. `_merge_tiny` 도 구역·조문 줄기가 다르면 붙이지
  않는다(붙이면 방금 세운 경계가 조용히 되돌려진다).
- **조각 표시와 표 제목은 레코드가 아니라 본문에 넣는다** (2026-08-13, 실물 검색 결과에서
  확인). 검색 결과가 LLM 에게 갈 때의 봉투는
  `<doc index='2' file_name='…' file_path='…' security_level='0'>본문</doc>` 이고
  **`i_table_part`·`i_section`·`table_title` 은 거기 실리지 않는다.** 그래서 세 번째 조각이
  "3번 항목부터 시작하는 표" 로 보였고, 앞의 1~2번이 어딘가 있다는 사실도 이게 한 표의
  일부라는 사실도 드러나지 않았다. 조문 머리말과 **같은 이유·같은 방식**으로 본문 첫 줄에
  넣는다:

  ```
  『위원회 생성형 AI플랫폼 구축 사업』 기술협상 의견 (표 8/14)
  <table><tbody>
  <tr><th>순번</th><th>주요 내용</th>…</tr>
  <tr><td>13</td>…</tr>
  </tbody></table>
  ```

  제목은 **표 바로 앞 한 줄짜리 짧은 문단**(60자 이하)만 인정한다 — 본문 문단을 제목으로
  삼으면 조각마다 그 본문이 반복돼 임베딩이 표에서 멀어진다. 조문 줄기가 있으면 제목은
  붙이지 않는다(그쪽 머리말이 이미 그 일을 한다). 레코드에도 `table_title` 을 함께 싣는다 —
  본문 머리말은 임베딩되라고 있는 것이고 레코드 값은 결과 표시·필터용이다.
- **행 하나가 상한을 넘으면 셀 안에서 한 번 더 나눈다** (2026-08-13). 그전에는 행 단위가
  마지막 경계라 거기서 멈췄고, 실물에서 **1,929자 청크**가 그대로 임베딩으로 갔다.
  임베딩 컨텍스트가 그보다 짧으면 **뒤쪽이 조용히 잘린다** — 레코드에는 글자가 남아 있어서
  검색이 왜 실패했는지 어디에도 안 드러난다. 나누는 규칙:
  - 짧은 칸(80자 이하: 순번·담당·수용여부)은 **조각마다 통째로 반복**한다. 머리행을
    반복하는 것과 같은 이유다 — 조각만 봐도 몇 번 항목인지 알아야 한다.
  - 긴 칸은 셀 안 줄바꿈(`<br>`) 경계로 채운다. 한 줄이 혼자 상한을 넘으면 문장 경계로 한 번
    더 나누고, 그때는 **공백으로 잇는다** — `<br>` 로 이으면 원문에 없던 줄바꿈이 생긴다.
  - **열 수는 그대로**라 조각도 여전히 올바른 표다. 되돌려 렌더한 것이 원래 `<tr>` 줄과
    글자까지 같을 때만 쪼갠다 — 모르는 모양에서 조용히 글자를 잃으면 검색 결과에 아무
    흔적도 남지 않는다.
  - 이 조각에 아무것도 안 실린 **긴** 칸에는 생략 표시(`…`)를 남긴다. 빈칸으로 두면 "그
    항목은 값이 없다" 로 읽혀 진짜 빈칸과 구분되지 않는다.
  - 글자는 버리지도 겹치지도 않는다 — 표 안에서 겹치면 같은 수치가 두 번 나와 합계가 틀린다.
  - **병합(`rowspan`/`colspan`)이 걸린 행과 중첩 표가 든 행은 행 단위까지만** 쪼갠다.
    병합은 "이 칸이 몇 행·몇 열을 덮는다" 는 선언이라 조각마다 되풀이하면 **없던 격자를
    지어내고**, 중첩 표는 조각 사이에서 갈린다.
- **머리말 자리는 미리 빼 둔다.** 조문 머리말은 일부러 길이 계산 뒤에 붙이지만(조가 깊을수록
  본문이 밀려 청크 크기가 들쭉날쭉해진다) 표는 제목이 하나뿐이라 예약이 균일하다. 예약하지
  않으면 상한을 지키려 행을 쪼갠 직후 머리말로 다시 넘어간다(실측: 1,022자).
- **한 문단에 개체가 둘 이상 매달리면 XML 순서가 곧 화면 순서가 아니다** (2026-08-13,
  실물에서 확인). 제목상자(1칸 표, `treatAsChar="1"`)와 본문 표(`treatAsChar="0"`,
  `vertOffset="5940"`)가 **같은 문단**에 매달려 있는데 XML 에는 본문 표가 먼저 있어서
  **문서 제목이 표 뒤로 밀렸다** — 표 조각 어디에도 제목이 없고 마지막 청크에서 제목·날짜·
  서명이 한 덩어리가 됐다. `hp:pos` 로 세로 위치를 읽어 정렬한다(글자처럼 취급 = 0,
  그 외는 `vertOffset`). **기준이 문단(`vertRelTo="PARA"`)이 아니면 정렬을 포기하고 문서
  순서를 지킨다** — 페이지 기준 오프셋을 문단 기준 값과 비교하는 것은 순서를 지어내는 것이다.

### 2. 페이지를 지어내지 않는다

hwpx 는 **흐름 문서**라 렌더링 전에는 페이지가 없다. 기존 전처리기는 docling/PDF 를
거치며 `i_page` 와 bbox 를 얻지만 이 경로에는 그 정보가 없다.

| 필드 | 값 |
|---|---|
| `i_page`·`e_page`·`n_page`·`i_chunk_on_page`·`n_chunk_of_page` | **`None`** |
| `chunk_bboxes`·`media_files` | **`None`** |
| `i_section`·`n_section` | 섹션 번호로 대신 (추가 필드) |

**0 으로 채우면 1페이지처럼 읽힌다.** 틀린 페이지 번호는 없는 것보다 나쁘다.
페이지가 꼭 필요하면 PDF 변환 경로를 써야 하고, 그건 표가 깨지는 쪽이다 — 둘 중
하나를 고르는 것이지 이 모듈이 흉내 낼 일이 아니다.

### 3. 조/항/호는 **결정적 규칙**으로 읽는다 (2026-08-13 추가)

규정·법령 문서는 길이로만 자르면 **조 한가운데가 잘린다.** 표를 반으로 자르면 안 되는
것과 같은 이유다 — 뒤 조각은 "제5조" 라는 말이 없어 검색돼도 무엇에 대한 규정인지
알 수 없고, 두 조가 한 청크에 붙으면 검색이 엉뚱한 조를 근거로 든다.

**사다리는 문법이라 하드코딩이 맞다.** 편(1) 장(2) 절(3) 관(4) **조(5)** 항 `①`(6)
호 `1.`(7) 목 `가.`(8) — 발행처가 정한 표기이므로 마크다운 표 문법이나 hwpx 슬롯 문법과
같은 성격이다. LLM 에 물으면 **같은 문서가 적재할 때마다 다른 청크로 갈릴 수 있다**
(청크 경계는 결정적이어야 재적재가 재현된다). 지능형 전처리기처럼 레이아웃 모델에
맡기지 않는 이유는 따로 있다 — 그쪽 라벨은 깊이가 `TITLE`(0)/`SECTION_HEADER`(1) 로
평탄화돼 4단 위계를 담지 못한다. 이 경로는 hwpx XML 을 직접 읽어 문단 텍스트가 그대로
있으므로 표기에서 위계를 바로 읽는다.

**하드코딩하면 안 되는 것은 "어느 사다리인가" 다.** 같은 `1.` 이 법령에서는 호(조 아래
3단계)이고 공문서에서는 최상위 항목이다. 그래서 사다리를 무조건 걸지 않고
`outline_mode="auto"`(기본)가 **조 표기를 세어 본 뒤에만** 켠다 — `제N조` 는 목록
기호로 쓰이지 않아 오탐이 사실상 없고, 2개 미만이면 **아예 끄고 옛 동작 그대로 간다.**
일반 문서에 사다리를 걸면 `1.`·`가.` 목록이 전부 제목으로 승격돼 지금보다 나빠진다.

지키는 규칙 넷:

- **조 이상에서만 끊는다.** 항·호·목에서 끊으면 조문 하나가 문장 조각으로 부서진다.
  조가 상한을 넘을 때만 길이 기준이 안에서 작동하고, 그때 경계는 자연히 항(`①`) 머리에
  떨어진다.
- **인용은 제목이 아니다.** `제5조에 따라` 처럼 조사가 붙으면 본문이다. 문단 **첫머리**
  에서만 보고 뒤에 한글이 오면 막는다 — 이걸 놓치면 인용 자리에서 청크가 끊겨 앞 조의
  마지막 항이 뒤 조의 것처럼 검색된다. **조각을 눈으로 봐도 멀쩡해 보인다.**
- **조각마다 위계를 머리말로 인다** (`제2장 총칙 > 제5조(목적)`). 표 조각에 머리행을
  반복하는 것과 같은 이유이고, 임베딩되는 문자열에 들어가야 검색에 걸린다.
  `outline_path`/`outline_title` 로 따로도 싣는다 — 그쪽은 출처 표시·조 단위 필터용이다.
- **줄기에는 구조 제목까지만.** 항·호·목은 제목이 아니라 조문의 **내용**이라, 줄기에
  쌓으면 머리말이 본문 문장을 통째로 되풀이한다.

`제5조의2`(가지조문)·`부칙`(장 취급)을 함께 읽고, `2026. 8. 13.` 같은 날짜 문단이
1호로 잡히지 않게 호 번호를 두 자리로 제한한다.

### 4. VDB 필드 이름을 기존 것에 맞춘다

`genos_files/attach_processor.py` 의 `GenOSVectorMeta` 와 같은 이름을 쓴다. 검색 쪽
(`quick_search` MCP 도구)이 `file_name`·`file_path`·`i_page`·`i_chunk_on_doc` 를 읽어
출처를 표시하므로, **이름이 어긋나면 같은 컬렉션에 못 넣는다.**

`pydantic` 모델을 만들지 않고 **dict 를 낸다** — 붙일 곳이 정해지지 않은 부품이라
의존을 늘리지 않는 편이 합칠 때 자유롭다. 합치는 쪽에서 `GenOSVectorMeta(**record)` 로
감싸면 된다 (`extra='allow'` 라 추가 필드도 통과한다).

**이 경로에만 있는 필드도 그 규약을 따른다.** 표 조각 번호는 `i_table_part`(0-based) +
`n_table_part` 로 싣는다 — `i_page`/`n_page` 와 같은 모양이다. 예전 이름은
`table_part` 였는데, `i_` 접두어가 없으면 UI 가 `표 {값}/{총}` 을 그대로 찍어 **첫
조각이 "표 0/16" 이 되고 "16/16" 은 영영 안 나온다.** 본문 머리말(`(표 1/16)`)만
사람이 읽는 값이라 1-based 이고, 그 +1 은 `_table_prefix_for` 한 곳에서만 한다.

## 지능형 전처리기와 합치지 않고 **따로 등록한다**

> 2026-08-31 에 **합친 등록 단위도 생겼다**(`final_preprocessor.py`). 아래는 여전히
> 유효한 기본 선택지이고, 합치는 쪽의 근거·대가는 다음 절에 있다.

루트 `CLAUDE.md` 의 "hwpx 전용 전처리기" 절이 남겨 둔 질문은 "전처리기 커스터마이즈
지점이 등록하는 단일 파일뿐인가, 설치 패키지 `genon.preprocessor` 안에도 손댈 수
있는가" 였다. `genos_files/intelligence_processor.py`(지능형)·`attach_processor.py`
(첨부용) 는 **읽기 전용 참조 사본**이라 이 저장소에서 그 안을 고칠 수 없고, 고칠 수
있다 해도 설치 패키지 쪽은 다른 파일 형식(pdf/docx/xlsx/…)이 걸린 코드라 손대면
회귀 범위가 그쪽까지 넓어진다.

그래서 답을 (ㄱ) 으로 확정했다 — **hwpx 전용 전처리기를 새 등록 단위로 따로 올린다.**
지능형/첨부용 전처리기는 그대로 두고 손대지 않는다. GenOS 관리 화면에서 hwpx 업로드가
이 전처리기로 가도록 **연결(매핑)을 지정하는 것**이 붙이는 절차의 전부다 — 코드
쪽에서 더 할 일이 없다:

```python
from preprocessor import DocumentProcessor

processor = DocumentProcessor()          # 인자 없이 생성 가능 — GenOS 가 이렇게 부른다
records = await processor(request, file_path)   # file_path 가 .hwpx 가 아니면 즉시 예외
```

붙이는 시점에 확인할 것:

- **청크 크기** — 기본 `chunk_size=1000`/`chunk_overlap=100` 은 임시값이다(`__call__`
  의 `**kwargs` 로 등록 화면에서 조정한다). 임베딩 모델 컨텍스트에 맞춰야 한다.
- **토크나이저** — `ChunkOptions.length` 에 콜러블을 주입하면 문자 대신 토큰으로 잰다.
  기본이 문자인 이유는 **폐쇄망에 토크나이저 파일이 없을 수 있어서**이고, 없을 때
  청킹이 통째로 실패하는 것보다 대략적인 길이로라도 도는 편이 낫다. `DocumentProcessor`
  는 이 주입 경로를 아직 kwargs 로 노출하지 않는다 — 필요해지면 추가한다.
- **`security_level`** — 배포별 필드면 `extra_metadata` kwarg 로 넣는다
  (`to_records(extra=...)` 로 전달된다).
- **다른 파일 형식은 여전히 지능형/첨부용이 처리한다.** 등록 화면에서 **받을 확장자를
  고를 수 있다는 것이 확인됐다**(2026-08-14) — 이 전처리기는 **`hwpx` 만** 걸고 나머지는
  종전 전처리기에 그대로 둔다. 그러면 다른 형식은 이 파일에 도달하지 않는다.
  - **`.hwp`(구버전 바이너리)를 넣지 말 것.** 이 파서는 zip 기반 hwpx 전용이라 `.hwp` 는
    열지 못한다. 그쪽은 첨부용(GenosHwp SDK 네이티브 경로)이 우수하다.
  - 코드의 `SUPPORTED_EXTENSIONS = (".hwpx",)` 거부는 **그물로 남긴다.** 매핑을 잘못
    걸었을 때 이상한 결과를 조용히 내는 대신 그 자리에서 실패한다(§F 의 "미지원 확장자는
    명시적 오류").
  - **확장자 설정을 바꾸면 그 전처리기로 적재한 파일이 `needs_reingest` 가 된다**(§F).
    자동 재적재가 아니므로 매핑을 확정한 뒤에 올리는 것이 순서다.

> **지능형 전처리기를 이 파일에 이식하지 않는다.** 확장자를 고를 수 있으므로 이식할
> 이유가 없고, 대가만 크다 — 3,500줄 + docling·PDF 변환 의존을 떠안게 되고(지금은
> stdlib + `lxml` 뿐이라 어디서도 뜬다), GenOS 가 유지하는 읽기 전용 참조 사본을
> 우리가 복사해 유지 책임을 나눠 갖게 되며, hwpx 규칙만 고쳐도 **PDF·docx 적재분까지**
> 재적재 대상이 된다. 참조 구현 둘(첨부용·지능형)이 한 파일 안에서 확장자로 분기하는
> 것은 그쪽이 **전 확장자를 받는 등록**이기 때문이지 그것이 규약이라서가 아니다.

## 한 등록으로 합치는 길도 있다 — `final_preprocessor.py` (2026-08-31)

위 결정은 **없어지지 않았다.** 확장자별로 따로 등록할 수 있다면 그쪽이 여전히 단순하다.
다만 **등록을 하나로 가져가야 하는 경우**(확장자별 매핑을 나눌 수 없거나, 운영이 전처리기
등록을 하나로 유지하려는 경우)를 위해 합친 등록 단위를 만들었다.

```
onprem/preprocessor/
  hwpx_preprocessor.py           # hwpx 규칙의 **정본**. 여기서 고친다
  router_template.py             # 라우팅·폴백·스키마 정렬. 여기서 고친다
  build_final_preprocessor.py    # 위 둘 + GenOS 첨부용 참조 사본을 붙인다
  final_preprocessor.py          # ⚙ **생성물 · 외부 검증용**. 직접 고치지 말 것
  build_transfer_kit.py          # 타이핑할 자료를 만든다 (이관은 손으로 한다)
  transfer/                      # ⚙ **생성물 · 타이핑용**
```

> **이 파일을 그대로 등록 화면에 올리는 것이 아니다.** 폐쇄망에는 파일이 들어가지 않아
> 사람이 타이핑한다 — `final_preprocessor.py` 는 "합치면 이래야 한다" 를 외부에서
> 검증하는 물건이고, 실제로 치는 것은 `transfer/` 다. 위 "온프레미스 이관" 절 참고.

### 지능형은 **걷어냈다** (2026-09-01)

2026-08-31 에는 지능형(`intelligence_processor.py`)도 함께 붙여 pdf·ppt·엑셀·이미지를
그쪽으로 보냈다. **그 경로가 실환경에서 동작하지 않아 통째로 뺐다.** 지금 등록 단위는
**첨부용 + hwpx** 둘이고, hwpx 가 아닌 것은 전부 첨부용으로 간다.

> 그전에 적어 둔 "두 벤더의 약한 쪽이 정확히 반대라 한 엔진만 고르면 어느 형식이든
> 손해가 난다" 는 **여전히 사실이다.** 다만 지능형이 안 도는 상태에서는 그 선택지가
> 없다 — 손해를 감수하고 적재를 살렸다.

**대가는 pdf 한 자리다.** 첨부용 pdf 는 `PyMuPDFLoader` 평문 + 문자 수 분할이라:

- **표 격자가 문장으로 풀린다.** 지능형은 TableFormer 로 격자를 복원했다. 이건
  이 전처리기를 만든 이유(요구사항 §5 "표 깨짐")가 pdf 에서 재현되는 것이다.
- **스캔 PDF 는 OCR 폴백이 없어 빈 청크**가 된다.
- 오류는 나지 않고 적재도 되므로, 두 사실은 **"표를 물어봤는데 답이 이상하다" 로만**
  드러난다.

**pdf 의 조/항/호 위계는 살렸다.** 원본 문서 모양이 `DoclingDocument` 에서 langchain
`Document` 목록으로 바뀌었을 뿐이라, 라우터에 어댑터를 하나 더 뒀다 — 아래 "조/항/호를
pdf·docx 에도" 절.

되살릴 자리는 셋이다: `build_final_preprocessor.py`(PART 2 복원 + 겹침 처리표) ·
`router_template.py`(`_FP_ROUTES`·`_FP_ENGINES`·`_fp_enable_outline`) ·
`onprem/test/check_final_preprocessor.py`. 지운 코드는
`git show f7c4aec:onprem/preprocessor/build_final_preprocessor.py` 로 꺼낸다.

**형식별로 첨부용이 무엇을 쓰는지**(그대로다):

| 형식 | 첨부용 경로 |
|---|---|
| `.docx` | `GenosMsWordDocumentBackend` 네이티브 + `HybridChunker` |
| `.hwp`·`.hml` | GenosHwp SDK 네이티브 (실패 시 레거시 → 최후에 PDF) |
| `.ppt(x)` | PDF 변환 + 경량 docling (실패 시 langchain 폴백) |
| 엑셀·`.csv` | `TabularLoader` 직접 처리 |
| 오디오 | Whisper STT (**지능형에는 이 경로가 아예 없었다**) |
| `.txt`·`.md`·`.json` | `TextLoader` |
| `.pdf`·이미지 | `PyMuPDFLoader` / `UnstructuredImageLoader` + 문자 수 분할 |

**`.hwp` 는 첨부용으로 보낸다** — 우리 파서는 zip 기반 hwpx 전용이고, 그쪽이 네이티브로
읽는다. hwpx 파서의 `SUPPORTED_EXTENSIONS` 거부는 잘못 건 매핑을 드러내는 그물로 그대로
남는다. **hwpx 파싱 실패 시 폴백도 첨부용**이다 — 같은 이유로 덜 잃는다.

**문서 본문 200자가 컨테이너 로그에 남는다.** §3.8 이 금지하는 것이고 확인용으로 일부러
넣었다 — **운영에 그대로 두지 말 것.**

### 합친 순서가 계약이다 — 겹치는 셋을 어떻게 했나

**첨부용 → hwpx → 라우터.** 한 네임스페이스라 뒤엣것이 앞엣것을 덮는다.

> 지능형이 있던 시절에는 첨부용과 최상위 이름 **24개**가 겹쳐 제거 13 / 개명 8 / 보존 3
> 으로 갈랐고, 그 분류를 AST 로 다시 계산해 지키는 `_classify_overlap` 이 빌드에 있었다.
> **지능형이 빠지며 그 겹침이 통째로 없어졌다** — 지웠던 13개는 첨부용 안으로 돌아왔고
> 개명했던 8개 중 7개는 원래 이름을 되찾았다.

지금 겹치는 것은 셋이다:

| 이름 | 어디서 | 어떻게 |
|---|---|---|
| `DocumentProcessor` | 셋 다 정의한다 | 첨부용 → `AttachDocumentProcessor`, hwpx → `HwpxDocumentProcessor`. **GenOS 가 실행하는 것은 마지막에 남는 하나**라 라우터 것이 그 이름을 가진다 |
| `Document` | 첨부용은 langchain 것을 import, hwpx 는 같은 이름의 데이터클래스를 정의 | hwpx → `HwpxDocument`. hwpx 가 뒤라 그대로 두면 첨부용의 20개 호출부가 터진다 — **import 는 통과하고 호출할 때** |
| `_log` | 둘 다 `logging.getLogger(__name__)` | 그대로 둔다. 한 모듈이라 `__name__` 이 같아 **결국 같은 객체**다 |

개명한 자리에는 `# [병합 개명]` 표식 주석이 있다. 허용 목록(`_ALLOWED_DUPLICATES`)은
`_log` 하나뿐이고 **그 밖이 겹치면 빌드를 세운다** — 목록을 넉넉히 두지 않는 것이
요점이다. GenOS 가 참조 사본을 갱신하며 hwpx 와 같은 이름을 새로 정의하면 그 순간
잡혀야 한다.

### 손으로 붙이지 않고 **생성한다**

첨부용 참조 사본은 GenOS 가 릴리스마다 갱신한다(파일 첫 줄에 버전이 박혀 있다). 손으로
옮겨 적으면 다음 릴리스에서 무엇이 바뀌었는지 대조할 수 없고, 그 어긋남은 **오류로
드러나지 않는다** — 새로 생긴 포맷 지원이나 버그 수정이 조용히 빠질 뿐이다.

```
python onprem/preprocessor/build_final_preprocessor.py
```

빌드가 네 함정을 막는다: (1) `from __future__ import annotations` 는 파일 맨 앞에만
올 수 있으므로 떼어내 한 번만 둔다, (2) 첨부용 절반은 통째로 `try:` 안으로 들어가는데
**줄마다 공백을 붙이면 여러 줄 문자열 27개의 내용이 바뀌므로** `tokenize` 로 문자열
안쪽을 가려낸다, (3) 조각이 한 네임스페이스에 들어오므로 이름이 겹치면 빌드를 세운다
(MCP 파일 넷을 합칠 때 실제로 밟은 함정이다 — 단 **같은 모듈에서 같은 이름을 가져온
import 는 겹쳐도 같은 물건**이라 통과시킨다), (4) 개명은 **토큰 단위**로 한다 —
정규식은 문자열 리터럴까지 바꾼다(`[DocumentProcessor]` 로 시작하는 로그 문자열이
있다). 그리고 **AST 로 원본과 대조**하고, 개명은 **AST 트랜스포머라는 독립 구현으로
교차 확인**한다 — 문자열이 한 글자만 달라지거나 토큰 치환이 속성·키워드 인자를
건드리면 걸린다.

### 벤더 스택이 없어도 이 파일은 import 된다

첨부용 절반이 `try:` 안에 있어서, docling·`genon.preprocessor.*` 가 없으면 그 절반만
비활성이 되고 hwpx 경로는 그대로 돈다. 이유는 둘이다 — 무거운 의존 하나가 빠졌을 때
hwpx 적재까지 같이 죽으면 안 되고, 회귀 점검이 로컬(stdlib + `lxml`)에서 이 파일을
import 할 수 있어야 한다. **비활성 사실은 숨기지 않는다**: 생성 시점에 경고를 남기고,
그 엔진으로 갈 파일이 들어오면 사유를 담아 예외를 던진다.

> 지능형이 있던 시절에는 **첨부용이 지능형 절반에도 의존**했다(지운 13개의 자리를
> 지능형 판본이 채웠다). 라우터가 그것을 갈라 보고했는데, 지금은 첨부용이 자기 정의를
> 전부 들고 있어 **첨부용의 가부는 첨부용 적재 결과 하나로 정해진다.**

### 사이트 설치본이 참조 사본보다 **낡을 수 있다** (2026-09-02)

실환경에서 pdf 적재가 이렇게 막혔다:

```
'attach' 전처리 경로를 사용할 수 없어 이 형식은 처리할 수 없습니다
(ModuleNotFoundError: No module named
 'genon.preprocessor.facade.enrichment.page_description')
```

`genos_files/attach_processor.py`(v.2.2.4 참조 사본)가 그 모듈을 **최상위에서** 들여
오는데 사이트에 설치된 `genon.preprocessor` 에는 없다. 그러면 위 절의 가드가 첨부용
절반을 통째로 비활성으로 만들고, 라우터가 **hwpx 아닌 전 형식을 거부한다.**

- **증상이 원인을 가린다.** hwpx 는 가드 밖이라 그대로 돌기 때문에 **"pdf 만 안 되는"**
  얼굴로 나타난다. import 한 줄 때문에 전 형식이 막혔다는 것이 드러나지 않는다.
- **그 import 하나만 감쌌다** (`build_final_preprocessor.py` 의
  `_ATTACH_OPTIONAL_IMPORTS`). **PPT 페이지 단위 이미지 설명 전용 심볼**이라
  (`attach_processor.py:1831`·`:2050`) pdf·docx 경로는 지나지 않고, 없을 때
  `enabled=False` 스텁으로 떨어뜨리면 **PPT 설명만 빠진다**(벤더의
  `page_description.enable=false` 와 같은 상태).
- **이관 절차(`transfer/`)에는 이 가드가 필요 없다.** 그쪽은 벤더 절반을 **사이트 자기
  파일**로 뜨므로 그 사이트 패키지와 짝이 맞는다. 이 가드는 우리가 만든
  `final_preprocessor.py` 를 **그대로 등록할 때**를 위한 것이다.
- **다음 오류가 나도 목록을 늘리기 전에 판본을 확인할 것.** 가드는 첫 실패에서 멈추므로
  뒤에 또 없는 모듈이 있으면 그것이 다음 오류로 나온다. 특히 `:460` 의 `guardrail` 은
  **민감정보 마스킹(#315)** 이 걸린 자리라 스텁으로 덮으면 마스킹이 **조용히** 빠진다 —
  그건 패키지를 맞춰야 하는 문제다.
- **미검증**: 실물 설치본에서 이 가드로 pdf 가 실제로 적재되는 것은 확인하지 못했다.
  로컬에는 docling 이 없어 첨부용 절반이 아예 안 뜨므로, 점검이 보는 것은 **스텁 자체의
  동작과 생성물에 가드가 살아 있는가**까지다.

### 조/항/호를 **pdf·docx 에도** 매긴다 (2026-09-01)

설계 결정 3(조문 위계)이 hwpx 전용이 아니게 됐다. 규정집이 hwpx 로만 오지 않기 때문이다.

**위계 층은 원래부터 포맷 중립이었다.** `annotate_outline`·`chunk_blocks` 는
`Block(kind, text, section)` 만 보고, hwpx 전용인 것은 `parse()` 하나다. 그래서 새로
만든 것은 **어댑터 하나**(`_fp_docling_blocks`)이고 조 경계 청킹·머리말·표 분할은
그대로 재사용된다.

- **벤더의 청커만 갈아 끼운다.** 두 벤더가 같은 3단이다 —
  `load_documents() → split_documents() → compose_vectors()`. 가운데만 바꾸고
  **`compose_vectors` 는 벤더 것을 그대로 쓴다**: 그쪽이 bbox·이미지 업로드·
  **민감정보 마스킹(#315)**·페이지 카운트를 붙인다. 우회하면 그 값들이 조용히 사라지고
  레코드는 멀쩡해 보인다.
- **그래서 청크가 출처를 들고 다녀야 한다.** `Block.origin`/`Chunk.origin` 이
  원본 항목을 실어 나른다(hwpx 경로에서는 **언제나 비어 있다** — 실물 5벌 출력이
  변경 전후로 같다). 비면 `compose_vectors` 가 `doc_items[0]` 에서 `IndexError` 로
  죽어 **적재가 통째로 실패하므로**, 하나라도 비면 벤더 청커로 돌아간다.
- **원본 모양이 둘, 산출 모양이 셋이다** (2026-09-01 에 하나씩 늘었다):

  | 거는 자리 | 받는 것 | 내는 것 |
  |---|---|---|
  | 첨부용 **최상위**(pdf·이미지·txt·md) | langchain `Document` 목록 | 같은 목록 (`page_content`/`metadata`) |
  | 첨부용 `docx_processor`, `chunker_type="recursive"`(기본) | `DoclingDocument` | dict `{text, page_no, doc_items}` |
  | 첨부용 `docx_processor`, 그 밖 | `DoclingDocument` | `DocChunk` |

  **가운데(위계 판정·조 경계 청킹)는 하나다** — `Block` 으로 옮기고 나면 어디서
  왔는지 알 필요가 없다. 갈라지는 것은 입구의 어댑터와 출구의 조립뿐이다.
  langchain 쪽 조립은 **클래스를 이름으로 찾지 않고 `type(원본)` 으로 만든다** —
  라우터는 벤더 가드 밖이라 `Document` 라는 전역이 있다는 보장이 없다.
  metadata 는 **청크마다 사본**이어야 한다(원본을 물리면 뒤 청크가 앞 청크의 페이지를
  바꾼다. 점검이 값이 아니라 **정체**로 본다 — 값 비교는 원본 페이지가 다르면
  공유해도 통과한다).
- **`headings` 는 채우지 않는다.** 두 벤더의 compose 가 그 값을 본문 앞에 다시 붙이는데
  우리 청크에는 조문 머리말이 이미 들어 있다 — 채우면 같은 제목이 두 번 실린다.
- **글자 없는 항목(그림)을 버리지 않는다.** 다음 블록에 얹어 청크까지 따라가게 한다.
  빼면 이미지 업로드가 통째로 빠지는데 오류는 안 난다 — 그림이 없는 문서로 보일 뿐이다.
- **구역(`section`)은 전부 0 이다.** 페이지를 구역으로 쓰면 `chunk_blocks` 가 구역
  경계에서 끊으므로 **페이지를 걸친 조가 반으로 갈린다** — 조가 검색 단위라는 전제와
  정면으로 어긋난다.
- **표는 여기서도 한 줄 HTML 이다**(`column_header` 가 있으면 그 행이 `<th>`, 없으면
  hwpx 와 같이 첫 행). 덮인 자리에는 칸을 내지 않는다 — 내면 그 행만 열이 하나 는다.
- **판정은 kwargs 와 문서 내용만 본다.** 처리기 인스턴스는 요청 사이에 공유되므로
  "이번 요청에는 켜라" 를 인스턴스 속성에 적으면 동시 요청끼리 서로의 설정을 본다.
- **실패는 폴백이지 오류가 아니다.** 어댑터가 죽든 docling 이 없든 벤더 청커로 돌아간다
  (hwpx 폴백 규약과 같다) — 다만 로그에 남긴다.
- **거는 자리는 pdf·docx 둘뿐이다**(`_fp_enable_outline`). `.hwp` 를 넣으려면
  `processor.hwp_processor` 에 같은 줄을 하나 더 걸면 된다 — 요구 범위 밖이라 안 걸었다.
  **pdf 는 첨부용 최상위다**: 첨부용 `__call__` 이 `.docx` 는 `docx_processor` 로,
  `.hwp` 계열은 `hwp_processor` 로 보내고 **나머지는 자기 안에서** 3단을 돈다.

**켜지는 조건은 hwpx 와 같다** — `auto` 는 `제N조` 표기를 2개 이상 세었을 때만 켠다.
그래서 **조문 문서가 아닌 pdf·docx 의 산출물은 벤더 청커 그대로**이고, 이것이 이
변경의 회귀 위험이 낮은 이유다. 최상위에 걸면 이미지·txt·md·json 과 hwp/ppt 의 PDF
변환 폴백 경로가 같은 `split_documents` 를 지나지만, 그 갈래들도 이 조건에 걸린다.
`statute` 를 명시하면 전부에 걸린다 — 그 선택은 등록자가 한 것이다.

**pdf 는 "표기가 텍스트로 남는다" 는 가정 위에 있다.** `PyMuPDFLoader` 가 `제5조`·`①`
을 줄 머리에 남겨 주어야 한다 — 어댑터가 **줄 단위로** 가르고 `_match_statute` 가
줄 머리에서 표기를 읽기 때문이다. 스캔 PDF 의 OCR 오인식·2단 조판의 읽기 순서는
남는다. **실물 pdf 로 확인하지 못했다** — 아래 "아직 확인 못 한 것".

> **지능형이 있던 시절 이 가정은 docling 레이아웃에 걸려 있었다** — 그쪽은
> `merge_list_items` 가 항·호를 앞 문단에 병합하는 것이 위험이었고, 우리가 청커 앞에서
> 가로채 피했다. 지금은 로더가 `PyMuPDFLoader` 라 그 단계 자체가 없다. **대신 페이지가
> 곧 `Document` 경계**라, 페이지를 구역으로 쓰지 않는 것이 이쪽의 핵심 가드다.

`align_vector_schema` 가 있는 이유: **한 등록이 한 컬렉션에 두 모양의 메타를 넣으면**
그 필드로 거르는 검색이 한쪽을 통째로 놓치는데, 그 상태는 오류가 아니라 "결과가 좀
적네" 로만 보인다. 값은 벤더가 못 채웠을 때 내는 것과 같은 것을 쓴다 — **지어내지
않는다.**

### 합치는 대가 — 이건 없어지지 않았다

**hwpx 청킹 규칙만 고쳐도 이 등록으로 적재한 PDF·docx 까지 `needs_reingest` 가 된다**

등록을 나누는 쪽(`hwpx_preprocessor.py` 단독)이 여전히 낫다.

```bash
export PYTHONIOENCODING=utf-8
cd SFR-018 && python -m unittest tests.test_preprocessor_chunking   # 103건

# 합친 등록 단위 — 생성물이 원본 둘과 맞는가 + 라우팅·폴백·스키마 정렬
python onprem/test/check_final_preprocessor.py                     # 168건
#   실물 hwpx 5벌은 `data/` 에서 **있는 것만** 태운다 — 경로가 어긋나면 147 로

#   위계 청킹이 **두 갈래**다 — docling(docx) 대역과 langchain(pdf) 대역을 각각
#   등록 단위 밖에서 꽂는다.
```

`check_final_preprocessor.py` 가 따로 있는 이유는 `final_preprocessor.py` 가 **생성물**
이기 때문이다. 생성 스크립트를 안 돌리고 커밋하면 원본과 갈리는데 **그 상태도 정상으로
돈다** — 그래서 점검이 다시 생성해 대조한다. 겹침 처리도 본다 — 지운 13개가 하나로
정리됐는지, 개명한 8개가 **둘 다** 살아 있는지, 분류가 원본과 여전히 맞는지. 라우팅은
형식별 엔진과 hwpx 내용 확인을 본다(hwpx 가 벤더로 새면 표가 깨지는데 **적재는 성공으로
보이고**, pdf 가 hwpx 파서로 가면 그 문서가 검색에서 통째로 사라진다). 벤더가 있을 때만
도는 갈래(지연 생성·폴백·kwargs 전달)는 **대역을 등록 단위 밖에서 꽂아** 태운다.
**여덟 갈래를 각각 되돌려 FAIL 을 확인했다.**

pdf·docx 위계 청킹도 같은 방식이다 — 어댑터가 보는 것은 `iterate_items()`·`item.text`·
`item.data.table_cells`·`item.prov` 뿐이라 **그 모양만 갖춘 대역이면 검사된다.** 실물
docling 을 요구하게 두면 이 층을 보는 점검이 **0건이 된다.** 여기서도 여섯 갈래를 각각
되돌려 FAIL 을 봤다: 출처 전파 · 글자 없는 항목 · 조 경계 · `auto` 판정 · `headings` ·
덮인 자리. 마지막 것은 처음에 `<tr>` 개수로 봤는데 **행 수는 그대로라 안 잡혔다** —
행별 칸 수를 세도록 고치고 다시 확인했다.

지키는 것: 블록 순서, 표 형식(언제나 HTML), **표를 쪼개도 행이 새지 않음**, 조각마다 머리행
반복, 표가 문단과 안 섞임, 긴 문단은 문장 경계로 분할, VDB 필드 존재, 페이지 필드가
`None`(0 이 아님), 그리고 `docs/GENOS_RULES.md` §F 가 요구하는 `DocumentProcessor`
필수 케이스(정상/빈 파일/손상 파일/미지원 확장자/파라미터 경계).

표 조각 머리말은 **조각 번호·제목이 본문에 들어가는지**, 본문 문단을 제목으로 오인하지
않는지, 제목이 다음 표로 새지 않는지, 조문 문서에서 머리말이 두 겹이 되지 않는지를 본다.
조각 번호는 **레코드가 `i_table_part`(0-based) 라는 것과 본문 머리말(1-based)이 같은
조각을 가리키는지**, 옛 이름 `table_part` 가 남지 않았는지, 안 쪼갠 표에는 키 자체가 없는지를
본다(1/1 을 달면 "쪼개진 표" 로 읽힌다).
초과 행 분할은 **상한 준수·무손실·무중복**, 짧은 칸 반복, 열 수 불변, 생략 표시,
**병합·중첩이 걸린 행은 셀 안에서 쪼개지 않음**(병합 선언 복제·안쪽 표 갈림), 그리고
**쪼갤 필요 없는 표는 건드리지 않음**을 본다. 표 형식은 병합이 없는 표도 HTML 로 나가는지와
첫 행이 `<th>` 인지를 본다. 매달린 개체 순서는
글자처럼 취급된 상자가 먼저 나오는지와 **기준이 다르면 문서 순서를 지키는지**를 본다.

조문 위계는 **사다리 자체**(8단계 레벨, 가지조문, 부칙, 인용 배제, 날짜 오탐),
**언제 켜지나**(auto 문턱·강제·해제·잘못된 값), **청킹**(조가 안 섞임, 항·호·목에서
안 끊김, 길 때만 항 경계로 갈림, 머리말 중복 없음, 짧은 조가 앞 조에 안 흡수됨,
제목 문단을 버려도 글자는 남음, 일반 문서는 옛 동작과 **바이트까지 동일**)을 본다.

**누락 없음**은 손실 자리마다 판정을 하나씩 세웠다 — 탭·줄바꿈·조판 공백 뒤 글자,
글상자·각주·머리말·꼬리말·숨은 설명·메모, 표 캡션(그리고 **두 번 나오지 않는지**),
셀 안 상자, 상자 안 표, 수식, 글머리표 복원, 개요 번호의 증가·하위 초기화·빈 문단
소비·셀 안 적용, 표시 문자열이 없는 단계, `header.xml` 부재·손상, **`@idRef` 해석**
(실물 모양 인덱스 참조·정의 부재 폴백·`@char` 없는 글머리표·sentinel·카운터 공유).

**되돌려 확인했다** — 조 경계 끊기·인용 가드·줄기 깊이 제한·섹션 번호 수정을 각각
옛 코드로 되돌리면 해당 테스트가 FAIL 한다(6/1/2/1건). 누락 방지 셋도 같은 방식으로
확인했다: `tail` 처리 제거 → 3건, 상자 버리기 → 6건, 번호 복원 제거 → 5건 FAIL.
`@idRef` 해석 5갈래도 각각 되돌려 봤다 — 인덱스 폴백 제거 → 3건, 카운터를 원본 ref 로
→ 1건, 숫자 폴백 제거 → 1건, sentinel 가드 제거 → 1건, 글머리표 폴백 제거 → 1건 FAIL.

만들면서 테스트가 잡은 실제 버그 셋:

1. 문장 분리 정규식이 `(?<=[다요])\.\s+` 로 **마침표를 소비**해, 쪼개진 문단에서 `.`
   가 조용히 사라지고 있었다. 청킹이 본문 글자를 지우면 검색 결과에 원문과 다른
   문장이 뜬다.
2. `ChunkOptions` 에 `overlap_chars >= max_chars` 를 넣으면 문자 분할 예외 경로
   (`_split_long_text`)가 **같은 조각을 무한히 반복**했다 — 매 반복 전진폭이
   `max_chars - overlap_chars` 인데 그 값이 0 이하가 되기 때문이다. GenOS 등록
   화면에 파라미터를 잘못 입력해도 재적재가 멈추면 안 되므로
   `ChunkOptions.__post_init__` 에서 항상 `overlap_chars < max_chars` 로 clamp 한다.
3. **표 뒤에서 시작하는 청크가 앞 청크의 섹션 번호를 물려받고 있었다.** 버퍼가 빌 때
   `not chunks and not buffer_section` 일 때만 섹션을 잡았는데, 길이 초과로 끊길 때는
   따로 갱신하므로 드러나지 않고 **표를 만나 끊긴 뒤에만** 값이 얼어붙었다. 검색 결과
   출처가 틀린 섹션을 가리키는데 화면에는 정상으로 보인다. (조문 위계 작업 중 발견 —
   `outline_path` 도 같은 자리에서 정해지므로 함께 틀렸을 자리다.)

## 아직 안 한 것

- **조문 위계는 실물로 확인하지 못했다** — 사내 규정 hwpx 로 `outline_mode="auto"` 가
  실제로 켜지는지, 이름표가 쓸 만한지 봐야 한다. 아래 실물 점검에 쓴 기술협상서에는
  `제N조` 표기가 없어 위계가 **켜지지 않았다**(설계대로다).
- **상한 초과를 로그로 남기지 않는다.** 초과 행을 셀 안에서 나누는 것 자체는 설계 결정 1
  에 적은 대로 구현했다(실물 두 벌에서 **초과 청크 0개**, 최장 999자 / 993자 — 그전에는
  1,929자 청크가 나왔다). 다만 **병합·중첩이 걸린 행은 행 단위에서 멈추므로** 그 경우는
  여전히 상한을 넘을 수 있고, 넘겼다는 사실을 경고로 남기는 코드는 없다. 병합표 실물에서
  초과가 실제로 나오면 그때 붙일 것 — 지금 남은 위험은 "셀 단위로 못 나눈다" 가 아니라
  "못 나눈 자리를 조용히 지나간다" 다.
- **공문서 사다리**(`1.` → `가.` → `1)` → `(1)` → `①`) — 붙이지 않았다. 규칙 표
  (`_STATUTE_RULES`)에 한 줄 더 얹으면 되는 모양이지만, 그쪽 기호는 법령 사다리와
  **레벨이 정면으로 어긋나서**(법령의 `1.` 은 호, 공문서의 `1.` 은 최상위) 실물 없이
  넣으면 어느 쪽이든 틀린다. 필요해지면 `outline_mode="document"` 로 **명시 opt-in**
  으로만 열 것 — auto 로는 절대 켜지 말아야 한다.
- **페이지 구분 인식** — hwpx 의 페이지 나눔 컨트롤을 읽으면 `<!-- PB -->` 마커를 낼 수
  있을지 모른다. 확인하지 않았다.
- **이미지** — 뽑지 않는다. `media_files` 가 늘 `None` 인 이유다. (**수식은 2026-08-19
  부터 뽑는다** — `hp:script` 의 원본 문자열 그대로이고, 렌더된 모양이 아니다.)
- **`hwpx_preprocessor.py` 는 `check_table_grid.py` 의 1·2층 대조 대상이 아니다.**
  표 렌더링이 일부러 다르기 때문이다(여기는 언제나 HTML + `<th>`). **3층(누락 방지)에는
  들어간다** — 2026-08-23 부터 이 파일이 그 층의 **정본**이고, 점검이 네 사본의 문단
  텍스트를 여기 출력과 맞춘다. 여전히 이 파일에만 있는 것은 **조문 위계·청킹**이다 —
  RAG 적재에 필요한 것이지 LLM 입력 경로에 필요한 것이 아니다. **1칸 표를 문단으로
  내는 판정(`_boxed_text`)은 2026-08-23 에 넷으로 함께 갔다** — 저장소 실물 기술협상서
  2벌이 문서 제목을 1칸 표로 담고 있어, 사본에 없으면 제목이 `| 『…』 |` + `|---|` 로
  나가고 다섯 벌의 문단 텍스트가 갈린다.
- **표 요약(`[표 설명]`)** — 지능형 전처리기는 표마다 요약을 붙인다. 그건 LLM 호출이라
  이 패키지 밖의 일이다.
