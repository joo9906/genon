## 1. 한 눈에 보기

**결론: 우리가 만든 것의 핵심은 이 라이브러리로 대체되지 않는다.** 슬롯 문법, 세션·대화,
톤, 근거 검증은 대응물이 없거나 요구사항이 우리 쪽이 더 구체적이다.

가져온 것은 **우리에게 없던 층**이다 — *검증*과 *측정*. 특히 개봉 안전 검사는
"이 저장소에는 한/글이 없어 산출물이 열리는지 확인할 수 없다" 는, 006·FAQ 양쪽에
남아 있던 공백을 **한/글 없이** 닫는다.

대조 과정에서 실물 결함 둘이 나왔고(§3) 둘 다 고쳤다. 하나는 이미 산출물에 나가고 있었고,
다른 하나는 미입력 필드를 입력됨으로 판정하던 동작 결함이다.

## 2. 대체 가능성 판정

| 우리 구현 | 라이브러리 대응 | 판정 |
|---|---|---|
| 슬롯 문법 `{'제목', 16pt, 고딕, 볼드}` (`hwpx_fields.py`) | 없음 (`{{token}}`·누름틀·라벨셀만) | **대체 불가 — 우리 고유 도메인** |
| 세션·대화·톤·근거 검증 | 없음 (문서 라이브러리다) | **대체 불가** |
| FAQ 반복 블록 확장 (`faq/exporters/hwpx_export.py`) | `merge_template_rows` 는 **행당 문서 1개** 생성 — 한 문서 안 N개 반복이 아니다 | **대체 불가** |
| 서식 `charPr` 파생 (`hwpx_style.py`) | `body_patch._materialize_restyled_charpr` (동형 로직) | 부분 — 슬롯 결합부는 우리 것 |
| 본문 블록 문단 복제 (`hwpx_blocks.py`) | `body_patch` 의 `insert_paragraph_by_clone` op | 부분 대체 가능 |
| hwpx→markdown 추출기 **3벌** (006 / 번역 / FAQ) | `export_markdown` 하나 | 대체 가능 — **이번에는 안 했다**(§5) |
| 누름틀 스캔·채움 | `doc.fields.add/all/fill` | 대체 가능 |
| 산출물 검증 — **없었다** | `validate_editor_open_safety` | **가져왔다**(§4-2) |
| 값 넘침 판정 — **없었다** | `form_fit.measure` | **가져왔다**(§4-3) |
| eval 무결성 지표 | `doc_diff` (`doc-diff-v1`) | **가져왔다**(§4-4) |

## 3. 실측으로 찾은 결함 둘

### 3.1 파트 XML 선언에서 `standalone="yes"` 가 빠지고 있었다

한/글이 쓴 원본 파트는 `<?xml version="1.0" encoding="UTF-8" standalone="yes" ?>` 로
시작한다. `etree.tostring(root, xml_declaration=True)` 는 standalone 을 빼고 쓴다.
실제 산출물이 그 상태였다:

```
data/파워.hwpx      (한컴 원본) : <?xml version="1.0" encoding="UTF-8" standalone="yes" ?>
data/FAQ_결과.hwpx  (우리 산출) : <?xml version='1.0' encoding='UTF-8'?>
```

OWPML 패키지 검사기는 이것을 파트 오류로 잡되 **advisory** 로 분류한다 — 실한컴이
그래도 열어 주는 것이 관측된 항목이라 지금까지 드러나지 않았을 뿐, **원본과 다른 파일을
내보내고 있었다.**

한 가지는 확인해 둘 만하다: 재직렬화 diff 를 뜨면 **다른 차이는 0** 이었다. lxml 이
나머지는 바이트 그대로 보존한다. 즉 우리 재직렬화 경로의 유일한 손실이 이것이었고,
인자 하나로 닫혔다.

### 3.2 누름틀 안내문을 "첫 stringParam" 으로 잡고 있었다 — 동작 결함

실한컴 CLICK_HERE 필드는 파라미터가 둘이고 **원시 명령 블롭이 먼저** 온다:

```xml
<hp:stringParam name="Command">Clickhere:set:51:Direction:wstring:9:이름을 적으세요 HelpState:…</hp:stringParam>
<hp:stringParam name="Direction">이름을 적으세요</hp:stringParam>
```

옛 구현(`_first_string_param_text`)은 "한/글 버전마다 name 이 다를 수 있으니 첫 것" 이라는
근거로 **Command 블롭을 안내문으로** 잡았다. 결과가 둘로 샜다:

1. `Clickhere:set:51:…` 이 그대로 LLM 프롬프트·화면의 안내문이 됐다.
2. **미입력 필드가 입력됨으로 판정됐다.** `filled` 는 `현재텍스트 != guide` 인데, 빈
   필드의 현재 텍스트는 안내문("이름을 적으세요")이고 guide 는 블롭이라 둘이 늘 달랐다.
   `missing_field_names` 가 그 필드를 빼면서 **사용자에게 묻지도 않고 안내문이 값인 채로
   문서가 나간다** — 부분 초안 계약이 여기서 무너진다.

**같은 결함이 `eval/eval_mcp/structure_metrics.py` 의 `_guide_text` 에도 있었다.**
이쪽이 더 나쁘다. "파서를 공유하면 파서 버그를 함께 놓친다" 는 규칙으로 두 벌을 유지했는데,
두 벌을 같은 손이 같은 가정으로 써서 **지표가 결함을 승인하고 있었다.** 규칙은 지켰고
목적은 놓친 상태다. 둘 다 고쳤고, 그 위에 제3의 구현으로 교차검증을 붙였다(§4-4).

## 4. 적용한 것

### 4.1 재직렬화 일원화 — `hwpx_fields.serialize_part`

재직렬화가 세 모듈에 흩어져 있었다(`hwpx_fields`·`hwpx_style`·`hwpx_blocks`, 5개 호출).
한 곳만 고치면 나머지가 남으므로 한 함수로 모았다. FAQ 는 **배포 단위가 달라 import 하지
않고** 같은 규칙을 자기 파일에 적는다.

### 4.2 개봉 안전 게이트 — `hwpx_verify.py`

`document.build` 의 마지막 단계다. 산출 바이트를 `validate_editor_open_safety` 로 재고,
**개봉을 막는 오류가 있으면 아무것도 내보내지 않는다**(fail-closed). 검사기는 셋을 본다:
OPC 패키지 계약, OWPML 문서 스키마, 그리고 산출 바이트를 실제로 다시 열어 보기.

세 가지 설계 결정이 있다.

- **차단과 경고를 나눈다.** advisory(실한컴이 열어 주는 것이 관측된 항목)로는 막지 않는다.
  전부 막으면 열리는 문서를 못 열린다고 거절하는 쪽으로 틀린다.
- **라이브러리가 없으면 통과시킨다.** 워크플로우(02) pod 는 `requirements.txt` 를 설치하지
  않는다(가이드 11.5.6). 검사기가 없다는 이유로 문서 생성을 막으면 *검사를 붙였다는 사실
  자체가 기능을 죽인다.* 대신 `open_safety_checked=False` 와 `X-Open-Safety-Checked: 0`
  으로 **미판정을 통과와 구분해** 드러낸다.
- **미리보기는 검사하지 않는다**(`verify=False`). 파일이 나가지 않고, 턴마다 도는 경로에
  문서 재개봉을 얹으면 대화가 그만큼 느려진다. 다운로드 경로에서는 같은 바이트가 반드시
  검사를 받는다.

오류는 `TemplateError` 로 올려 기존 경로(`ERR_API_INPUT`)를 탄다. 새 오류 코드를 만들지
않은 이유는 사용자가 할 일이 같기 때문이다 — 템플릿을 고쳐 다시 올린다.

### 4.3 값 넘침 측정 — `overflow.py`

표 셀 슬롯에 값이 들어갈 때 칸을 넘치는지 `form_fit` 으로 추정한다. 셀 폭에서 좌우 여백과
인라인 개체 폭을 빼고, 그 셀의 글꼴 크기·줄간격으로 예상 폭·줄 수를 낸다. 폭 추정 모델은
한/글 자신의 `lineSeg/@horzsize` 와 대조해 맞춘 것이라 우리가 다시 만들 이유가 없다.
**우리 몫은 어느 자리가 슬롯인가뿐이고**, 그래서 슬롯 문법을
`hwpx_fields.iter_slot_matches` 하나로 뽑아 문단 경로와 공유한다.

- **본문 문단은 재지 않는다.** 넘치면 다음 줄로 흐를 뿐 레이아웃이 깨지지 않는다.
  깨지는 것은 폭이 고정된 표 셀이다.
- **중첩 표까지 훑는다.** 부모 셀 폭에 갇혀 오히려 더 좁다 — 빼면 가장 넘치기 쉬운 자리를
  놓친다.
- **절대 막지 않는다.** 추정에는 불확실 구간이 있고, 값이 길다는 이유로 거절하면 "긴 제목을
  못 쓰는 기능" 이 된다. `X-Overflow-Fields` 로 알리고 판단은 UI·사용자에게 넘긴다.

### 4.4 eval 교차검증 — `hwpx_text_crosscheck`

`hwpx_document_integrity` 와 같은 것을 **다른 파서**(`doc_diff`)로 다시 잰다. 둘이
어긋나면 둘 중 하나가 문서를 잘못 읽고 있다는 뜻이다 — 한 벌만 있을 때는 알 수 없다.
§3.2 의 동반 실패가 이걸 붙인 계기다.

라이브러리가 없으면 `available=False` 를 돌려주고, 스위트에서는 `not_measured` 로 남는다.
**미측정을 통과로 위장하지 않는다** — eval 의 기존 규율 그대로다.

## 5. 적용하지 않은 것과 그 이유

**추출기 3벌 통합** (006 `hwpx_markdown.py` / 번역·FAQ `hwpx_text.py`) — 보류.

실측으로는 대체 가능하다. `data/파워.hwpx`·`data/FAQ_결과.hwpx` 에서 우리 출력과
`export_markdown` 출력이 **완전히 같았고**, 병합 셀이 든 표에서만 갈렸다(우리는 빈 칸,
라이브러리는 `rowspan` HTML — 둘 다 열 밀림은 없다). 즉 지금 구현이 틀린 게 아니라,
합치면 중첩 표·각주·이미지 fidelity 가 덤으로 따라온다.

미룬 이유는 **파급 대비 리스크**다. 이건 번역·FAQ 의 운영 입력 경로를 건드리는
리팩터링이고, 이번에 넣은 검증·측정과 달리 실패해도 조용하다. 루트 `CLAUDE.md` 의
"hwpx 전용 전처리기" 과제와 같은 건이므로 그 작업과 함께 다루는 편이 맞다.

## 6. 의존성·배포 전제

`python-hwpx>=6.0,<7` 을 `SFR-006_template_fill/requirements.txt` 와
`eval/requirements.txt` 에 넣었다.

- **순수 파이썬이고 의존성은 `lxml` 하나**다(이미 쓴다). 사용자 Dockerfile 도, 기본 이미지
  변경 절차(11.5.6)도 필요 없다 — `pip install -r` 로 끝난다.
- **폐쇄망에는 사내 registry 에 이 wheel 이 있어야 한다.** 없으면 게이트와 넘침 측정이
  스스로 꺼지고(`event=open_safety_unavailable` / `overflow_unavailable`) 나머지는 그대로
  돈다. 즉 배포가 깨지지는 않지만, **그 환경에서는 산출물이 검증 없이 나간다.**
- major 를 고정한 이유: 6.0 에서 파사드 표면이 크게 움직였고(루트 멤버 102 → 34), 7.0 에서
  호환 shim 이 제거될 예정이다. 우리는 `hwpx.__all__` 의 stable 표면만 쓴다.
- 라이브러리 자체는 Alpha 다. 게이트는 `TEMPLATE_FILL_VERIFY_OUTPUT=0` 으로 끌 수 있다 —
  검사기가 정상 문서를 오판해 운영이 막힐 때의 탈출구이고, 그 외에는 끄지 않는다.

## 7. 검증

```
python onprem/test/check_output_safety.py   # 12건 — 파트 선언·누름틀 안내문·개봉 게이트·넘침
```

뒤 7건은 `python-hwpx` 가 있어야 돈다. 없으면 SKIP 으로 표시하고 종료 코드 0 이다 —
라이브러리 없는 환경이 정상 상태이기 때문이다. 나머지 점검 명령은 루트 `CLAUDE.md` 참고.

점검 픽스처에서 지킬 것 둘:

- **Command 파라미터를 Direction 보다 먼저 둔다.** 순서를 뒤집으면 옛 구현도 통과해
  검사가 무의미해진다.
- **최소 픽스처로 게이트를 재지 않는다.** 파트 두 개짜리 합성 hwpx 는 온전한 OPC 패키지가
  아니라 게이트가 정당하게 거절한다(실제로 거절했다). 게이트 검사는 온전한 패키지로 한다.

적용 시점 실측 결과: 파트 선언 복원 후 advisory 오류 0건, 누름틀이 `filled=False` 로
바뀌어 질문 목록에 정상 진입, mimetype 손상 문서 차단 확인, 긴 값에 `lines=2 ratio=1.51`
경고 + 문서는 정상 생성. 기존 점검 `check_body_blocks`(17) ·`check_chat_turn`(23) ·
`check_tone_policy`(10) 무변화.

`check_deploy_contract.py` 에는 import 이름 ↔ 배포 이름 별칭(`hwpx` → `python-hwpx`)을
추가했다. 그게 없으면 requirements 에 적어 두고도 "선언 누락" 으로 잡힌다.

## 8. 남은 확인

- **누름틀이 든 실물 한컴 템플릿이 없다.** §3.2 의 파라미터 순서는 라이브러리가 재현한
  한컴 계약으로 확인했고, 한/글이 직접 저장한 파일로는 아직 대조하지 못했다.
- **폐쇄망 registry 의 `python-hwpx` wheel 가용성** — §6. 배포 전에 확인해야 게이트가
  실제로 켜진다.
- **advisory 목록은 라이브러리가 정한다.** 지금은 그 분류를 그대로 신뢰한다. 실한컴에서
  안 열리는 문서가 advisory 로 통과하는 사례가 나오면 그때 우리 쪽 판정을 얹는다.
- **넘침 측정은 항목별로 잰다.** 한 셀에 슬롯이 둘 이상이면(`{'소속'} {'성명'}`) 합친
  길이로 재야 맞다. 그런 템플릿 실물이 나오면 합산 경고를 따로 붙인다.
- 추출기 통합(§5)은 "hwpx 전용 전처리기" 과제와 묶어 다룬다.
