## 0. 먼저 — 질문 둘에 대한 답

### Q1. "코드서빙을 여러 개 만들어 기능을 각각 넣는 거 맞나?" → **맞다. 정확히 4개다.**

**코드 서빙 하나 = 컨테이너 하나 = URL 하나**다. 리비전·환경변수·복제본·시작 커맨드가
전부 서빙 단위로 붙으므로 기능마다 따로 등록한다. 예를 들어 22번에 번역, 23번에
글다듬이 — 그 방식이 맞다.

| # | 기능 | 저장소 경로 | 이 서빙 ID 를 꽂는 곳 |
|---|---|---|---|
| 1 | HWPX 템플릿 채우기 (006) | **`not/SFR-006_template_fill/`** | 워크플로우 `TEMPLATE_FILL_SERVING_ID` |
| 2 | 글다듬이 | **`not/SFR-018_text_polish/`** | 워크플로우 `TEXT_POLISH_SERVING_ID` |
| 3 | 번역 | **`not/SFR-018_translation/`** | 워크플로우 `TRANSLATION_SERVING_ID` |
| 4 | FAQ 생성 | **`not/SFR-018_faq/`** | 워크플로우 `FAQ_SERVING_ID` |

> ⭐ **2026-09-14: 두 판본의 기능 차이가 0 이 됐다.** 스트리밍 셋(글다듬이·FAQ·번역)이
> 차례로 정본에 올라가면서, `not/` 과 `onprem/codeserving/` 이 갈리는 것은 **전송 계층
> 12개뿐**이다 — 네 단위 × (`llm.py`·`config.py`·`requirements.txt`).
> 그물은 `not/check_not_units.py`(**92건**), 근거는 [`not/README.md`](not/README.md).
>
> **그래서 고르는 기준은 하나다 — 사내 mirror 에 `openai` 패키지가 있는가.**
> 있으면 `not/`, 없으면 `onprem/codeserving/` 을 올린다(없는데 `not/` 을 올리면
> `pip install -r` 이 그 자리에서 선다). 위 표의 경로는 `openai` 판 기준이고,
> `httpx` 판은 `onprem/codeserving/<같은 이름>/` 이다.
>
> **프롬프트는 이제 두 판본이 같다** — `not/prompt/` 든 `onprem/prompt/` 든 내용이
> 동일하다. **MCP 넷·전처리기 2벌·워크플로우 스텝 9개도 `onprem/` 그대로다** —
> 그쪽은 표준 라이브러리만 쓰므로 판본이 갈리지 않는다.
>
> 📁 **기능별로 갈라 놓은 읽기용 배치가 [`final/`](final/) 에 있다** —
> `final/<기능>/request`(httpx 판 전체) + `open_ai`(갈리는 3개) + `prompt`.
> `python make_final.py` 가 만들고, 덮어쓰면 `not/` 이 되는지까지 매번 검증한다.

**합칠 수 없는 이유는 취향이 아니라 배선이다.** 워크플로우 스텝이 기능마다 **다른
`*_SERVING_ID`** 로 다른 URL 을 부른다. 넷을 한 서빙에 넣으면 그 네 변수가 같은 값을

없다. 리소스도 같이 묶여, FAQ 가 긴 문서를 돌 때 번역 응답이 함께 느려진다.

**단, 저장소는 1개다.** 네 서빙이 같은 저장소·같은 커밋을 가리켜도 되고 디렉토리 구분은

> (MCP 는 2026-09-07 에 `genon_pii_audit.py` 가 붙어 4 → 5 가 됐다가, 같은 날

### Q2. "글다듬이 톤·문서유형 프롬프트가 사라진 것 같다" → **사라지지 않았다. `.j2` 가 아닐 뿐이다.**

값은 **`onprem/codeserving/SFR-018_text_polish/text_polish/tone_presets.py`** 에 그대로
있다. 오늘 확인했다:

```
python onprem/test/check_tone_policy.py     → OK 20 / 20
```

`system.j2` 에 톤 문구가 없는 것은 **설계**다. 그 파일은 `{{ tone_label }}`·
`{{ tone_instruction }}`·`{{ doc_type_label }}`·`{{ doc_type_instruction }}` 을 **받아서
끼우는 골격**이고, 목록을 프롬프트에 베껴 두면 톤이 바뀔 때 프롬프트만 옛 목록을 들고
있게 된다(그 어긋남은 오류가 아니라 결과물의 문체로만 드러난다).

**지금 들어 있는 값 — 톤 4종**

| code | label | 지시문 요지 |
|---|---|---|
| `polite` | 격식·정중 | 격식 있는 존댓말, 명령형·반말을 정중한 문어체로 |
| `friendly` | 친절·안내 | 부드러운 존댓말, 한자어·관공서식 표현을 쉬운 말로 |
| `clear` | 명확·간결 | 한 문장에 한 가지, 군더더기 제거(존댓말은 유지) |
| `objective` | 사실·객관 | 주관적 평가·추측·과장 제거, 근거 있는 서술만 |

옛 코드 `report` 는 `LEGACY_TONE_ALIASES` 가 `clear` 로 받는다 — 캔버스에 옛 값이 남아
있어도 조용히 기본 톤으로 떨어지지 않는다.

**문서유형 5종**

| code | label | 톤 |
|---|---|---|
| `email` | 메일 | 자유 선택 |
| `post` | 게시글 | 자유 선택 |
| `customer_notice` | 고객발송문구 | 자유 선택 |
| `debt_reason` | 채무 및 연체발생 사유 | **`objective` 고정** |
| `reviewer_opinion` | 심사역 의견 | **`objective` 고정** |

**같은 표가 MCP `onprem/mcp/genon_lang_policy.py` 에도 한 벌 있다**(강제 톤 판정은 MCP 가
한다). 둘이 갈리면 화면에서 고른 톤이 워크플로우에서 무시되므로 `check_tone_policy` 가
대조한다 — **한쪽만 고치지 말 것.**

#### 그래서 "프롬프트 라이브러리로 뺀다" 는 무슨 뜻인가 — **문장만 덮는다**

**2026-09-07 에 방식이 바뀌었다.** 그전 계획은 프롬프트 한 건의 본문에 JSON 을 담는
것이었는데, "프롬프트는 전부 라이브러리에서 당겨 쓰되 **코드서빙 안에서 JSON 을
해석하지 않는다**" 로 요구가 확정돼 걷어냈다. 지금은 **이름=ID 매칭** 하나다:

```
POLISH_PROMPT_IDS=system=43,system_polite=51,system_objective=54,doc_type_debt_reason=62
```

| 이름 | 본문 | 덮는 것 |
|---|---|---|
| `system` | 시스템 프롬프트 골격 | `system.j2` |
| `system_<톤코드>` | 그 톤 전용 시스템 프롬프트 | 있으면 골격 대신 쓴다 |
| `doc_type_<문서유형코드>` | 문서유형 추가 지시문 | 내장 표의 `extra_instruction` |

- **본문은 문장 그대로다** — JSON 이 아니다. 톤 코드·문서유형 코드는 위 두 표의 `code` 다.
- **안 적은 이름은 안 덮인다.** 톤 넷 중 하나만 등록해도 나머지는 `system.j2` + 내장
  지시문으로 돈다 — **미설정은 오류가 아니라 정상 경로다.**
- **지시문을 덮어도 라벨·강제 톤은 표 값이다.** 안 그러면 `debt_reason` 의 문구를 고친
  순간 사실·객관 고정이 풀리는데, 그건 오류가 아니라 결과물의 문체로만 드러난다.
- **MCP 쪽에 넣을 것이 없다** — `genon_lang_policy` 는 admin-api 를 부르지 않는다.
  대신 톤을 늘리거나 강제 톤을 바꿀 때는 **표 2벌을 함께** 고친다.

**못 하게 된 것 둘** (ID 매칭의 대가다 — ID 하나는 본문 하나를 가리킨다):

| 못 하는 것 | 대신 |
|---|---|
| 관리자가 **톤·문서유형을 새로 추가** | 개발자가 `tone_presets.py` 표 2벌 + eval `TONE_RULES` 에 넣는다 |
| 내장 톤 **감추기**(`disabled`) | 없다. 필요해지면 환경변수로 받는다 |

**내장 항목의 문구를 고치는 것**(요구의 본체)은 그대로 됩니다. 등록 절차는 §5-2·§5-3.

> **`.j2` 로 새로 만들 것은 없습니다.** 톤 전용 프롬프트를 쓰겠다면 `system.j2` 를
> 복사해 톤에 맞게 고친 뒤 **라이브러리에 붙여 넣으면** 됩니다(파일로 두려면
> `onprem/prompt/SFR-018_text_polish/system_<톤코드>.j2` 로 두면 그대로 폴백이 됩니다).

## 9. 실물이 있어야만 확인되는 것 — 우선순위 순

`onprem/ONPREM.md` §9 가 정본이다. 여기 요약만 둔다.

1. **LLM 실호출 경로 전체.** `/chat/extract`·`/polish`·`/generate`·`/translate` 의 LLM
   왕복을 **한 번도 본 적이 없다.**
2. **게이트웨이가 MCP JSON-RPC 를 그대로 통과시키는가.** 우리 도구 파일과의 계약은
   확인했지만 게이트웨이 통과는 미확인. 형식이 다르면 각 스텝의 `_mcp_call` 한 곳만 고친다
   (자기완결 규율상 9번 고치는 것이 정상이다).
3. **빌드·시작 커맨드가 셸을 거치는가** (§4-1).
4. **캔버스가 `faq_hwpx_path`·`translate_hwpx_path` 를 채워 주는가** (§6).
5. **워크플로우 스텝 간 `data` 크기 한도.** 문서 본문을 스텝 사이로 넘긴다 — 걸리면
   본문 대신 **핸들(세션 키)** 만 넘기는 형태로 바꿔야 한다.
6. **조각 예산이 실물에 맞는가** — `POLISH_MAX_CHUNK_CHARS`(6,000)가 90초 안에 도는가,
   `POLISH_LLM_CONCURRENCY`(4)가 게이트웨이 상한과 맞는가(429 면 여기부터 내린다).
7. Redis 실연결 · 006 hwpx 를 **한/글에서** · txt 를 **사내 PC 메모장에서** ·
   실제 사내 용어사전 파일 적재(`_MAX_TERM_WORDS=6`·캐시 30만이 실물에 맞는지).
8. **전처리기 조문 위계**를 사내 규정 hwpx 로 — `outline_mode="auto"` 가 실제로 켜지는지.
9. **CDN 업로드가 폐쇄망에서 되는가** — 안 되면 옛 `POST /download` 폴백이 남아 있다.
10. **`<mark>` raw HTML 을 렌더러가 허용하는가.** 막으면 상수 두 곳
    (`glossary_report._OPEN_TAG` · `genon_text_guard._TGMARK_OPEN`)만 고친다.
11. **hwpx 적재 결과가 GenOS 화면에 뜨는가**(페이지 자리를 구역으로 채웠다).
    화면이 페이지가 아니라 **원본 미리보기(PDF 렌더)** 를 요구하는 것이라면 이 값으로는
    해결되지 않는다.

## 12. 참고 — 열지 못한 자료

사내 Notion 페이지(GenOS 플랫폼 문서)는 **비공개라 이 세션에서 열 수 없었다.**
claude.ai 커넥터 설정에서 Notion 을 연결하면 다음부터는 읽을 수 있다.
그래서 **플랫폼 화면의 칸 이름·등록 UI 세부는 이 문서에 반영돼 있지 않다** — §4-1 의
빌드·시작 커맨드 셸 동작(§9-3)처럼 **플랫폼 문서로 교차 확인할 항목**은 그때 한 번 더 본다.
