## 공통·SFR-018

### hwpx 표 — 병합·중첩은 HTML 로 낸다 (2026-08-11)

**마크다운 표에는 병합 문법이 없다.** 그래서 `rowSpan`/`colSpan` 이 빈 칸이 되고 중첩 표는
한 덩어리 텍스트로 뭉개졌다. 재현한 실제 출력:

```
| 구분 | 2025년 실적 |   | 비고 |   ← colSpan 사라짐 → 3열이 빈칸
|   | 상반기 | 하반기 | - |        ← rowSpan 사라짐 → 1열이 빈칸
| 세부 | 소분류<br>값 |   |   |     ← 중첩표가 텍스트로 뭉개짐
```

**수치는 남는데 그 수치가 무엇의 값인지가 사라진다.** 요구사항 §5 의 "표 깨짐" 이 이것이고,
렌더러 버그가 아니라 **형식의 한계**라 마크다운으로는 못 고친다.

- **손실이 있을 때만 HTML.** 병합·중첩이 있으면 `<table><tbody><tr><td rowspan="2">…`,
  없으면 마크다운 그대로. 잃을 게 없는 표까지 바꾸면 토큰만 늘고 읽기 나빠진다.
- **새 형식이 아니다.** 지능형 전처리기가 이미 한 줄 HTML 표를 내고, 번역 스켈레톤
  분해기(`markdown_units`)에 그 경로(`_HTML_TABLE_REGION_RE`·`_split_html_table`)가
  이미 있다. 즉 **이미 지원하는 형식**으로 내는 것이라 하위 경로를 안 건드렸다.
- **적용 범위는 LLM 입력 경로 둘**(2026-09-07 갱신): 번역 `office/hwpx_text.py` ·
  FAQ `faq/hwpx_text.py`. **006 `hwpx_markdown.py` 는 제외** — 그쪽 출력은 채팅 화면
  미리보기용이라 마크다운이 맞다. (셋 중 정본이던 MCP `genon_hwpx_text.py` 는
  2026-09-07 에 지웠다 — 첨부 문서는 전처리기가 읽는다. 남은 둘은 **직접 업로드
  경로**(`POST /translate/hwpx`·`/faq/hwpx`) 전용이라 그대로 있다.)
- **전처리기(area 05)는 2026-08-13 부터 이 규칙에서 갈라져 나갔다** — `final_preprocessor.py` PART 2
  는 병합이 없는 표도 **언제나 HTML** 로 낸다. RAG 검색 결과가 프롬프트로 조립될 때 개행이
  뭉개져 마크다운 표가 통째로 무너지기 때문이다(아래 "실제 검색 결과와 대조" 절). 위 세
  사본은 그 경로를 지나지 않으므로 그대로 둔다.
- **원인은 `tc.iter(hp:p)`** 였다. 셀 텍스트를 뽑을 때 중첩 표 안 문단까지 딸려왔다.
  `_owning_cell` 로 소유 셀을 따져 자기 것만 고른다.
- **덮인 자리에 `<td>` 를 내지 않는다.** 내면 그 행만 열이 하나 늘어난다.

**검증**: 무손실 왕복(항등 번역 시 문자 단위 동일)·태그열 불변·숫자 셀이 번역 단위가
되지 않음·엔티티 왕복을 `Test/SFR-018/tests/test_hwpx_tables.py`(10건)가 지킨다.
`check_table_grid.py` 는 **세 층**이 됐다 — 단순표 4벌, 병합표 3벌, **누락 방지**
4벌 + 전처리기(2026-08-23).

### MCP 를 서빙이 아니라 **파일**로 다시 만들었다 (2026-08-11 정정)

재배치할 때 MCP 를 **코드서빙처럼 만들었다** — 디렉토리마다 FastAPI 앱, `/health`,
`$PORT`, `requirements.txt`, 손으로 구현한 `/mcp` JSON-RPC 라우트. **전부 틀렸다.**

GenOS MCP 등록은 **소스 파일 한 개**를 받아 실행하고 `mcp` 객체를 런타임이 전역으로
주입한다. 도구는 `@mcp.tool()` 로 등록하고 **JSON 문자열**을 돌려주며, 엔벨로프는
런타임이 씌운다. 앱도 포트도 우리 몫이 아니다.

- **디렉토리 4개 → 파일 4개.** `mcp/genon_{text_guard,lang_policy,glossary,hwpx_text}.py`.
- **모든 최상위 심볼에 파일별 접두어**(`TG`/`LP`/`GL`/`HX`). 한 서버에 여러 도구 파일이
  함께 로드될 수 있고, 겹치면 나중 것이 앞엣것을 덮는다 — 그 실패는 "도구가 이상한 값을
  낸다" 로만 드러난다. **도구 함수 이름만 예외**(LLM 에 노출되는 계약이라 못 붙인다).
- **`""` 주입 대비.** GenOS 는 값이 없을 때 `None` 이 아니라 빈 문자열을 준다. 선택
  인자를 `int`/`float` 로만 선언하면 **본문에 닿기 전에 타입 검증에서 죽는다.**
- **`mcp` 미주입 대비 shim** 이 없으면 로컬에서 파일을 열어 볼 수조차 없다.
- **`requirements.txt` 가 없으므로** 비표준 패키지는 파일 안에서 설치한다
  (`genon_hwpx_text.py` 의 `lxml` 하나).
- **기동 훅이 없다.** 용어사전 적재는 첫 도구 호출로 미뤘다 — import 가 느리면 서빙이
  왜 안 뜨는지 드러나지 않지만, 첫 호출로 미루면 그 지연이 그 호출의 지연으로 보인다.

**합치면서 밟은 함정 셋** (같은 작업을 다시 할 사람이 같은 자리에서 또 헛걸음하지 않게):

1. **정규식으로 이름을 바꾸면 문자열 리터럴까지 바뀐다.** `resolve_tone` 이 함수 이름이자
   도구 이름 문자열이라 `_HANDLERS` 의 키가 바뀌었고, 그 도구가 통째로 `UNKNOWN_TOOL`
   이 됐다. → 토큰 단위로 바꾸고 문자열은 건드리지 않는다.
2. **별칭 import 를 놓치면 호출부만 옛 이름으로 남는다.**
   `from .languages import supported_payload as supported_languages` — 정의부는 접두어가
   붙는데 호출부는 그대로라 `NameError`. **import 는 통과하므로 도구를 실제로 불러야**
   드러난다.
3. **다른 파일이 같은 이름을 정의하면 뒤엣것이 앞엣것을 덮는다.** `languages.py` 와
   `registers.py` 가 둘 다 `supported_payload` 를 가져서, 합친 뒤 `list_languages` 가
   **문체 목록**을 돌려줬다.

**그물**: `check_mcp_tools.py`(36건)가 네 파일을 **한 네임스페이스에 넣어** 덮이는지
보고, 도구를 직접 불러 결정적 판정과 빈 문자열 주입을 확인한다.
`check_deploy_contract.check_mcp_files()` 가 접두어·`async … -> str`·shim·상대 import
금지·부팅 설치 절차를 정적으로 본다. 상세는 `final/mcp/README.md`.

**덤으로 찾은 기존 버그 하나**: `resolve_register` 가 `getattr(code, "code", str(code))`
로 값을 꺼냈는데 `Register` 의 필드는 `key` 다. 항상 `str(code)` 로 떨어져 **파이썬 repr
이 응답에 통째로 실렸고**(영문 지시문 포함), `fell_back`(기본값으로 떨어졌다는 사실)은
계산해 놓고 버렸다. 둘 다 고쳤다 — 후자가 없으면 사용자가 고른 문체가 조용히 무시된다.

### 선택지는 **도구 스키마로 강제한다** (2026-08-18)

MCP 도구 인자가 전부 맨 `str` 이었다. 언어·문체·문서유형·톤은 **백엔드가 표를 갖고
있는 값**인데, 노출되는 스키마에는 "문자열" 이라고만 적혀서 **선택지가 계약 어디에도
없었다.** 그러면 호출부(캔버스 화면·워크플로우 변수·도구를 고르는 LLM)가 자기 목록을
들고 있게 되고, 언어가 늘거나 빠질 때 한쪽만 고친다 — 예외는 나지 않고 빈 드롭다운이나
"지원하지 않는 언어입니다" 로만 드러나 **사용자에게는 백엔드가 막은 것처럼 보인다.**

표(`LPSUPPORTED_LANGUAGES`·`LPREGISTERS`·`LPDOC_TYPE_POLICIES`·`LPTONE_PRESETS`·
`_GLLANGUAGE_CODES`)에서 `enum` 을 **만들어서** 얹는다. `Literal[...]` 이 아니다 —
그러면 별칭(`"한국어"`·`"korean"`·`"문어체"`)이 타입 검증에서 죽고, `allowed=false`·
`tone_overridden`·`fell_back` 처럼 **"고른 값이 조용히 무시되지 않게" 하려고 만든 판정**이
전송 실패와 구분되지 않는 형태로 바뀐다. **스키마에는 선택지를 싣되 판정은 본문이 한다.**
근거와 적용 자리 표는 `final/mcp/README.md` §4-1.

- **`pydantic` 은 감싼 선택 의존이다.** FastMCP 가 스키마를 만들 때 이미 쓰는 패키지라
  따로 설치할 것이 아니고, 없으면 맨 `str` 로 떨어져 그냥 돈다.
  `check_deploy_contract._mcp_guarded_imports` 가 **다시 던지지 않는** try/except 만
  선택 의존으로 친다 — `except ImportError: raise` 는 감싸지 않은 것과 결과가 같다.
- **`genon_glossary` 는 정규화가 아예 없었다.** `target_lang` 이 색인의 키로 그대로
  쓰여서 `"KO"`·`"한국어"`·`"ko-KR"` 이 `language_missing` 으로 떨어졌다 — **용어사전만
  조용히 빠진 번역**이 나가고, 대조할 용어가 없으니 준수율은 늘 1.0 이라 정상으로 보인다.
  언어 표를 `genon_lang_policy` 와 같은 내용으로 두고(사본 대조 대상) `glnormalize_lang`
  을 두 핸들러 입구에 걸었다.
- **그물**: `check_mcp_tools.py` 46 → **60건**. 스키마를 **시그니처에서 실제로 만들어**
  표와 대조하고(손으로 적은 기대값이 아니다), 사전을 하나 적재해 놓고 표기 5종으로
  조회한다 — 미적재 상태에서는 어떤 표기든 똑같이 `enabled=false` 라 **정규화를
  되돌려도 통과**하기 때문이다. 셋 다 되돌려 FAIL 이 나는 것을 보고 넣었다.

### 원문 언어 — 감지는 폴백이 아니라 **교차검증**이다 (2026-08-18)

위 절(선택지 강제)에서 나온 질문이다: **"프론트가 정해진 언어만 보내게 강제하면
`lpdetect` 같은 감지는 없어야 하는 것 아닌가."** 아니다 — **enum 이 강제하는 것은
"어떤 값이 칸에 들어올 수 있는가" 이고, 감지가 답하는 것은 "업로드한 문서가 무슨
언어인가" 다.** 후자는 드롭다운이 아니다.

`archive/data/translation_rule.md` §2 가 사용자에게 고르게 하는 것은 **대상 언어와 문체**다.
그런데 §6 은 "한국어가 아닌 쌍(`en→ru`)은 고려 X" 를 요구한다 — 이 축을 집행하려면
원문 언어를 알아야 하는데 **선택으로 들어오지 않는다.** 그래서 감지가 §6 의 유일한
집행 수단이다.

**그런데 그 감지가 정작 필요한 자리에서 꺼져 있었다.** `source_lang` 이 오면
`resolve_direction` 이 감지를 **건너뛰었다**(주석에도 "감지는 폴백이다" 라고 적혀
있었다). 화면에 원문 드롭다운이 있으므로:

> "한국어 → 러시아어" 를 고르고 **영어 문서**를 올린다 → 실제 방향은 `en→ru` →
> §6 이 막으려던 바로 그 쌍인데 **선언을 믿어 그대로 통과**했다.

이제 **항상 감지하고 선언과 대조한다.** 다만 **정본은 선언값이다** — 감지가 사용자의
선택을 조용히 덮으면 이 코드가 없애려는 바로 그 실패 형태가 된다(`fell_back`·
`tone_overridden` 과 같은 취지). 감지는 **거부의 근거로만**, 그것도 §6 이 실제로 깨질
때만 쓴다.

- **거부 판정을 최빈값으로 하면 안 된다 — 실제로 밟았다.**
  `본 사업 KPI 는 ROI, TCO, SLA, API, SDK 로 관리한다` 는 라틴 문자가 **62%** 라
  최빈값으로는 영어이고, 문턱을 60% 로 뒀더니 이 **멀쩡한 한국어 문장이 거부됐다.**
  사용자에게는 우회할 방법이 없는 오차단이다. 그래서 판정 근거를 **"선언한 언어의
  문자가 문서에 사실상 없는가"**(`declared_share < 10%`)로 바꿨다 — 영어 문서에 한글은
  0% 이고, 영문 용어가 많은 한국어 문서도 한글은 20% 밑으로 잘 안 내려간다.
- **통과하는 충돌은 막지 않고 보고한다.** 대상이 한국어면(`th`선언 + 한국어 문서 →
  `ko`) 어느 쪽으로 읽어도 §6 을 어기지 않으므로 진행하고, `source_mismatch` 로 알린다.
- **사본이 2벌이다** — MCP `genon_lang_policy.py`(워크플로우 경로)와 번역 코드서빙
  `office/languages.py`(직접 업로드 `POST /translate/*` 경로). **직접 업로드는 MCP 를
  지나지 않으므로** 한쪽만 고치면 그 경로에 뒷문이 남는다. 둘을 같은 코드로 두고
  점검도 각각 태운다.
- `resolve_direction` 이 `(source, target)` 튜플 대신 **`DirectionVerdict`** 를 돌려준다.
  "원문 언어를 어디서 얻었나"(선언인가 감지인가·어긋나지는 않았나)가 튜플로는 경계를
  넘지 못한다. 호출부 넷(`_LPvalidate_direction`·`pipeline._resolve_options`·테스트 2곳)이
  같이 바뀌었다 — 반환형을 바꾸면 **언패킹이 즉시 터지므로** 조용히 새는 곳이 없다.
- **그물 셋.** `check_mcp_tools`(60→**66**), `check_unit_endpoints`(61→**64**),
  `check_workflow_run`(72→**74**), SFR-018 unittest(146→**152**). 셋 다 되돌려 FAIL 을
  확인했고, **코드서빙 사본만 되돌리면 `check_unit_endpoints` 만 FAIL** 하는 것으로
  두 벌이 따로 검사되는지도 봤다.

### `evidence_check` 를 MCP 에서 걷어냈다 (2026-08-18)

**아무도 안 쓰는데 갈릴 수 있는 사본**이었다. 도구는 등록돼 있었지만 운영 호출부가
**0건**이고(FAQ 스텝은 `hwpx_to_markdown` 만 부른다), 근거 대조는 FAQ 코드서빙이 자기
안에서 한다(`faq/evidence.py`). MCP 쪽 판정부는 그 파일과 **줄 단위로 같은 사본**이었고
(`_NGRAM = 3`, 같은 정규식 3개, 같은 `check()`), **사본 대조 점검도 없었다** — 표 격자는
`check_table_grid`, 톤은 `check_tone_policy` 가 보는데 이것만 아무도 안 봤다.

근거 규칙(n-gram 크기·min_ratio)을 고치면 MCP 쪽만 옛 판정을 계속 내고, 그걸 부른 LLM 은
서빙과 **다른 답**을 받는다 — 오류로는 드러나지 않는다. 141줄이 빠졌다(713 → 572).

- **지우면서 커버리지가 사라질 뻔했다.** `check_mcp_tools` 의 근거 대조 4건이 그 규칙을
  태우는 **유일한** 점검이었는데, 그마저 **사본을 태우고 있었다** — 운영이 쓰는
  `faq/evidence.py` 는 한 번도 검증된 적이 없었다. 도구와 함께 그냥 지웠으면 근거 대조를

### 변경·용어 표시는 **답변 아래 목록이 아니라 본문 위 하이라이트**다 (2026-08-27)

두 기능의 표시가 같은 이유로 사용자에게 닿지 않고 있었다 — **값은 다 만들어 놓고 화면에
쓰지 않았다.** 둘 다 예외를 내지 않고, 응답에는 필드가 들어 있으니 로그로도 드러나지 않는다.

| 기능 | 그전 | 지금 |
|---|---|---|
| 글다듬이 | 본문 뒤에 `---` + "주요 변경 내역" + `` `개발함` → `개발하였습니다` `` **목록** | 바뀐 **낱말**에 `<mark>`. 목록은 없앴다 |
| 번역 | `markdown_highlighted` 를 payload 에만 싣고 `text` 로는 **정본**을 흘렸다 | `text` 가 사본을 담는다 |

**번역 쪽이 더 조용했다.** 사본을 만드는 코드도, 좌표를 내는 코드도, 겹침을 병합하는
코드도 다 있었다. 그런데 스텝이 `display_text = notice + translated` 였다 — payload 를
읽는 별도 UI 가 없으면 **용어사전 하이라이트가 캔버스 채팅에 한 번도 나타나지 않았다.**
`translation_rule.md` §2 가 요구하는 표시가 통째로 빠진 상태이고, 그 사실이 어디에도
드러나지 않는다(값은 정상이므로). **사본을 만드는 것과 화면에 쓰는 것은 다른 일이다.**

#### 좌표가 없으면 인라인 하이라이트는 성립하지 않는다

`diff_changes` 가 내던 것은 `{before, after}` 문장 쌍뿐이었다. 그 형태로는 프론트가
`after` 문자열을 본문에서 **다시 찾아야** 하고, 같은 낱말이 두 번 나오면 어느 쪽을 칠할지
결정할 수 없다. 원인은 한 줄이다 — 문장으로 쪼갠 뒤 `strip()` 을 걸어 **위치가 복원
불가**였다. 그래서 `_TGsplit_units_with_spans` 로 갈아 `(텍스트, start, end)` 를 낸다
(`re.split` 은 위치를 버리므로 `finditer` 로 자른다).

- **문장이 아니라 낱말 단위**다. 문장 쌍은 "이 문장이 바뀌었다" 까지만 말하고, 그대로
  칠하면 문장 전체가 형광이 되어 **어느 낱말을 손질했는지가 오히려 묻힌다.** 바뀐 단위
  쌍을 낱말로 한 번 더 갈라(`_TGword_changes`) 그 안에서 달라진 낱말만 뽑는다.
- **삭제만 일어난 자리는 `span=None`** 이다. 되쓴 글에 칠할 글자가 없다 — 0 을 넣으면
  문서 맨 앞이 칠해진다.
- **좌표와 표시를 한 함수에 두지 않는다.** `changes[].span` 을 payload 로 그대로 내보내고
  (프론트가 자기 방식으로 칠할 수 있어야 한다), `<mark>` 사본은 따로 만든다.
- **건수 상한을 두지 않는다 (2026-08-28 변경).** 처음에는 `max_items`(기본 50) 로 앞쪽만
  내고 걸린 사실을 `truncated` 로 알렸는데, **잘린 목록으로 `highlighted` 를 만들기
  때문에 그 상한이 곧 하이라이트 상한**이었다 — 51번째 변경부터는 `<mark>` 가 아예
  붙지 않는다. 안내문("앞쪽 N건만 표시")을 띄워도 정작 봐야 할 자리를 못 찾는 것은
  그대로라, 변경을 보여준다는 도구의 목적과 상한이 충돌했다. 크기의 실제 상한은
  **입력 길이**(`_TGMAX_TEXT_CHARS`)가 잡고, 그쪽은 넘으면 자르지 않고 요청을 세운다.
  `truncated` 필드도 함께 지웠다 — 언제나 false 인 필드는 읽는 쪽이 "확인했다" 고
  믿게 만든다. **번역 쪽 용어사전 하이라이트에는 원래 건수 상한이 없다.**

#### 태그는 `<mark>` 로 통일했다 — `<strong>` 은 원문 강조와 구분되지 않는다

번역은 `<strong>` 을 쓰고 있었다. 근거가 "`**` 는 원문에도 있으니 태그로 쓴다" 였는데
**`<strong>` 도 원문에 나오는 표기다**(전처리기가 HTML 을 낸다). 굵게 보여도 그것이
사전 용어인지 원문 강조인지 화면에서 가릴 수 없고, **가리는 것이 요구사항 §2 의 요점**
이므로 그 상태는 표시가 있으나 마나다. `<mark>` 는 본문에 쓰이지 않고 기본 렌더가
형광이다. 태그는 상수 두 개(`glossary_report._OPEN_TAG`·`genon_text_guard._TGMARK_OPEN`)
에만 있어 렌더러가 raw HTML 을 막으면 그 둘만 고친다 — **그 허용 여부는 미확인이다.**

#### 정본은 손대지 않는다 (기존 규약을 그대로 따랐다)

`POST /download` 가 정본을 그대로 파일로 만들므로 태그가 섞이면 사용자가 메모장에서
지워야 한다. 파일 단계에서 **지우는** 방식은 원문에 원래 있던 태그까지 지운다. 그래서
번역이 이미 갖고 있던 "정본 + 표시용 사본" 두 갈래를 글다듬이에도 그대로 뒀다.


#### 칠하면 손상이 되는 두 구간

- **코드펜스 안** — `<mark>` 가 화면에 글자 그대로 나온다.
- **HTML 태그** — `<td rowspan="2">` 가운데를 가르면 표가 통째로 깨진다.

그런데 **피하는 것만으로는 반대 결함이 생겼다.** 낱말을 공백으로만 끊으면 전처리기가 낸
한 줄 HTML 표가 **통째로 낱말 하나**가 되고, 그 구간은 태그에 걸치므로 버려진다 —
**HTML 표 안 변경은 영영 칠하지 못한다.** 그래서 낱말을 끊을 때 HTML 태그를 따로
끊는다(`_TGWORD_RE`). 구현 중 실제로 밟았고, 되돌려 FAIL 을 확인한 갈래 중 하나다.

### 한국어 조사 때문에 **프롬프트·지표·표시가 함께 틀리고 있었다** (2026-08-28)

토큰이 `[가-힣]+` 라 `가맹점을` 이 한 덩어리다. 사전의 `가맹점` 과 매칭되지 않았고,
그 실패가 **방향마다 다른 얼굴**로 나타났다:

| 방향 | 어디서 깨지나 | 증상 |
|---|---|---|
| ko→en | `match_occurrences` 0건 | **그 용어가 프롬프트에 실리지 않는다** — LLM 은 "가맹점 → merchant" 를 들은 적이 없다. 준수율은 `matched_count=0` 이라 **1.0** |
| en→ko | `contains_phrase` False | `신용회복위원회를` 로 제대로 옮겼는데 **준수율 0.0** 이고 양쪽 하이라이트가 안 붙는다 |

**두 증상이 반대 방향(1.0 / 0.0)이라 지표만 보면 서로를 가린다.** 표시 문제가 아니라
프롬프트·지표·표시가 함께 틀리는 문제였다.

- **형태소 분석기는 필요 없다.** 이 파일의 옛 서술("조사 분리는 모듈 책임 범위 밖")이
  전제한 만큼이 아니다 — 사전 용어는 대부분 명사이고 뒤에 붙는 조사는 **닫힌 목록**이라
  영어 `_EN_SUFFIX_RULES` 와 같은 구조로 끝난다.
- **색인이 아니라 조회할 때 뗀다.** 색인 키에 절단을 걸면 사전 표제어가 함께 깎여
  `신용도` 가 `신용` 으로 굳고 **원래 용어가 사라진다.** 문서 쪽 토큰만, 그것도 **정확
  일치를 먼저 찾아보고 없을 때만** 뗀다 — 사전에 `신용도`·`신용` 이 둘 다 있으면
  앞엣것이 이긴다.
- **한 곳을 고치면 셋이 같이 풀린다.** `match_occurrences`(매칭·프롬프트 선정·원문 좌표)
  ·`contains_phrase`(준수율)·`phrase_positions`(번역문 좌표)가 **같은 토큰화·정규화**를
  공유한다. 뒤의 둘은 규칙이 갈리면 "썼다는데 위치는 못 찾는" 상태가 되므로 함께 고쳤다.
- **칠하는 구간은 문서에 실제로 적힌 글자다** — `<mark>신용회복위원회를</mark>` 처럼
  조사까지 덮는다. `invoice` 가 `invoices` 를 덮는 기존 규약과 같다.
- **남는 한계**: 3자 이상이면서 조사 글자로 끝나는 표제어(`신용도`)가 사전에 없고
  절단형만 있으면 그쪽으로 걸린다. 과절단은 **떼고 2자 이상** 가드가 막는다(`추가`→`추`).
- **사본 2벌** — 번역 `glossary_exact.py` · MCP `genon_glossary.py`. 한쪽만 고치면
  워크플로우 경로와 직접 업로드 경로가 **다른 용어 목록**을 쓴다.
- **그물**: `check_mcp_tools` 76→**80**(조사 폴백 3갈래 + 과절단 가드),
  `test_glossary_policy` +6(방향별 증상·과절단·정확 일치 우선·여러 낱말 용어).

### 가드레일이 **검증되지 않은 채** 있었다 — eval (2026-08-30)

`Test/eval` 은 네 기능의 합불을 정하는 코드인데 **회귀 점검이 0건**이었다
(README 가 "세션 임시 디렉토리에서 스모크로 확인했다" 고 적어 뒀다 — 저장소에 남지
않는 기록이다). 여기가 조용히 틀리면 **틀린 기준으로 합격 도장을 찍는다.**

`check_eval_metrics.py`(68건)를 붙이면서 결함 일곱을 찾았다. 전부 예외를 던지지 않고,
리포트는 정상으로 보인다.

| 결함 | 어떻게 보였나 |
|---|---|
| **환각률이 미측정인데 0.0** | 화이트리스트(템플릿 스키마)를 안 주면 `rate: 0.0` → 기준 `< 0.05` 를 **한 번도 재지 않고 늘 통과** |
| **빈 비교로 만점** | `pairs` 키를 `source/target` 으로 주면 `structure_pass_rate` 가 `""` 와 `""` 를 비교해 **1.0** (다섯 집계기가 각자 다른 별칭을 읽고 있었다) |
| **평범한 낱말을 조사 오류로** | `평가`·`증가`·`국가`·`가을`·`사과` 를 전부 오류로 냈다 → 그런 낱말이 든 문서는 **톤 불합격** |
| **슬롯 잔여 표기를 값으로** | 안 채운 `{'제목', 16pt}` 를 `filled` 로 세어, 부분 초안에서 `agreement_rate`·`guide_state_kept` 가 **정확히 반대**로 나왔다 |
| **자카드가 문서 길이에 반비례** | 같은 답변이 짧은 원천 1.0 → 200문장 원천 0.2. 길이에 따라 값이 달라지면 **임계를 걸 수 없다** |
| **한 문장짜리 문서는 늘 어미 불일치** | 뒤 절반이 비어 우세 유형이 `other` → 짧은 문서만 모으면 이 지표가 0 이 된다 |
| **`tone_pass_rate` 가 카탈로그에 없었다** | "표에 없는 도구는 운영 지표가 아니다" 가 규약인데 그 도구가 운영 합불 기준이었다 |

**공통점은 방향이다 — 대부분 "재지 않고 통과" 쪽으로 틀렸다.** 가드레일에서 이 방향의
오류가 제일 나쁘다(불합격 쪽으로 틀리면 사람이 바로 알아챈다).

- **입력 쌍의 키 해석을 `pairs.py` 한 곳으로 모았다.** 원문이 없으면 **예외**이고
  (빈 비교로 만점을 주지 않는다), 결과가 없으면 **불합격**이다(측정 불가가 아니다 —
  다듬기·번역이 아무것도 못 내놓은 것은 실제 실패다).
- **조사 검사는 앞말이 명사임을 아는 자리에서만 한다.** 받침 판정 자체는 정확하지만
  **무엇이 조사인지**를 형태소 없이 알 수 없다. `으로/로` 만 보는 절충도 안 된다
  (`진로`·`선로`·`항로`). `nouns`(사내 용어사전 표제어)를 준 자리에서만 재고, 검사
  여부를 `particle_check.scope` 로 낸다 — **미검사를 통과로 보이게 하지 않는다.**
- **집계는 항목 하나 때문에 죽지 않는다.** 원천 없는 FAQ 항목·빈 결과물이 예외를 내면
  나머지 99건의 채점이 통째로 사라진다. 단건 도구는 엄격하게 두고(쓰레기가 들어오면
  오류) **집계가 감싸서** `unmeasurable` 로 드러낸다.
- **`chrF` 가 O(n²)** 였다(`list.remove` 반복). 3천자/5천자 한 쌍에 0.5초 — 문서가 열
  배면 백 배다. `Counter` 다중집합 교집합으로 바꿨다(결과는 같다, 0.010초).
- **점검의 네 번째 층이 제일 값어치 있다**: `SUITES[…]["targets"]` 의 경로가 실제
  산출물에 도달하는지 **완전한 입력을 주고** 본다. 지표 키를 한 번 바꾸면 그 기준은
  **영원히 `not_measured`** 가 되는데, 그 상태는 리포트에서 "아직 안 쟀네" 로만 보인다.

**일곱 갈래를 각각 되돌려 FAIL 을 확인했다.**

### PII 마스킹 누락을 **네 기능 출구에서** 잡는다 — eval (2026-09-02)

민감정보 마스킹(#315)은 적재 전처리기(첨부용 `guardrail`)의 몫인데 **그 층이 없어도
조용하다.** 사이트 설치본에 모듈이 없거나(2026-09-02 에 실제로 그 import 가 없어 pdf
적재가 막혔다) 설정이 꺼져 있으면 적재는 성공하고 검색도 되며, 네 기능이 그 텍스트를
최종 답변에 **원문 그대로** 싣는다. 오류가 없으니 로그에도 안 남는다 — 사용자가 화면에서
주민등록번호를 발견할 때까지 아무도 모른다. `pii_leak_count` 가 그 출구를 본다.

- **비율이 아니라 절대 건수다.** 허용치가 0인 값에 비율 기준을 걸면 200문장 문서의
  1건이 0.5% 라 임계를 통과한다 — **기준이 사고를 승인한다.**
- **네 기능이 같은 지표를 같은 방식으로** 돈다(`suites._run_pii`). 마스킹 누락은 기능
  고유의 실패가 아니라 그 텍스트가 넷을 모두 통과하는 것이라, 기능마다 다르게 재면 안 된다.
  **FAQ 는 이것이 유일한 운영 기준이 됐다**(근거성에는 기준을 두지 않는다).
- **`leak_count == 0` 은 "개인정보 없음" 이 아니다.** `detectors` 에 적힌 유형만 본다 —
  이름·주소·계좌번호는 안 센다(NER 이 없고, 계좌번호는 체크섬이 없어 일반 숫자열과
  구분되지 않는다). 그 공백을 응답에 싣는다. `masked_count` 도 함께 낸다 —
  `leak=0 · masked=0` 은 "개인정보가 없던 문서" 와 "아무것도 안 돌았다" 가 구분되지 않는다.
- **체크섬으로 오탐을 거른다**(주민·사업자·카드). **오탐은 결국 미탐으로 간다** —
  가드레일이 상시 빨간불이면 사람이 임계를 올리거나 지표를 끈다.
- **검출한 값은 응답에 담지 않는다**(3.8절). 자리와 유형만 낸다 — 담으면 평가 리포트가
  유출 경로가 된다.

**같이 고친 것 — `<mark>` 가 채점을 무너뜨리고 있었다.** payload 에 남은 텍스트는
하이라이트 사본이고 정본은 파일로만 있다(2026-08-28). 태그째 채점하면 어미가
`…습니다</mark>` 로 끝나 종결어미 판정이 전부 `other` 로 떨어지고 `ending_consistency`
가 **불합격이 아니라 미측정으로 조용히 빠진다.** `pairs.pair_texts` 한 곳에서 벗긴다
(다섯 집계기가 전부 거기를 지난다). **`<mark>` 만** 벗기고 `<table>` 은 남긴다.

**그물**: `check_eval_metrics` 68 → **80건**. 되돌려 FAIL 을 본 갈래는 셋이다 —
`pair_texts` 의 태그 제거(3건 동시 FAIL) · 체크섬 제거(오탐) · `scan_text` 의 태그
제거(미탐). 완전 입력 픽스처에 `answers` 를 넣지 않으면 **네 기능의 기준 도달 판정이
전부 FAIL** 하는 것도 확인했다(그 층이 이번에도 제일 먼저 잡았다).

### 긴 문서에서 **뒷부분이 통째로 빠지고 있었다** (2026-08-29)

두 단위가 상한을 서로 다른 방식으로 잘못 다루고 있었다. 둘 다 예외를 던지지 않고,
나온 결과도 멀쩡해 보인다 — **없어진 자리에 흔적이 남지 않는** 종류다.

| 단위 | 그전 | 사용자에게 어떻게 보였나 |
|---|---|---|
| FAQ | 24,000자를 넘으면 `source[:상한]` 으로 **자르고** 한 번만 호출 | 뒷부분 내용으로는 **FAQ 가 나올 수 없다.** 기각 건수에도 안 잡힌다 — LLM 이 본 적이 없으니 `ungrounded` 도 `duplicate` 도 아니다 |
| 글다듬이 | 문서 전체를 한 번에 호출 (상한 20만 자) | 상한에 닿기 한참 전에 **`RES_TIMEOUT`(90초)이 먼저** 났다. 재시도 가능으로 분류돼 같은 자리에서 또 걸린다 — "긴 문서는 그냥 안 되는 기능" |

**실질 상한은 업로드 용량이어야 한다** (요구 확정). 그 안쪽 문서는 끝까지 처리한다.

- **FAQ 는 조각마다 자기 몫을 만든다.** 호출 수는 **총량 상한**이 정한다 — 구간당
  5개 · 총량 30개면 조각이 40개여도 6번 부르고, 태울 조각을 **고르게 표집한다**
  (`plan_quota`). 앞에서부터 채우면 잘라 쓰던 시절과 결과가 같아진다.
  - **사용자는 총 개수만 고르고 배분은 우리가 한다 (2026-09-03 요구 확정).** 고른
    숫자가 곧 받는 개수다. 2026-08-31~09-02 에는 선택이 **구간당** 개수였고 총량을
    `FAQ_MAX_TOTAL_COUNT` 가 잡았는데, 그러면 **고른 숫자와 받는 개수가 달라진다**
    (구간이 여섯이면 5를 골라도 30개). 그 규약이 막으려던 것(긴 문서에서 조각당 몫이
    0 에 가까워져 그 구간 내용이 후보에서 빠지는 것)은 이제 **호출 수 상한**
    (`FAQ_MAX_CHUNK_CALLS`, 기본 6)이 막는다 — 태울 구간 수가 묶여 있어 조각이 40개여도
    여섯 구간이 나눠 갖고 몫은 1 밑으로 내려가지 않는다. **개수는 사용자가, 비용은
    배포가** 정한다: 한 손잡이에 묶으면 둘 중 하나를 못 지킨다.
    옛 `FAQ_MAX_TOTAL_COUNT` 는 없앴다(언제나 안 걸리는 상한은 읽는 쪽이 "확인했다" 고
    믿게 만든다). `FAQ_MAX_COUNT` 기본값은 10 → **30** 이다 — 옛 총량 상한과 같은 값이라
    실제로 만들 수 있던 최대치가 유지된다.
  - **상한에 걸려 못 태운 구간은 `coverage_capped` 로 알린다.** `source_truncated`
    (조각 수 상한)와 **다른 사건**이라 갈라 뒀다 — 그쪽은 문서 뒤를 아예 안 본 것이고
    이쪽은 전체를 나눴지만 일부만 태운 것이다. 조용히 건너뛰면 사용자는 문서 전체에서
    뽑은 결과로 읽고, **안 나온 내용이 문서에 없는 것으로 보인다.**
  - **`requested_count` 는 사용자 선택 그대로다** (2026-09-03 되돌림). 조각 수와 무관
    하고 상한으로 깎인 값만 반영한다 — 2026-08-31~09-02 에는 "배정된 몫의 합" 이었고
    그때는 안내문이 "5개 중 28개를 만들었습니다" 가 되지 않게 하려는 보정이었다.
    선택이 총 개수가 된 지금은 그 보정 자체가 필요 없다. `per_chunk_count`·`total_cap`
    필드는 없어지고 **호출 수 상한이 `call_cap`** 으로 나간다.
  - **번역·글다듬이에는 이 배분이 없다** — 그 둘은 개수를 뽑는 것이 아니라 **모든
    유닛·조각을 처리**하므로 나눌 몫 자체가 없다. 같은 방식을 얹을 자리가 아니다.
  - **조각 호출은 2026-09-09 부터 병렬이다** (아래 "FAQ 조각을 병렬로 부른다" 절).
  - **근거 대조는 조각이 아니라 문서 전체로** 한다. 조각 경계가 문장 가운데를 지나면
    그 문장을 든 항목이 오탐 기각된다.
  - **중복 판정도 조각을 가로질러 공유**한다. 같은 주제가 여러 절에 나오면 조각마다
    같은 질문이 나오는데, 조각별로 따로 세면 그게 전부 통과한다.
  - `FAQ_MAX_CONTEXT_CHARS` 의 **뜻이 바뀌었다** — 문서 상한이 아니라 **호출 한 번의
    예산**이다. `source_truncated` 도 뜻이 바뀌었다: 예전에는 "앞부분만 봤다", 지금은
    "조각 수 상한(`FAQ_MAX_CONTEXT_CHUNKS`, 기본 40 ≈ 96만 자)에 걸릴 만큼 길다".
- **번역은 이 배분과 무관하다 — 모든 유닛을 번역한다.** 다만 같은 성격의 **조용한
  절단이 한 자리 남아 있었고 2026-08-31 에 고쳤다**: `POST /translate/hwpx` 만 상한을
  파서에 넘겨(`to_markdown(max_chars=500,000)`) 넘는 만큼을 **버렸다.** 번역 쪽
  `HwpxDocument` 에는 `truncated` 필드가 없어 **응답에도 로그에도 흔적이 없고**,
  사용자는 뒷부분이 빠진 번역문을 받는다. 나머지 세 경로는 초과를 오류로 세우고 있었으니
  **같은 문서를 어느 경로로 넣었는지에 따라 결과가 달랐다.** 이제 넷이 같다.
- **글다듬이를 나눠도 되는 근거는 이 기능이 하는 일이다.** 내용을 다시 쓰는 것이
  아니라 **문체에 맞게 낱말·어미를 손질**한다 — 판단 단위가 문장이라 조각 경계 너머의
  문맥이 필요하지 않다(번역이 유닛 단위로 도는 것과 같은 근거).
  - **꼬리 공백을 코드가 되꽂는다.** LLM 은 응답 끝 공백을 지운다 — 다듬은 조각을 그냥
    이어붙이면 **문단 경계가 사라져** 제목과 본문이 한 줄이 된다. 조각을 (본문, 꼬리)로
    갈라 본문만 보내고 꼬리는 코드가 붙인다. 무손실 왕복이 계약이다.
  - **코드펜스·여러 줄 HTML 표 안에서 끊지 않는다** — 그 둘은 **안에 빈 줄이 올 수
    있어** 경계 규칙만으로는 갈린다. 절반만 보내면 그 조각의 출력이 표·코드로 보이지
    않고, `markdown_structure_issues` 가 잡는 훼손을 **우리가 만들어 내는** 셈이 된다.
    (마크다운 표는 안에 빈 줄이 없어 이미 안전하다. 따로 떼는 것은 앞뒤 문단이 붙어
    덩어리가 커지는 것을 막기 위해서다 — 되돌려 보고 근거를 고쳐 적었다.)
  - **실패한 조각 자리에는 원문이 들어간다.** 빈 문자열로 두면 그 구간이 통째로 사라진
    결과가 정상 응답처럼 나간다. **전량 실패만 오류**이고 부분 실패는 건수로 낸다
    (번역의 전량 폴백 규약과 같다).
  - **설정 부재는 첫 조각에서 끝낸다** — 재시도로 풀리지 않는 배포 문제라 조각 수만큼
    두드릴 이유가 없다.

### 미준수는 **알리고, 다시 할지는 사용자가 정한다** (2026-08-29)

용어사전 미준수(`term_map_unapplied`)는 2026-08-14 부터 응답에 있었지만 **아무도 읽지
않았다.** 화면에 닿지 않으니 사용자는 어떤 용어가 빠졌는지 알 수 없고, 준수율은 검수용
이라 payload 에도 없다. 부분 실패·숫자 드리프트도 2026-08-28 에 "disclaimer 가 확정되면
붙인다" 며 **판정만 하고 아무 데도 내보내지 않는** 상태로 뒀다.

- **자동 재번역을 하지 않는 것이 결정이다** (요구 확정). 미준수 유닛만 골라 한 번 더
  부를 수도 있지만, 사용자가 고르지 않은 LLM 호출을 쓰면서 **결과가 나아진다는 보장이
  없다.** 사실을 말하고 다시 번역할지는 사용자가 정한다.
- **안내문은 건수만 말한다.** 어느 용어·어느 문장인지는 문서 내용이고(3.8절), **자리는
  이미 화면에 있다** — 원문 사본은 매칭된 용어를 전부 칠하므로 오른쪽 짝이 비어 있는
  형광이 곧 "사전 용어인데 번역이 그 말을 안 썼다" 다.
- **`notice` 는 있을 때만 실린다** (`error` 와 같은 규약). 늘 있는 빈 배열은 읽는 쪽이
  "확인했다" 고 믿게 만든다.
- **문구는 스텝 파일 안 고정 한국어 문장**이다 — 서빙의 안내문을 옮겨 오지 않는다
  (§3.8). 옮기면 같은 문장이 두 곳에 살고 한쪽만 고쳐진다.
- 세 기능이 같은 채널을 쓴다: 번역(용어 미준수·부분 실패·숫자) · 글다듬이(조각 실패·
  구조 훼손·숫자) · FAQ(조각 실패·문서 절단·근거 확보 부족).

### 번역 유닛에 **절 제목을 문맥으로** 단다 (2026-08-29)

구조 보존을 스켈레톤 분해로 하는 대가다 — 표 파이프·제목 마커는 코드가 쥐고 **LLM 에는
셀·문장 텍스트만** 들어간다. 그래서 표 셀 하나짜리 유닛(`대상`·`금액`·`해당 없음`)은
그것이 무엇에 관한 값인지 알 방법이 없고, 주어가 생략된 한국어 문장은 더 그렇다.

- **`TranslationUnit.context_scope` 는 원래부터 있었다** — 노드 경로에서만 채워지고
  (`units.py` 가 `node["scope"]` 를 읽는다) 프롬프트는 그 값을 한 번도 쓰지 않았다.
  계산해 놓고 안 쓰던 값이고, 마크다운 경로에서는 채워지지도 않았다.
- **번역 대상이 아니다.** 출력 스키마는 `{id, t}` 그대로이고 시스템 프롬프트가
  "`c` 는 배경이며 번역하지도 출력하지도 말라" 를 못박는다. 이 지시가 없으면 모델이
  문맥을 번역문에 섞고, **구조는 코드가 지키므로 그 결과가 정상 응답으로 내려간다.**
- **문맥이 없으면 키 자체를 넣지 않는다** — 빈 문자열을 실으면 모델이 그것도 번역해야
  할 무엇으로 읽을 여지가 생기고 토큰만 는다.
- **제목 자신에게는 달지 않는다** (자기가 그 문맥이다).
- **단건 폴백에도 같이 싣는다.** 폴백에만 빠뜨리면 배치가 실패한 유닛들만 문맥 없이
  번역되고, 그 차이는 **배치가 실패했을 때만** 드러나 알아채기 어렵다.
- **중복 제거 규약은 그대로다** — 같은 원문은 한 번만 부르므로 여러 절에 나오는 같은
  문구는 **처음 만난 절의 제목**을 문맥으로 쓴다. 절마다 따로 부르면 호출 수가 늘고
  같은 문구가 자리마다 다르게 번역되는 흔들림이 돌아온다.

### 번역 스트리밍은 **구조 보장과 맞바꾸는 것**이다 (2026-09-09, **09-14 정본 이식**)

요구가 "번역도 주루룩 보이게" 로 바뀌어 만든 경로다. 처음에는 반입 판본 `archive/not/` 에만
뒀는데, **2026-09-14 에 정본으로 옮겼다** — 아래 "번역 스트리밍을 정본으로 옮겼다" 절.
스트리밍 자체가 전송 계층에 묶일 이유가 없었다(글다듬이 정본이 이미 `httpx` SSE 로
같은 일을 한다). **지금 이 절의 설계 판단은 양쪽 판본에 그대로 적용된다.**

**정본 번역이 스트리밍을 안 하는 것은 게을러서가 아니다.** 유닛이 배치 JSON(`{id, t}`)
으로 오가므로 흘릴 것이 없고(원시 JSON 이 화면에 보인다), 배치 15개가 도는 순서도 문서
순서가 아니다. 흘리려면 **LLM 이 마크다운 본문을 그대로 내야** 하는데, 그러면 스켈레톤
분해가 성립하지 않는다 — **구조를 지키는 주체가 코드에서 프롬프트로 넘어간다.**
요구사항 §5 의 "표 깨짐" 을 코드로 막던 장치를 내려놓는 것이라 정본에 얹지 않았다.

- **감수한 것을 감추지 않는다.** 우리가 깨뜨리지는 않고(조각을 코드펜스·표 가운데에서
  끊지 않는다), 끝나고 **지문을 대조해 알린다**(`stream_pipeline.structure_diff` —
  표 행·셀·펜스·제목 개수). 글다듬이 `markdown_guard` 와 같은 취지다. 정본 경로
  (`POST /translate/markdown`)는 그대로 있고 **표가 많은 문서는 그쪽이 맞다.**
- **두 번 부른다** — 흘리고(`POST /translate/stream`, SSE), 끝나면
  `POST /translate/finalize` 가 `{original_text, translated_text, glossary, structure,
  download_url}` 을 준다. 하이라이트가 번역이 끝나야 정해지기 때문이다: 준수 판정은
  번역문 전체를 봐야 하고 좌표는 최종 문자열 기준이라 흐르는 도중에는 없다.
- **흘리는 것은 정본이다.** 사본(`<mark>`)을 흘리면 ① 하이라이트가 스트리밍 중에 먼저
  나타나 요구가 말한 순서와 어긋나고 ② 태그가 조각 경계에서 갈려 부스러기가 남는다.
- **finalize 는 무상태다.** 프론트가 방금 받은 두 텍스트를 되돌려 보내면 서빙이 대조를
  다시 한다 — 용어 매칭은 결정적이라 같은 답이 나오고, 세션을 붙이면 이 무상태 단위에
  상태가 생긴다. LLM 을 부르지 않으므로 재시도해도 안전하다. **`done` 이 준
  `translated_text` 를 그대로 보내야 한다** — 프론트가 델타를 이어 붙인 값과 한 글자라도
  다르면 좌표가 밀리고, 그 어긋남은 **하이라이트가 한 칸 밀린 화면**으로만 드러난다.
- **순서 버퍼·전량 실패 규약은 글다듬이와 같은 코드다** (2026-09-09 절). 머리 조각은
  라이브로, 뒤 조각은 버퍼에 모았다가 차례에 한 번에. **전량 실패에서는 한 글자도
  흘리지 않는다** — 실패 자리의 원문을 즉시 흘리면 오류로 갈아엎을 때 답이 나왔다가
  사라진다.
- **SDK 판본만의 차이 하나**: `model` 을 다시 싣는다(`LLM_MODEL_ID`, 기본 `"default"`).
  정본이 2026-09-07 에 없앤 값인데 **SDK 는 `model` 없이 요청을 만들지 않는다.**
- **그물**: `archive/not/check_not_units.py` **92건** — 정적(네 `llm.py` 가 같은 전송
  규약인가·전역 클라이언트 없음·`max_retries=0`) · 기동·라우트(네 단위) · 동작(순서·
  무손실·전량 실패에 원문 미유출·finalize 좌표가 그 낱말을 가리키는가).
- **미검증**: 실환경에서 SDK 경로가 뜨는지, 게이트웨이가 `stream=True` 를 받는지,
  중간 프록시가 SSE 를 모아 보내지 않는지, `model` 값을 게이트웨이가 어떻게 다루는지.

### 반입 판본을 **`archive/not/` 하나로** 합쳤다 (2026-09-09 요구 변경)

사내 mirror 에 **`lxml`·`openai` 가 들어왔다.** 그래서 판본 셋 중 둘의 존재 이유가
없어졌다 — `archive/not/` 은 "lxml 이 없어 깎아낸 것" 이고 `archive/not/openai/` 는 "SDK 도 되는지 보려고
나란히 둔 것" 이었다. **반입 대상은 `archive/not/` 하나이고, 기능이 가장 많은 판본이 됐다.**

| `archive/not/` 의 성격 | lxml 없이 깎아낸 한시 판본 | **반입 판본. 정본 + SDK + 스트리밍 셋** (스트리밍은 2026-09-14 에 정본으로 갔다) |
| 006 산출물 | `.txt`(hwpx 를 되쓸 수 없었다) | **`.hwpx`** |

| 스트리밍 | 글다듬이만 | **글다듬이·번역·FAQ 셋** |
| `archive/not/openai/` | 별개 판본(62건 그물) | **흡수** → `archive/not_openai_absorbed/` |

- **깎아낸 코드를 되살려 붙이지 않았다.** `archive/not/openai/` 가 이미 "정본 + SDK + lxml +
  번역 스트리밍" 이었으므로 **네 단위를 그것으로 교체**했다. 되살려 붙이는 쪽은 정본과
  갈릴 자리를 새로 만든다.
- **`archive/not/openai/` 를 지우지 않고 옮겼다.** `archive/not/` 전체가 **git 미추적**이라 지우면
  복구할 수 없다. 반입 표면에서 near-duplicate 만 없앤 것이다.
- **FAQ 스트리밍은 엔진만 있고 HTTP 로 안 열려 있었다.** 증분 파서(`markdown_items.py`)·
  `faq_stream_async`·`generate_faqs_stream` 이 다 있는데 `main.py` 가 import 조차 하지
  않아 **호출부 0건**이었고, 그 판본의 점검은 오히려 **"FAQ 는 스트리밍이 없다" 를

  먼저 굳은** 자리다). `POST /generate/stream` 을 붙였다.
- **FAQ 는 토큰을 그대로 흘리지 않는다.** 항목이 스키마·근거·중복을 지나야 화면에 나갈
  자격이 생기므로, 프롬프트가 `근거 → 질문 → 답변` 순으로 쓰게 해서 검증을 **접두어
  연산**으로 만든다 — 근거가 닫히면 대조하고(실패면 한 글자도 안 나간다), 질문이 닫히면

  끝내 안 오는 경우(형식 위반)에 **답 없는 질문이 화면에 남기** 때문이다.
- **payload 조립은 한 함수다**(`_store_and_payload`). 스트리밍·비스트리밍이 각자
  조립하면 `markdown`·`download_url`·`download_ready`·세션 저장 넷 중 하나가 한쪽에만
  붙고, 그 어긋남은 오류가 아니라 **다운로드 버튼이 한 경로에서만 켜지는** 형태로만
  드러난다.

  빠지면 그 기능이 조용히 사라지는데 **오류로는 드러나지 않는다.** 목록 밖이 갈리면

### 스트리밍이 **캔버스에 닿지 않고 있었다** (2026-09-09)

서빙 세 경로를 다 만들었는데 **워크플로우 스텝이 비스트리밍을 부르고 있었다.** 즉
`archive/not/openai/` 의 FAQ 스트리밍이 "엔진만 있고 `main.py` 가 import 조차 안 해 호출부
0건" 이던 것과 **같은 형태가 한 층 위(서빙 → 스텝)에서 반복**된 것이다.

| 스텝 | 부르던 곳 | 화면 |
|---|---|---|
| 글다듬이 | `/polish/stream` | **진짜로 흐른다** |
| 번역 | `/translate/markdown` | 완성 뒤 `_stream_chunks` 연출 |
| FAQ | `/generate` | 완성 뒤 `_stream_chunks` 연출 |

`emit` 뒤 `sleep(0)` 은 지연이 아니라 스케줄러 양보라 조각이 수 ms 안에 다 나가고
브라우저는 한 프레임에 그린다 — **"한방에" 와 구분되지 않는다.**

- **스텝 사본을 만들지 않았다.** 정본 스텝에 **SSE 시도 + 폴백**을 넣었다(글다듬이가
  이미 그 모양이다). 정본 서빙에는 스트리밍 라우트가 없으므로 SSE 아닌 응답이 와서
  **자동으로 폴백**하고 지금 동작 그대로다 — 흐르는 것은 `archive/not/` 서빙뿐이다. 스텝을
  `archive/not/` 에 두면 반입 표면이 늘고 사본 드리프트가 새로 생긴다.
- **SSE 리더는 `_stream_serving(env_name, path, payload, *, read_timeout)` 하나다** —
  `_post_serving` 과 시그니처를 맞췄고 **세 스텝이 같은 이름·같은 코드**로 든다.
  `check_deploy_contract` 의 "워크플로우 스텝 사본 일치" 가 **같은 이름의 함수는 같은
  본문**이라야 통과시키므로, 이름을 단위마다 다르게 두면 그 대조를 빠져나간다.
- **프레임 종류를 리더가 열거하지 않는다.** `done`·`error` 가 아니면서 `text` 를 든
  프레임은 무엇이든 흘린다 — 글다듬이·번역은 `delta` 하나지만 FAQ 는 `item_open`·
  `item_close` 도 화면 조각을 들고 온다. 종류를 리더에 적으면 단위가 프레임을 하나
  더할 때 **세 스텝을 모두** 고쳐야 하고, 안 고치면 그 조각이 조용히 화면에서 빠진다.
- **번역은 두 번 부른다** — 흘리고(`/translate/stream`), 끝나면 `/translate/finalize`.
  `_finalize_stream` 이 그 둘을 **비스트리밍 응답 모양으로 정규화**한다. 뒤 코드가 두
  모양을 각각 분기하면 조립이 두 벌이 되고 한쪽만 고치는 실수가 화면에서만 드러난다.
  **finalize 실패는 fail-open** 이다 — 번역문은 이미 흘렀으므로 되돌릴 수 없고,
  하이라이트가 없다고 결과를 버리면 **사용자가 방금 본 글이 오류로 바뀐다.**
  - **그래서 `finalize` 가 사본도 낸다** (`markdown_highlighted`·
    `source_markdown_highlighted`, **`/translate/markdown` 과 같은 키 이름**). 좌표만
    주면 태그를 끼우는 쪽이 스텝이 되고 겹침 병합·역순 삽입 규칙이 워크플로우에 한 벌
    더 생긴다. 조립은 `highlight_units` 를 그대로 쓴다.
- **FAQ 는 화면 조각을 서빙이 프레임에 실어 준다**(`_display_text`). 스텝이 제목 줄을
  조립하면 FAQ 화면 형식이 워크플로우에도 한 벌 생긴다. 형식이 서빙 안에서 두 곳
  (`_display_text` · `formatting._render`)인 것은 남지만, 갈리지 않는 근거를 **등식**
  으로 뒀다 — 흘린 조각을 이어 붙이면 최종 마크다운과 같아야 한다.
- **흘리는 시점이 전량 폴백 판정보다 앞이다** (번역). 비스트리밍은 판정을 끝내고
  흘렸는데 여기서는 흘리면서 간다. 성립하는 근거는 **서빙 쪽 보장**이다 — 전량 실패에서
  한 글자도 흘리지 않는다. 그 보장이 깨지면 답이 나왔다가 사라지는 화면이 된다.
- **그물이 이 층을 하나도 안 보고 있었다.** `_stub_gateway` 는 `_post_serving` 만
  바꾸므로 그대로 두면 `_stream_serving` 이 실패해 **폴백으로 지나가고 스트리밍 경로를
  한 줄도 태우지 않는다.** `check_workflow_run` 108 → **118**(번역 5 + FAQ 5),
  `archive/not/check_not_units` 91 → **92**(서빙 등식). **네 갈래를 되돌려 FAIL 을 확인했다** —
  조건부 스트리밍 제거(번역·FAQ **각각**, 두 번 흘린다) · `finalize` 호출 제거 ·
  리더를 `delta` 만 흘리게 되돌리기. 등식 판정은 `**Q{n}.` 의 번호를 하나 밀어 확인했다
  (**길이가 같은 어긋남**도 잡는다).
- **`_NO_STREAM_STEPS` 가 FAQ 를 아직 붙들고 있었다.** FAQ 스트리밍은 2026-09-02 에
  되살아났는데 그물이 따라오지 않아 **그때까지 한 번도 검사된 적이 없었다**(CLAUDE.md
  가 미해결로 적어 두었던 그 자리다). 네 스텝이 다 흘리므로 그 목록은 비었고, FAQ 는
  "오류 경로에서는 흘리지 않는다"(`_NO_STREAM_ON_ERROR`) 쪽으로 옮겼다.
- **미검증은 그대로다** — 게이트웨이가 `stream=True` 를 받는지, 중간 프록시가 SSE 를
  모아 보내지 않는지.

있었다** — 번역은 배치를 `LLM_CONCURRENCY`(15)로, 글다듬이는 조각을
`POLISH_LLM_CONCURRENCY`(4)로 겹쳐 도는데 FAQ 만 `for` 루프 안에서 하나씩 `await`
했다. **조각 사이에 순서 의존이 없다** — 앞 조각의 결과가 뒤 조각의 프롬프트에 들어가지
않으므로 순차로 돌 이유가 없었고, 대기시간만 조각 수에 그대로 비례했다(기본 호출 상한
6조각이면 한 번 호출 시간의 여섯 배다).

- **호출만 겹치고 채택은 조각 순서대로 한다.** `_request_chunk` 는 공유 상태를 건드리지
  않는 순수 호출이고(프롬프트 렌더 + LLM), 판정·채택은 `generate_faqs` 가 `gather` 결과를
  받아 **조각 순서대로** 흘린다. 도착 순서대로 채택하면 중복 판정(`seen_questions`)·
  기각 건수·**조각별 채택 상한**(`현재 + 몫`)이 전부 누적 상태라 **같은 문서가 실행마다
  다른 분포를 낸다** — 오류로는 드러나지 않고 "어느 구간에서 몇 개가 나왔나" 만 흔들린다.
  즉 병렬로 바뀐 것은 **타이밍뿐이고 결과는 순차 시절과 같다.**
- **첫 실패에서 멈추지 않는다** (멈출 것이 없다). 순차 시절에는 실패한 조각에서 `break`
  했지만 병렬에서는 호출이 이미 전부 나갔다 — 성공한 조각의 결과를 버리는 것은 손해다.
  실패는 **조각 순서 기준 첫 건**을 기록하고(전량 실패면 그것이 사용자에게 나가는 분류다),
  건진 항목이 있으면 기존 부분 실패 규약대로 `chunks_used < chunks_planned` 로만 남는다.
- **동시 수는 별도 손잡이다** — `FAQ_LLM_CONCURRENCY`(기본 6). `FAQ_MAX_CHUNK_CALLS` 는
  "몇 번 부르나"(비용)이고 이쪽은 "동시에 몇 개가 도나"(대기시간)다. 기본값을 그 상한과
  같게 둬서 **기본 설정에서는 배정된 조각이 한 번에 다 뜬다** — 상한을 올린 배포에서만
  둘이 갈리고, 그때 게이트웨이에 실리는 부하는 이 값이 잡는다. 429 가 나면 여기부터 내린다.
- **조각 크기 기본값을 24,000 → 12,000 으로 내렸다** (요구). 순차 시절에는 잘게 쪼개면
  호출 수만 늘어 손해였지만, 겹쳐 도는 지금은 **조각 하나의 크기가 곧 전체 대기시간**이다.
  덮는 문서 길이가 줄지 않게 `FAQ_MAX_CONTEXT_CHUNKS` 를 40 → 80 으로 함께 올렸다
  (80 × 12,000 ≈ 96만 자로 그대로다) — 안 올리면 `source_truncated` 문턱이 조용히 절반이
  되고, 그 상태는 "왜 뒤쪽에서 FAQ 가 안 나오나" 로만 드러난다.
- **부족분 재요청(`_fill_shortfall`)은 순차로 둔다.** 그쪽은 **이미 채택된 항목 목록을
  프롬프트에 실어** 다시 부르는 호출이라 앞 호출의 결과가 뒤 호출의 입력이다 — 겹쳐
  돌리면 같은 질문을 다시 받는다. 호출도 총 2회 상한이라 얻을 것이 없다.
- **스트리밍은 건드리지 않았다.** FAQ 스텝이 흘리는 것은 서빙이 조립을 끝낸 마크다운이고
  (2026-09-02), 근거·중복 기각을 지나기 전 항목을 흘리지 않는다는 규약이 그대로다.
- **그물**: `test_faq_chunking` 의 `ParallelChunkCallTest` **신규 4건**. 동시 호출 여부는
  **타이밍이 아니라 `peak`(동시에 떠 있던 수)** 로 본다 — 순차 코드에서는 어떤 타이밍에도
  1 을 넘을 수 없어 흔들리지 않는다. **세 갈래를 되돌려 FAIL 을 확인했다**: `gather` 를
  순차 `await` 로(3건 동시 FAIL) · 채택을 도착 순서로(분포가 뒤집힌다) · 동시 수 상한.
  기존 27건(→31)과 `check_unit_endpoints` 113 · `check_workflow_run` 108 은 그대로다.

### 글다듬이는 **다듬어지는 대로** 흘린다 — 연출이 아니라 진짜 스트리밍 (2026-09-09)

아래 2026-09-01 절이 되살린 것은 **완성 뒤의 연출**이었다. 서빙이 문서를 다 다듬어 한 번에
주고, 스텝이 그 글을 조각내 흘린다 — 그러니 사용자가 기다리는 수십 초 동안은 화면이 그대로
비어 있다. 게다가 `emit` 뒤의 `await asyncio.sleep(0)` 은 **지연이 아니라 스케줄러 양보**라
(가이드 5.2 의 write buffer flush) 조각 전부가 수 ms 안에 나가고 브라우저는 한 프레임에
그린다 — **조각을 나눈 것이 화면에서는 "한방에" 와 구분되지 않는다.** 네 스텝이 다 그렇다.

**글다듬이만 고쳤다. 넷 중 이 방식이 성립하는 유일한 단위다:**

| 단위 | LLM 출력 | 진짜 스트리밍이 되나 |
|---|---|---|
| 글다듬이 | **마크다운 본문 그대로** (`system.txt`: "다듬은 글만 반환합니다") | **된다** |
| FAQ | JSON 스키마 | 안 된다 — 원시 `{"question": …` 이 보이고, **근거·중복 기각을 지나기 전** 항목이 흘러 기각될 항목이 나타났다 사라진다 |
| 번역 | 배치 JSON (`{id, t}`, 15개 동시) | 안 된다 — 같은 이유 + 유닛 순서가 배치에 묶여 있다 |
| 006 | 발화 추출 JSON → 안내문 조립 | 안 된다 — 흘릴 것이 LLM 출력이 아니다 |

- **경로가 하나 늘었다** — `POST /polish/stream`(SSE). `POST /polish` 는 **폴백으로 남는다**:
  폐쇄망에서 게이트웨이가 `stream: True` 를 받는지 **실물로 확인되지 않았고**(네 단위가
  지금까지 `"stream": False` 를 명시해 온 이유가 그것이다), 안 받는 배포에서 기능이 통째로
  죽으면 안 된다.
- **폴백은 서빙이 흡수한다.** 게이트웨이가 스트리밍을 거절하면(`STREAM_UNSUPPORTED` —
  400·415·422·501) 서빙이 그 자리에서 `polish_document` 로 되돌아가 결과를 한 덩어리로
  흘린다. **스텝은 SSE 하나만 알면 된다** — 스텝에 두면 캔버스에 등록된 파일을 고쳐야
  폴백이 바뀌고, 그 파일은 사본 대조 대상이라 넷을 함께 고치게 된다. (스텝에도 한 겹 남긴
  폴백은 **서빙 판본이 어긋난 배포**용이다: SSE 가 아닌 응답이 오면 `POST /polish` 로 간다.)
- **순서 버퍼** — 조각은 세마포어 상한 안에서 함께 도므로 조각 3이 조각 1보다 먼저 끝난다.
  끝난 순서대로 흘리면 문단이 뒤섞이는데, **`result` 가 갈아 끼우므로 최종 결과는 멀쩡하다** —
  스트리밍 중에만 틀리고 로그에는 아무것도 안 남는다. 그래서 병렬은 유지하고 흘리는 순서만
  묶었다: **머리 조각**은 델타가 오는 대로 라이브로, **뒤 조각**은 자기 버퍼에 모아 두고
  차례가 오면 **한 번에** 붙인다(요구 확정).
- **흘린 것 == 정본이 계약이다.** `llm.polish_stream_async` 가 델타를 이어 붙인 것을
  그대로 `content` 로 내고 **`strip()` 을 걸지 않는다**(조각 사이 공백은 `rebuild` 가
  `suffix` 로 되꽂는다). 어긋나면 화면이 순간 다른 글을 보여주고 오류로는 안 드러난다.
- **첫 델타 뒤에는 재시도하지 않는다.** 다시 부르면 그 출력이 화면에 **이어붙어** 같은
  문장이 두 번 나온다 — 사용자는 그것을 결과물로 읽는다. 그래서 흘린 뒤의 실패는 그 조각의
  실패로 확정하고, 화면과 정본이 어긋난 사실을 `stream_diverged` → 안내문으로 낸다.
- **실패 조각의 원문은 최종 판정 뒤에만 흘린다.** 실패 자리에 원문을 되꽂는 것은 기존
  규약인데(`chunking.rebuild`), 그것을 **실패하는 즉시** 흘리면 전량 실패에서 원문이 통째로
  화면에 나간 뒤 오류로 갈아엎는다 — 답이 나왔다가 사라진다. **구현 중 실제로 그렇게
  만들었고 스모크가 잡았다.** 지금은 한 글자도 안 흘린 실패 조각을 만나면 그 자리에서
  멈추고, `gather` 가 끝나 `ok` 면 풀어 흘린다(전량 실패면 풀지 않는다 — 흘린 것이 0 이라
  오류 프레임만 나간다).
- **`stream_fallback` 을 잃을 뻔했다** — 폴백 결과로 `outcome` 을 덮으면 그 객체의
  `stream_unsupported` 는 거짓이라 "되돌아갔다" 는 사실이 사라진다. 값을 만들어 놓고 잃는
  자리가 이 저장소의 단골이다(2026-08-27 건과 같은 형태).
- **그물**: `Test/SFR-018/tests/test_polish_chunking.py` **+15건**(`PolishStreamOrderTest` 8 +
  `PolishStreamTransportTest` 7), `check_unit_endpoints` 107 → **113**,
  `check_workflow_run` 103 → **108**. 뒤엣것은 **HTTP 경계에 대역을 꽂는다** — `_stub_gateway`
  는 `_post_serving` 만 바꾸므로 그대로 두면 `_stream_polish` 가 실패해 **폴백으로 지나가고
  스트리밍 경로를 한 줄도 태우지 않는다**(MCP 406 이 넉 달을 살아남은 것과 같은 공백이다).
  **다섯 갈래를 각각 되돌려 FAIL 을 확인했다**: 순서 버퍼 · 실패 조각 보류 · `content` 에
  `strip()` · 스텝의 조건부 스트리밍(두 번 흘린다) · Accept 헤더.
- **미검증**: 실환경에서 게이트웨이가 `stream: True` + SSE 를 내주는지, 그리고 **중간 프록시가
  SSE 를 모아 보내지 않는지**(모으면 "한방에" 로만 보이고 오류가 없다 — 그래서
  `X-Accel-Buffering: no` 를 실어 둔다).

### 결과는 **흘리고**, 하이라이트는 끝나고 **갈아 끼운다** (2026-09-01)

좌우 비교 화면이 붙으면서 2026-08-28 에 토큰 스트리밍을 없앴는데, 요구가 바뀌었다 —
**바뀐 쪽이 "AI 가 주루룩 답변하는" 것처럼 보여야 한다.** 그때 적어 둔 근거("전용 UI 가
한 번에 그리므로 필요 없다")는 화면이 **완성된 뒤**를 말한 것이고, 그 전 수십 초 동안
화면이 비어 있다는 사실은 다루지 않았다. **번역·글다듬이 둘에 되살렸다.**

- **흘리는 것은 정본이다.** 사본(`<mark>`)을 흘리면 ① 하이라이트가 스트리밍 중에 이미
  나타나 요구가 말한 순서와 어긋나고 ② 태그가 조각 경계에서 갈려 `<ma` 같은 부스러기가
  남는다. **원시 마크다운·태그가 스트리밍 중에 보이는 것은 허용된 동작이다**(요구 확정).
  - **번역 쪽이 실수하기 쉽다** — 그쪽은 사본이 코드서빙 응답에 **이미 와 있다**
    (글다듬이는 MCP 를 한 번 더 불러야 생긴다). 그래서 두 단위가 다른 것을 흘리기 쉽고,
    그 어긋남은 오류로 드러나지 않는다.
- **흘리는 시점은 "되돌릴 수 없게 된 뒤" 다.** 서빙 결과를 받고, 번역은 **전량 폴백
  판정까지 끝난 뒤**에 흘린다. 그 판정은 응답이 200 이고 본문도 비어 있지 않은데
  **사용자 원문이 그대로 돌아온** 경우를 오류로 세우는 자리라, 그 앞에서 흘리면 원문을
  번역문인 양 뿌린 뒤 오류로 갈아엎게 된다 — 사용자에게는 **답이 나왔다가 사라지는**
  것으로 보인다. **오류 경로에서는 토큰이 한 개도 나가지 않는다.**
- **점검 호출과 겹쳐 돈다.** 점검을 먼저 띄워 두고 그 동안 흘린다. 순서대로 하면
  스트리밍이 순수한 연출이 되고 전체 시간만 늘어난다.
- **조각 크기는 글 길이에 따라 늘린다.** 32자 고정이면 20만 자 문서가 emit 6,250회다 —
  소켓 메시지 수가 글 길이에 비례하면 긴 문서에서 그 자체가 부하다. 총 emit 수에 상한
  (`_STREAM_MAX_EMITS` 400)을 두고 조각을 키운다. **사본이 3벌이라 006 도 함께 고쳤다**
  (`check_deploy_contract` 의 사본 일치 판정이 잡았다). 006 은 답변이 짧아 동작이
  바뀌지 않는다 — 12,800자 미만에서는 조각이 그대로 32자다.
- **그물**: `check_workflow_run` 85 → **91건**. 흘린 토큰을 버리지 않는 `_drain_with_tokens`
  를 만들었다 — 그전에는 `result` 만 남겨서 **"무엇을 흘렸나" 가 검사된 적이 없었다.**
  네 갈래를 되돌려 FAIL 을 봤다: 스트리밍 제거 · 사본 흘리기 · 오류 경로 흘리기 ·
  조각 상한 제거.
  - **판정 순서를 한 번 고쳤다.** 처음에 무손실 판정을 앞에 뒀더니 사본을 흘렸을 때
    그쪽이 먼저 걸려 **"사본을 흘렸다" 판정이 영영 FAIL 할 수 없었다.** 되돌려 보고
    알았고, 사본 판정을 앞으로 옮겼다(진단도 이쪽이 정확하다).

### 하이라이트는 **원문·결과 양쪽**, 내려받기는 **링크**다 (2026-08-28)

화면이 원문과 결과를 **좌우로 놓고 비교**하게 되면서 셋이 함께 움직였다. 상세는
`final/docs/change_0828.md`.

#### 좌표를 계산해 놓고 **한쪽만 쓰고 있었다** — 두 단위에서 같은 모양으로

| 단위 | 이미 있던 것 | 쓰던 것 |
|---|---|---|
| 글다듬이 | `_TGwords` 가 before·after 양쪽을 문서 절대 좌표로 편다 | `after` 쪽만 |
| 번역 | `hits[].spans`(원문) + `hits[].target_spans`(번역문) | 뒤엣것만 |

`changes[].span` 이 없어서 프론트가 문자열 검색으로 떨어졌던 것과 **같은 형태의
유실이고 세 번째다**. 새로 계산할 것은 없었다 — 버리던 값을 내보내면 된다.

- **삭제가 화면에서 사라지고 있었다.** `<mark>` 가 결과 기준이라 지워진 낱말에는 칠할
  글자가 없다(그래서 `span=None` 이었다). 좌우 비교에서는 **왼쪽에 자리가 있다** —
  이제 `source_span`/`target_span` 으로 갈라 "어느 쪽에 자리가 있느냐" 로 정리된다.
- **조립기는 하나다.** `key`/`span_key` 만 바꿔 두 번 부른다. 전용 경로를 두면 겹침
  병합·보호 구간 규칙이 두 벌이 되고, 한쪽만 고치는 실수는 **표가 깨지는 형태로만**
  드러난다. 번역은 재조립도 **같은 `rebuild_markdown`** 을 탄다.
- **보호 구간은 각 텍스트에서 따로 계산한다.** 코드펜스·HTML 태그 위치가 원문과
  결과에서 다르므로 한쪽 좌표를 다른 쪽에 쓰면 `<td rowspan="2">` 한가운데를 가른다.
- **번역은 양쪽이 같은 기준이다** — **실제로 참고한 것만**(`applied_only=True`),
  그리고 **사전에 걸린 낱말만**. 요구사항 §2 가 요구하는 것이 "어떤 단어가 용어사전의
  어떤 단어를 참고하였는지" 라 참고하지 않은 자리는 칠할 관계가 없다. 원문에 나오기만
  하면 칠하면 미준수가 화면에 드러나지만 **형광이 두 가지를 뜻하게 된다** — 미준수는
  `term_map_unapplied`·준수율이 맡는 검수용 값이고, `term_map` 이 미적용을 담지 않는
  것과 같은 기준이다.
- **옛 이름 `span` 은 내지 않는다.** 좌표가 둘인데 필드를 셋 두면 남는 하나는 언제나
  사본이고, 읽는 쪽이 어느 것이 정본인지 모른다.

#### 내려받기 — 미리 만든 파일 + 링크 (GenOS MinIO)

프론트가 정본 텍스트를 `POST /download` 로 되돌려 보내던 것을, 결과를 만들 때 서빙이
txt 를 굳혀 CDN 에 올리고 `download_url` 만 싣는 방식으로 바꿨다. **정본이 payload 에서
빠진다** — 화면이 파일 본문을 들고 있을 이유가 없어졌다.

- **`file_store.py` 사본 3벌** (`txt_output.py` 와 같은 규약). 운영 MCP 예제를 그대로
  옮기면 안 되는 것 셋: 동기 `urllib`(async 라우트의 이벤트 루프를 멈춘다) · 예외 원문
  반환(내부 URL 이 실린다, §3.8) · 임시 파일(`delete=False` 라 예외 경로에서 남는다).
- **fail-open.** 업로드 실패는 다듬기·번역이 실패한 것과 다른 사건이라 `download_url`
  을 비우고 결과는 그대로 낸다. 예외를 올리면 잘 만들어진 결과가 통째로 사라진다.
- **글다듬이는 여전히 무상태다.** 파일을 CDN 이 들고 있어서 Redis 를 붙이지 않았다.
- **폐쇄망에서 되는지는 미검증**이라 옛 `POST /download` 를 폴백으로 남겼다.

#### payload 는 **F12 에 나와야 할 값만**

**payload 는 사용자가 눈으로 보는 값만 담는다.** 내부 판정·검증·진단은 **로그가**
갖는다 — 프론트에 실어 보내면 화면이 그 값을 어떻게 쓸지 각자 정하게 되고, 쓰지 않는
값은 아무도 안 읽는 채로 계약에 남아 나중에 바꿀 때 발이 묶인다.

| 기능 | payload (정상) |
|---|---|
| 글다듬이 | `original_text` · `polished_text` · `download_url` |
| 번역 | `original_text` · `translated_text` · `download_url` |
| FAQ | `faq_items` · `download_url` |
| 006 | `text`(답변 + **미리보기**) · `download_url` (+ `session_id`·`template_id`) |

> 통일됐다. 정본은 `final/docs/FRONT.md` 요약 절이다.

**`error` 는 오류일 때만** 실린다 — 정상 응답에 `error: null` 을 넣지 않는다(있으나

오류 항목이 전부 덮는다.

빠진 것은 넷으로 갈린다 — **파일이 된 것**(정본), **disclaimer 로 가는 것**(구조·사실·

  지켜지는 상태였고, 실제로 `text`(사용자 질문)가 그렇게 새고 있었다. 남기는 것은

  `template_id` 를 더 남긴다. **허용 키 밖이 실리면 점검이 FAIL** 한다.
- **018 은 `text` 를 싣지 않는다.** 전용 UI 가 결과를 한 번에 그리므로 채팅용 조립

  지금은 payload 로도 화면으로도 안 나가는 **의도한 공백**이고 코드에 그렇게 적었다.
- `changes` 는 사본을 만드는 **입력**이지 화면이 읽는 값이 아니었고 운영 소비자가 0건.

### 프롬프트를 **라이브러리에서 받는다** — 네 단위 전부 (2026-09-03 요구 변경)

톤·문서유형 **목록**은 2026-08-18 부터 프롬프트 라이브러리에서 받고 있었다. 요구가
넓어졌다 — **자주 바뀌는 프롬프트 문장 자체를 전부 그리로 뺀다.** 006 의 항목 매핑
지시가 그 대표이고(코드서빙 안 `.j2` 파일이었다), 고정 골격인 **시스템 프롬프트는 파일로
둬도 된다.** 가이드 §10.5 가 "코드 PR 로 프롬프트 변경" 을 금지사항으로 든 그 자리다.

- **덮어쓰기지 이사가 아니다.** `.j2` 파일은 기본값이자 **폴백**으로 남고, ID 를 준
  이름만 라이브러리가 이긴다. 파일을 지우고 라이브러리만 두면 admin-api 장애가 곧
  기능 정지가 되고, 이관(손으로 옮겨 적는다)에서 프롬프트가 통째로 빠진다.
- **이름 → ID 매핑 하나로 배선한다** (`<단위>_PROMPT_IDS=extract_user=41,...`, JSON 도
  받는다). 이름은 **파일 이름에서 확장자를 뗀 것**이다 — 별도 이름표를 두면 "파일 이름
  ↔ 라이브러리 이름" 대조표가 하나 더 생기고, 어긋나면 **덮어쓰기가 조용히 일어나지
  않는다.** ID 는 코드에 적지 않는다(§10.5).
- **세 갈래가 전부 파일로 떨어진다** — 미설정 · 조회 실패 · **본문 렌더 실패**(관리자가
  변수 이름을 틀리면 `StrictUndefined` 가 그 자리에서 죽는다). 여기서 요청을 세우면
  문구 오타 하나가 기능을 통째로 막는다. **파일도 없을 때만 요청을 세운다** — 지시문
  없는 프롬프트의 결과는 정상 응답처럼 내려간다(기존 규약 그대로).
- **조용히 옛 문구로 돌지 않게** `GET /prompts` 가 이름마다 `source`/`reason` 을 낸다.
  이게 없으면 "ID 를 안 넣었다" 와 "넣었는데 못 읽었다" 가 화면에서 **똑같이 옛 문구**로
  보인다(글다듬이 `policy.source` 와 같은 규약). **본문은 싣지 않는다** — 담으면 그
  경로가 지시문 유출 경로가 된다(3.8절).
- **사본이 4벌**(단위 간 import 금지)이고 **본문까지 같아야 한다.** 갈리면 같은 관리자
  실수가 단위마다 다르게 끝난다 — 한쪽은 파일로 폴백하고 한쪽은 요청이 죽는 식이다.
  `check_deploy_contract.check_prompt_library_copies()` 가 AST 로 대조한다(독스트링 제외).
- **지시문 언어는 전부 한국어다** (2026-09-03). 시스템 프롬프트도 한국어로 쓴다 —
  라이브러리에 올릴 때도 같다(등록 절차: `final/docs/SERVING_REGISTRY.md` §2-3).
- **그물**: `Test/SFR-006/tests/test_prompt_library.py` **신규 10건**(덮어쓰기·세 갈래 폴백·
  캐시·미설정과 조회 실패 구분·본문 미노출), `check_api_contract` 46→**50**,

### MCP 호출이 **도구에 닿지도 못하고 있었다** — Accept 헤더 (2026-09-07)

실환경에서 MCP 경로가 전부 `406 Not Acceptable` 이었다. 먼저 의심한 것은 경로였는데
(`.../mcp/13/mcp` 가 이상해 보인다) **경로는 §H 그대로 맞다** — `{GENOS_URL}/api/gateway/`
+ `mcp/<서빙 id>/mcp` 이고, 뒤의 `/mcp` 는 서빙 안 MCP 엔드포인트다.

**틀린 것은 헤더다.** MCP 스트리머블 HTTP 서버는 POST 본문을 읽기 **전에** Accept 를 보고,
`application/json` 과 `text/event-stream` 을 **둘 다** 열거하지 않으면 도구를 부르지도 않고
끊는다. httpx 기본값은 `Accept: */*` 라 그 검사를 통과하지 못한다 — 즉 **도구를 아무리
고쳐도 닿지 않는** 상태였고, 스텝은 그 406 을 다른 4xx 와 같은 칸(`upstream_final`)에 넣어
"요청을 처리하지 못했습니다" 로만 냈다. **응답 본문에 사유가 그대로 적혀 있었는데**
(`Client must accept both …`) 3.8절대로 상태코드만 로그에 남으므로 그 문장이 어디에도
남지 않았다 — 원인을 찾는 데 걸린 시간이 전부 그 때문이다(아래 디버그 에코를 붙인 이유).

- **응답이 SSE 로 온다.** 서버가 JSON 응답 모드가 아니면 `tools/call` 결과를
  `text/event-stream` 프레임에 담아 준다. `response.json()` 만 쓰면 그때 `InvalidJson`
  으로 떨어지는데, 그 상태는 **통신도 되고 도구도 돌았는데 결과만 사라지는** 형태다
  (되돌려 보면 `failure=None` + `body={"text": ""}` 로 조용히 빈손이 된다).
  `_decode_body` 가 두 모양을 다 받는다.
- **진행 알림을 응답으로 읽지 않는다.** 프레임이 여럿 올 수 있고 앞쪽은 `method` 를 든
  알림이다 — 마지막 프레임을 집으면 알림을 결과로 읽는다. `result`/`error` 를 든 프레임이
  응답이다.
- **`_post_json` 은 9벌 사본이라 넷도 함께 고쳤다.** MCP 를 부르는 스텝은 다섯인데
  `check_deploy_contract` 의 "사본 일치" 가 나머지 넷을 잡았다 — 5벌만 고치면 같은 이름의
  함수가 두 가지가 되고 한쪽만 고쳐진 채 굳는다. **`_MCP_HEADERS` 는 부르는 다섯에만**
  둔다(코드서빙 POST 에 Accept 를 실을 이유가 없고, 모듈 상수는 대조 대상이 아니다).
- **다음에 나올 수 있는 실패는 `400 Missing session ID` 다.** 서버가 상태 유지 모드로 떠
  있으면 `initialize` → `Mcp-Session-Id` 핸드셰이크가 필요하다. 지금은 `tools/call` 한 번만
  보내고 **상태 없는 모드를 전제한다** — 미검증이고, 고칠 자리는 `_mcp_call` 하나다.
- **이 층을 보는 점검이 하나도 없었다.** `_stub_gateway` 가 `_mcp_call` 을 통째로 대역으로
  바꾸므로 **그 아래(헤더·본문 해석)는 검사된 적이 없다** — `translated_markdown`·`stats`
  가 유실됐던 것과 같은 형태의 공백이다. `_check_mcp_transport` 가 **HTTP 경계에** 대역을
  꽂아 스텝이 실제로 내보내는 헤더를 받아 보고, 서버가 406 을 내는 판정까지 실물과 같게
  흉내낸다. `check_workflow_run` 91 → **106**(스텝 5 × 3건).

`02-00020003` → **`ERR-02-00020003`**. 로그·응답에서 오류 코드를 눈으로 바로 가려내기

### 디버그 에코 — **테스트 기간 한정** (2026-09-07)

3.8절 화이트리스트가 값을 버리기 때문에(허용 목록 밖은 **이름만** 남는다) 로그만으로는
무엇이 왜 실패했는지 알 수 없다. 위 406 이 그 증거다 — 사유가 응답 본문에만 있었고
로그에는 상태코드만 남았다. 원인을 찾는 동안 표준 로그와 **별도로** 한 줄을 더 뿜는다.

- **`print` 가 아니라 `sys.stderr.write` 다.** 표준 로그와 섞이지 않게 하려는 것이다.
  MCP 는 stdout 이 전송 채널일 수 있어 한 줄만 섞여도 프로토콜이 깨진다 — 3.10절이
  print 를 금지하는 실제 이유이고 `check_deploy_contract` 가 그것을 본다. 플랫폼은
  stdout·stderr 를 둘 다 수집하므로 화면에서는 같다.
- **`GENON_DEBUG=1` 일 때만 낸다. 기본은 꺼짐** — 허용 필드 밖 값이 남으므로 원인을
  추적할 때만 켜고 운영에서 켜 두지 않는다.
- **값은 300자에서 자른다.** 문서 원문·프롬프트가 통째로 실리면 이 에코 자체가 유출
  경로가 된다(3.8절). 그래서 인자도 **키만** 싣는다(MCP 도구 호출·POST 페이로드).
- 붙인 자리는 넷이다 — 워크플로우 스텝 9개(요청·전송 실패·**HTTP 오류 본문**),
  코드서빙 4단위 `logging_utils`(`log_warning`·`log_error` 에 물렸다), 네 `llm.py`
  (게이트웨이 응답 본문·예외 원문), MCP 파일 5개(도구 이름·인자 키·예외 원문).
- **걷어낼 때는 각 파일의 `디버그 에코` 블록과 그 호출만 지운다** — 로그 경로는 손대지
  않았으므로 지우면 원래 규약으로 정확히 돌아온다.

### LLM 호출을 **`httpx` 로 직접** 한다 — `openai` SDK 제거 (2026-09-07)

실환경에서 SDK 때문에 호출이 실패했다. 게이트웨이는 **OpenAI 호환 경로**를 내주므로
SDK 가 하던 일은 `POST {base}/chat/completions` 한 번과 응답 dict 에서 본문을 꺼내는
것뿐이고, 그 둘은 각 `llm.py` 가 이미 하고 있었다(`_extract_content`).

**절반은 이미 그 모양이었다** — FAQ·006 은 처음부터 `httpx` 였고(워크플로우 이미지에
임의 패키지를 넣을 수 없던 시절의 유산이다), 옮긴 것은 **글다듬이·번역 둘**이다.
이제 **018 세 단위 중 SDK 를 요구하는 단위가 0개**이고 `requirements.txt` 에서
`openai` 가 빠졌다 — 사내 mirror 에 그 패키지가 없어도 빌드된다.

- **덤으로 4xx 를 재시도하지 않게 됐다.** SDK 판은 모든 예외를 같은 칸에 넣어 요청 자체가
  잘못된 경우(400·401·404)도 `LLM_RETRY_COUNT` 만큼 두드렸다 — 같은 결과가 나오는 호출을
  반복하며 대기시간만 늘고, 로그에서 일시적 장애와 구분되지 않았다. **번역은 배치를
  `LLM_CONCURRENCY`(15)로 동시에 돌리므로 그 낭비가 배치 수만큼 곱해졌다.**
- **전역 커넥션이 없어졌다** (§D.2). SDK 판은 `AsyncOpenAI` 를 모듈 전역에 캐시했고,
  그래서 **캐시 키를 설정값으로 잡는 방어 코드**가 따로 필요했다(토큰이 회전돼도 옛 값을
  쓰는 것을 막으려고, 2026-08-14). 전역이 없어지면서 그 방어 자체가 필요 없어졌다 —
  `check_unit_endpoints` 의 판정도 "캐시 키가 묶여 있는가" 에서 **"전역이 없는가"** 로
  뒤집었다. **아무 단위도 타지 않는 분기는 썩으므로** 옛 판정을 조건부로 남기지 않았다.
- **`LLM_MODEL_ID` 를 함께 없앴다** (요구 확정). 게이트웨이의 서빙 경로
  (`/rep/serving/{LLM_SERVING_ID}/v1/chat/completions`)가 이미 모델을 결정하므로
  `LLM_SERVING_ID` 가 모델 지정 역할을 함께 하고, 본문의 `model` 은 그 위에 얹히는
  중복이었다. **게이트웨이 필수 환경변수가 4종 → 3종**이 됐다.
  **되살릴 자리는 여덟이다** — 네 단위의 `config.py`(정적 메서드) + `llm.py`(요청 본문).
  게이트웨이가 OpenAI 규격대로 `model` 을 필수로 검증하는 배포를 만나면 400/422 로 드러난다.
- **번역 `CONFIG_MISSING` 을 상수로 올렸다.** 그 파일 안 리터럴 두 개였다 — 호출부가 이
  값으로 분기하게 되는 순간 한쪽만 고쳐도 예외 없이 조용히 분기가 죽는다(나머지 셋은
  이미 상수였다).
- **덤으로 사본 드리프트 하나를 찾았다**: `"stream": False` 가 **006 에만 없었다.**
  게이트웨이 기본값이 스트리밍이면 그 단위만 응답 모양이 달라지는데, 오류로는 드러나지
  않는다. 네 사본을 정적으로 대조하는 판정을 붙이자 그 자리에서 잡혔다.
- **그물**: `Test/SFR-018/tests/test_polish_chunking.PolishLlmTransportTest` **10건** +
  `test_translation_llm.py` **신규 14건**(번역 고유 셋 — 세마포어를 함수 안에서 잡는가·
  `max_tokens`·코드펜스 제거), `check_unit_endpoints` 95 → **107건**
  (`_check_llm_request_body` 가 **네 사본을 한 판정으로** AST 대조한다 — 한 단위에만
  남으면 그 단위만 다른 요청을 보내고, 게이트웨이가 무시하면 아무 일도 안 일어난다).

  `/chat/completions` 제거 · FAQ 한 단위에만 `model` 되살리기 · 번역에 `openai` import
  되살리기.
  - **`LLM_RETRY_COUNT` 는 import 시점에 굳는다** — 호출 시점 읽기는 게이트웨이 3종뿐이다.
    테스트가 환경변수로 3회를 기대했다가 실제 2회에서 FAIL 했고, 기대값을
    `Config.LLM_RETRY_COUNT` 에서 파생시키도록 고쳤다. **운영에서 이 값을 바꾸려면
    서빙을 재기동해야 한다.**

### 톤·문서유형 프롬프트도 **이름=ID 로** 받는다 (2026-09-07 요구 변경)

프롬프트를 **전부** 프롬프트 라이브러리에서 당겨 쓰기로 하면서, 코드서빙 안에서 **JSON 을

어긋나서 통째로 걷어냈다.

| | 그전 (2026-08-18~09-06) | 지금 |

| 등록 | 프롬프트 **한 건**에 JSON | 톤·문서유형마다 프롬프트 한 건 |
| 배선 | `POLISH_POLICY_PROMPT_ID` · `LANG_POLICY_PROMPT_ID` | `POLISH_PROMPT_IDS` 에 `system_<tone>=51,doc_type_<code>=62` |

### FAQ 의 운영 합불 기준이 **PII 하나**였다 — eval (2026-09-07)

근거성에 기준을 두지 않는 판단(재서술이 곧 오답은 아니다)은 그대로다. 그런데 그 결과로
FAQ 스위트의 `targets` 에 남은 것이 `pii_leak_count` 뿐이라 **30개를 요청해 2개가
나와도 `verdict: pass`** 였다. 품질이 무너져도 리포트가 초록불이면 가드레일이 아니다.

**서빙은 이미 답을 들고 있었다.** `FaqResult.as_payload()` 의 `count`·`requested_count`·
`rejected{schema,ungrounded,duplicate}`·`coverage_capped` 는 전부 **결정적 사실**이고
재서술 논쟁과 무관하다 — 계산해 놓고 아무도 채점하지 않던 값이다(값을 만들어 놓고 화면에
안 쓰던 2026-08-27 건과 같은 형태이고, 이번에는 그 소비자가 eval 이다).

- **거는 것은 둘뿐이다.** `yield_rate`(고른 개수 대비 산출)와 **스키마** 기각률.
  스키마는 **우리가 프롬프트로 못박은 계약**이라 문서 성격과 무관하다.
- **`ungrounded`·`duplicate`·커버리지는 보고만 한다.** 앞의 둘은 원천 문서의 성격에
  달렸고, 커버리지 상한은 **비용 손잡이**(`FAQ_MAX_CHUNK_CALLS`)가 정하는 값이다 —
  배포 설정을 품질 불합격으로 세면 상시 빨간불이 되고 사람이 지표를 끈다.
- **후보가 0건이면 기각률은 `None`** 이다. 0.0 을 주면 아무것도 못 만든 실행이 스키마
  기준을 **만점으로 통과**한다. **요청 개수가 없는 통계는 예외**다(`pairs.pair_texts`
  의 원문 부재 규약과 같다) — 조용히 1.0 을 주면 이 지표를 붙인 이유가 사라진다.
- **임계 둘(0.8 · 0.1)은 실측 전 잠정값**이고 `payload.thresholds` 로 덮는다.
  HANDOFF §A-2 의 조각 예산과 같은 성격이라 실물에서 처음 재는 순간 조정 대상이다.
- **`chrf_score` 의 어긋남은 남겨 뒀다** — `role: operational` 인데 `targets` 에 없어
  값이 아무리 낮아도 verdict 에 안 잡힌다. 참조 번역이 있는 입력이 아직 없어 임계를
  정할 근거가 없다. 정본은 `Test/eval/README.md`.

### 생성 문서 PII 감사는 **MCP 도구**로, 사람이 직접 돌린다 (2026-09-07)

`pii_leak_count` 는 eval 스위트 안에 있어 **평가를 돌릴 때만** 도는데, 요구는 야간·주간
단위로 **생성 문서를 모아 미마스킹 건수를 집계**하는 것이다. 그래서 다섯 번째 MCP 파일
`final/mcp/genon_pii_audit.py` 를 만들었다 — **등록이 9번에서 10번이 된다.**

- **스케줄러를 넣지 않는다** (요구 확정). 주기는 운영이 정하고 우리는 **집계만** 낸다.
  기능 응답 경로(payload)에도 붙이지 않는다 — 매 응답마다 도는 판정이 아니고, 응답에
  실으면 그 값이 화면 계약이 되어 나중에 바꿀 때 발이 묶인다.
- **LLM 을 쓰지 않는다.** ① 미마스킹 개인정보를 찾겠다고 그 텍스트를 모델 호출에
  실으면 **감사 자체가 유출 경로**가 된다 — 세려던 사고를 우리가 낸다. ② 주 단위 추세를
  보는 값인데 판정이 흔들리면 건수가 는 건지 모델이 달라진 건지 구분할 수 없다.
  ③ 허용치가 0이라 오탐 비용이 크고, **오탐은 결국 미탐으로 간다**(사람이 지표를 끈다).
  GenOS 가드레일(#315)과는 경쟁이 아니라 **짝**이다 — 마스킹은 적재 층이 하고 이 도구는
  그 층이 빠졌다는 사실을 **산출물 쪽에서** 잡는다.
- **본문 키가 없는 문서를 "유출 0건" 으로 세지 않는다.** 그렇게 세면 키 이름을 한 번
  잘못 준 감사가 **전건 통과**로 나오고, 그 상태는 오류도 경고도 없이 "이번 주도
  깨끗합니다" 로만 보인다 — 이 도구가 잡으려는 것과 정확히 같은 형태다. `unreadable`
  로 드러내고 `scanned` 를 `documents` 와 따로 낸다.
- **유출 목록에 상한을 두지 않는다.** 상한 뒤의 유출은 리포트에서 사라지는데, 감사에서
  그건 미탐과 같다(변경 하이라이트의 `max_items` 를 없앤 것과 같은 근거).
- **검출한 값은 응답에 담지 않는다** (3.8절) — 유형과 자리만. 담으면 감사 리포트가
  유출 경로가 된다. `not_detected`(이름·주소·계좌번호)를 이유와 함께 함께 내서
  `leak_count == 0` 을 "개인정보 없음" 으로 읽지 못하게 한다.
- **판정부는 `eval/eval_mcp/pii_metrics.py` 의 사본이다** (배포 단위 간 import 금지).
  갈리면 같은 문서가 감사 도구와 평가지표에서 **다른 건수**로 나오고 오류로는 드러나지
  않는다 — `check_mcp_tools` 가 두 구현에 **같은 입력을 태워** 대조하고(정적 diff 가
  아니다) **검출기 목록**도 맞춘다. 표본에 없는 유형을 한쪽에만 더하면 동작 대조만으로는
  안 잡히기 때문이다.

### 변경 하이라이트가 **문장 경계를 넘고 있었다** — 1:1 정렬 (2026-09-15)

글다듬이 결과의 변경 표시가 이상하다는 제보에서 시작했다. 원인은 둘이고 **둘 다
`difflib` 의 성질에서 나온다.**

| 증상 | 원인 |
|---|---|
| 형광이 **줄바꿈을 넘어** 칠해진다 | 문장 레벨 diff 가 여러 문장을 한 덩어리 `replace` 로 묶으면, 그 안의 낱말 LCS 가 **경계를 넘어** `("임. 자료", "입니다.")` 같은 항목을 만든다 |
| 문장이 **자리를 옮기면** 양쪽이 통째로 형광 | `SequenceMatcher` 는 **순서 보존(LCS)** 이라 교차하는 짝을 못 만든다 — 이동이 **삭제 + 삽입** 두 사건으로 쪼개진다 |

**삽입·삭제는 원래 멀쩡했다.** "앞에 문장 하나가 끼면 뒤가 다 밀려 못 쓰게 되는 것
아닌가" 를 실측으로 확인했는데, LCS 라 밀리지 않고 삽입 한 건으로 정확히 잡힌다.
고칠 것은 위 둘뿐이다.

#### 프롬프트가 요청하고 **코드가 검증한다**

문장을 1:1 로 되쓰게 하면 짝이 이미 정해져 **이동·경계 넘김이 원천적으로 불가능**해진다.
그런데 **프롬프트 지시를 보장으로 보지 않는다**(§5)가 이 저장소의 규약이라, 요청해
놓고 `diff_changes` 가 **센다**:

- 단위 수가 같고, 각 짝이 서로 닮았으면 → **`i↔i` 고정**, 문장 레벨 diff 를 아예 안 돈다.
- 아니면 → **예전 `difflib` 경로 그대로.** 그쪽은 지금도 운영에서 도는 코드다.

검증이 없으면 모델이 문장 하나를 더 쓴 순간 **뒤가 전부 한 칸씩 밀려** 문서 전체가
형광이 된다 — 예외는 나지 않고 화면만 무의미해지는, 이 저장소가 계속 잡아 온 형태다.

- **문턱이 둘인 이유.** 짝 하나가 크게 다시 쓰였다고 문서 전체를 폴백시키면 이 경로가
  거의 안 탄다. 반면 이동·밀림은 **거의 모든 짝**을 어긋나게 한다 — 그래서 짝별 문턱은
  낮게(`_TGMIN_PAIR_SIM` 0.2), 몇 개까지 봐줄지는 따로 둔다(`_TGMAX_MISALIGNED_RATIO` 0.2).
- **`max(1, …)` 로 한 칸은 언제나 봐준다.** 비율만 쓰면 **다섯 문장 미만 문서에서
  허용치가 1 밑으로 떨어져 무관용**이 되고, 한 문장만 크게 다시 써도 전체가 폴백한다.
  짧은 글이 흔한 기능이라 그러면 1:1 이 거의 안 선다 — **구현 중 실제로 밟았다**
  (네 문장짜리 픽스처가 폴백해서 판정이 안 갈렸다).
- **유사도는 문자 3-gram 다중집합 자카드**다. `SequenceMatcher.ratio()` 는 짝마다
  O(len²) 이고 문서 하나에 문장이 수백 개다(eval `chrF` 를 O(n²) 에서 고칠 때와 같은 방식).

#### 크게 다시 쓰인 자리는 **통째로 한 항목**

1:1 이 서도 **한 짝 안에서** 크게 다시 쓰이면 조사·흔한 낱말만 `equal` 로 남고 나머지가
흩어져 **형광이 누더기**가 된다 — 문장 전체를 칠한 것보다 어느 낱말을 고쳤는지가 오히려
묻힌다. 바뀐 낱말이 `_TGMAX_WORD_CHANGE_RATIO`(0.6)를 넘으면 접는다.
**항목이 둘 이상일 때만** 접는다 — 한 건짜리는 이미 통째 표시라 접으면 앞뒤 안 바뀐
낱말까지 형광에 들어간다.

#### `clear` 톤만 규칙에서 뺀다

"명확·간결" 의 지시문이 **"한 문장에 한 가지만 담고"** 다 — **문장을 나누라는 지시**라
1:1 과 정면으로 충돌한다. 넣으면 넷 중 하나가 제 일을 못 하고 그 손해는 **결과물의
문체로만** 드러난다. 그 톤에서는 문장 수가 달라져 자연히 폴백으로 흐른다.

- **문장은 코드가 아니라 프롬프트 디렉토리에 있다** (`sentence_rule.txt`) — §10.5 가
  코드 안 프롬프트 인라인을 금지하고, 이 경로면 라이브러리(`sentence_rule=ID`)로도 덮는다.
- **렌더 실패는 요청을 세우지 않는다.** 그 줄이 빠지면 2026-09-15 이전 동작으로 돌아갈
  뿐이라, 없어도 되는 지시 하나가 기능을 막으면 안 된다(톤 프롬프트 폴백과 같은 규약).
- **`diff_changes` 는 톤을 모른다.** 정렬 판정은 **결과를 보고** 하므로 도구 인자가
  늘지 않았다 — 톤을 넘기면 MCP 계약이 넓어지고 호출부가 그 값을 들고 다녀야 한다.

#### payload 계약은 한 글자도 안 바뀌었다

`changes[]` 는 `{before, after, source_span, target_span}` 그대로이고 `kind` 같은 필드를
더하지 않았다. **프론트가 고칠 것이 없다** — 같은 모양의 값이 더 정확해질 뿐이다.

#### 그물 — **손으로 지은 예제로는 갈리지 않았다**

`test_diff_highlight` 21 → **31건**, `check_prompt_render` 77 → **82건**.

처음 픽스처(3문장 존댓말 변환)로는 **1:1 을 통째로 꺼도 통과**했다 — 그 입력에서는 두
경로가 같은 답을 낸다. 그래서 **무작위 대조**를 돌렸다: 600건 중 1:1 이 서는 입력이
436건(73%)이고 **두 경로가 다른 답을 내는 입력이 56건(9.3%)** 이다. 그중 하나를 픽스처로
박아 판정이 실제로 갈리게 했다. 접기 판정도 같은 문제였다(공통 낱말이 앞에 몰린 예제는
접기 없이도 한 건이라, **공통 낱말이 흩어진** 입력으로 바꿨다).

**일곱 갈래를 각각 되돌려 FAIL 을 확인했다** — 1:1 분기 · 유사도 가드 · `max(1,…)` 관용
(**2건 동시**) · 변경 비율 접기 · `sentence_rule.txt` 삭제(**단위는 죽지 않고 규칙만
빠진다** — 설계한 폴백) · `clear` 톤 예외 · 라우트의 변수 전달.

### 번역 스트리밍을 **정본으로 옮겼다** — 두 판본이 전송 계층에서만 갈린다 (2026-09-14)

판본이 둘인데(정본 `final/` = `httpx`, 반입 `archive/not/` = `openai` SDK) **어느 쪽을
등록하느냐에 따라 기능이 달라지는** 상태였다. 마지막까지 남은 것이 번역 스트리밍이고,
그것이 전송 계층에 묶여 있던 이유는 하나다 — `stream_pipeline` 이 부르는
`llm.translate_stream_async` 를 **SDK 의 `stream=True` 로만** 구현해 뒀다.

**묶일 이유가 없었다.** 글다듬이 정본이 이미 같은 일을 `httpx` SSE 로 한다
(`polish_stream_async`, 2026-09-09). 그 코드를 옮겨 적고 번역 쪽 차이 둘만 뒀다.

| 옮긴 것 | 비고 |
|---|---|
| `llm.translate_stream_async` + `_delta_from_frame` + `STREAM_UNSUPPORTED` | 글다듬이와 **같은 코드**. 갈리면 같은 게이트웨이 거절이 두 단위에서 다르게 끝난다 |
| `stream_chunking.py` · `stream_pipeline.py` | **전송 계층을 모른다** — 그래서 그대로 옮겨진다 |
| `main.py` 두 라우트 · `api_contract.py` 요청 모델 둘 · `prompt_builder.build_stream_prompts` · `Config.STREAM_CHUNK_CHARS` | |
| 프롬프트 `*_stream.txt` 3벌 | 프롬프트는 전송 계층을 모르는 값이라 애초에 갈릴 이유가 없었다 |

- **번역이 배치 경로와 갈리는 자리 둘.** ① **`max_tokens` 를 싣는다** — 조각 응답이
  잘리면 그 구간이 조용히 원문으로 남는다. ② **세마포어를 함수 안에서 잡지 않는다.**
  `llm_call_async` 는 안에서 잡는데(단건 폴백이 그 제한을 우회하지 못하게) 스트리밍은
  반대다 — 조각 순서를 쥐는 것이 `stream_pipeline` 이라, 여기서 잠그면 "머리 조각은
  라이브로, 뒤 조각은 버퍼로" 를 `llm.py` 가 정하게 된다.
- **```json 펜스 제거는 안 옮겼다.** 배치는 출력이 JSON 이라 펜스가 붙으면 파싱이
  죽지만, 스트리밍 출력은 마크다운 본문이다 — 걷어내면 원문에 있던 코드펜스가 사라진다.

**결과: 갈리는 자리가 12개가 됐다** — 네 단위 × (`llm.py`·`config.py`·
`requirements.txt`). `EXPECTED_DIFF` 15 → **12**, `EXPECTED_EXTRA` 2 → **0**,
프롬프트 차이 3 → **0**. **기능 차이 0 이므로 판본을 고르는 기준은 하나다** — 사내
mirror 에 `openai` 패키지가 있는가(없는데 SDK 판을 올리면 `pip install -r` 이 그
자리에서 선다).

- **`EXPECTED_EXTRA` 가 비었다고 그 판정을 지우지 말 것.** 비어 있다는 사실이
  "기능이 양쪽에 다 있다" 를 못박는다 — 한쪽에만 파일이 생기면 거기서 FAIL 한다.
- **`check_not_units` 가 못 보는 자리가 있다.** `EXPECTED_DIFF` 는 **파일 단위**라
  `llm.py` **안에서** 함수가 사라져도 "원래 갈리는 파일" 이라 통과한다. 실제로 정본의

  `check_unit_endpoints` 가 119 → **81/83** 으로 잡았다(번역 단위가 통째로 못 뜬다).

드리프트만 잡는 것이 아니라 **한쪽의 결함도 잡는다**는 예다.

#### `final/` — 기능별로 갈라 놓은 읽기용 배치 (요구)

"실제로 도는 코드가 `archive/not/` 과 `final/` 둘인데 헷갈린다" 가 요구였다. `final/` 은 그
둘을 **기능별로 모아** 놓는다:

```
final/<기능>/request/   ← 정본(httpx) **전체 트리**. 그대로 등록할 수 있다
           /open_ai/   ← SDK 판에서 **갈리는 3개만**. request 위에 덮는다
           /prompt/    ← 그 기능의 프롬프트 (두 판본이 같다)
final/workflow/        ← 캔버스 파이썬 스텝 9개 (판본 무관)
final/mcp/             ← MCP 도구 파일 4개 (판본 무관)
```

- **스텝·MCP 는 기능별로 가르지 않았다** (2026-09-14 추가). 한 도구를 여러 기능이
  부르고(`text_guard` 는 글다듬이·번역), 스텝은 **캔버스에 붙이는 순서가 곧 그 기능의
  흐름**이라 아홉 개를 한자리에 놓고 표로 읽는 편이 맞다. 그 표가 `final/README.md` 에
  있다 — 스텝마다 무엇을 부르는지(서빙 경로·MCP 도구)와 읽는 환경변수 여섯.
- **이쪽은 두 판본이 바이트까지 같아야 한다.** 게이트웨이의 LLM 경로를 직접 부르지
  않아(스텝은 서빙·MCP 를 `httpx` 로, MCP 파일은 표 판정만) 전송 계층이 갈릴 자리가
  없다. **파일 수까지 못박는다** — 하나가 빠져도 나머지는 그대로 복사되고, 그 상태는
  "그 스텝만 캔버스에 없는" 형태로만 드러난다. 되돌려 FAIL 을 본 갈래는 둘이다
  (MCP 한 파일 드리프트 · 스텝 한 개 삭제 — 뒤엣것은 **개수와 목록 둘 다** FAIL 한다).
- **붙이자마자 드리프트 하나가 나왔다** — `archive/not/workflow/sfr018_faq_02_generate.py` 에
  공백만 있는 줄 하나가 더 있었다(실수로 들어간 편집). 동작은 같지만 **그 자리가
  갈릴 수 있다는 사실 자체가 문제**다: `check_not_units` 의 `EXPECTED_DIFF` 는 코드
  서빙 네 단위만 보므로 **스텝·MCP 의 드리프트를 보는 그물이 0건이었다.** `archive/not/` 쪽을
  정본에 맞춰 지웠다.

- **손으로 만들지 않는다.** `make_final.py` 가 `final/`+`archive/not/` 에서 만든다 — 손으로
  복사하면 다음에 코드가 고쳐질 때 조용히 갈리고, 그때 등록한 코드는 **저장소의 어느
  판본도 아닌 상태**가 된다. `make_submit.py` 와 같은 규약이다(`README.md` 는 살린다).
- **계약을 스크립트가 세운다.** 갈리는 자리가 12개 목록과 다르거나 · 한쪽에만 파일이
  있거나 · 프롬프트가 갈리면 **선다**(`make_submit.py` 가 빠진 것을 건너뛰지 않는 것과
  같은 규약). `archive/not/check_not_units.py` 의 `EXPECTED_DIFF` 와 **같은 목록을 양쪽에서**
  지키므로 둘 다 고쳐야 통과한다.
- **덮어쓰면 정말 `archive/not/` 이 되는지까지 본다.** 위 세 판정이 다 맞아도 **실제로 합쳐
  대조**하지 않으면 "덮어썼는데 SDK 판이 아닌 무언가가 되는" 상태를 못 잡고, 그 상태는
  등록해 돌려 보기 전까지 아무 데도 안 드러난다.
- **`final/` 은 `submit/` 에 넣지 않는다.** 같은 코드를 세 번 싣게 된다 — `submit/` 은
  `final/`·`archive/not/` 을 저장소 배치 그대로 담는 메일 꾸러미다.

#### 용어사전 on/off — **코드를 고치지 않기로 했다** (2026-09-14 판단)

번역 용어사전이 아직 완성이 아니라 끌 수단이 필요한데, **배포 단위로는 지금도 된다** —
`TRANSLATE_GLOSSARY_API_URL`·`_DRIVE_ID`·`_WORKSPACE_ID` **중 하나라도 비우면**
`glossary_store` 가 적재를 건너뛰고(`not_configured`) 프롬프트의 용어 절·준수율 판정·
`<mark>` 하이라이트가 **전부 함께** 꺼진다. 요청 단위 on/off(화면 체크박스)는 요구가
아니라고 확정됐다.

> **남는 결함 하나를 적어 둔다.** 지금은 **"안 쓰기로 했다" 와 "설정을 빠뜨렸다" 가

> `not_applicable` 로 계속 갈라 온 바로 그 실패 형태다. 관리자는 자기가 설정을 빠뜨린
> 줄 안다. 가르려면 `TRANSLATE_GLOSSARY_ENABLED` 를 두고 사유를 `disabled_by_config`
> 로 낸다(고칠 자리는 `config.py`·`glossary_store.py`·`main._load_glossary` 셋).
> **안 만든 것은 의도한 공백이다.**

### 이관 직전 정리 — **안 쓰는 줄은 곧 타이핑 비용이다** (2026-09-08)

폐쇄망 이관은 **화면을 보며 손으로 친다.** 그래서 죽은 코드는 "언젠가 치우면 되는 것"이
아니라 **지금 사람이 치게 되는 줄**이다. 이관 전 마지막 훑기에서 참조 0건인 정의와
미사용 import 를 걷어냈다. **전부 동작 변화 0** — 점검 건수가 전후로 같다
(그때 932건. 뒤이은 프론트 계약 작업으로 지금은 934건이다).

| 걷어낸 것 | 왜 남아 있었나 |
|---|---|
| `lpdetect` (MCP) · `detect` (번역 `office/languages.py`) | `*_detail(...)[0]` 껍데기. 호출부 0건 |
| `lru_cache`·`log_info` import (`prompt_loader.py` **4벌**) | jinja 를 걷어내며(2026-09-07) 쓰는 자리가 사라졌다 |
| `only_me.document_text` + `replace` import | "회귀 점검용" 이라 적혀 있었지만 점검은 `parse()` 를 직접 부른다 |
| `lpresolve_tone` 의 **도달 불가 방어**(존재 확인 순회 + `NO_TONE_AVAILABLE`) | 관리자가 톤을 지울 수 있던 시절의 것. 그 경로는 2026-09-07 에 없어졌다 |

**마지막 것이 제일 값어치 있었다.** 그 방어가 남아 있는 동안 MCP 와 글다듬이의
`resolve_tone` 이 **다른 모양**이었고, 두 사본이 갈렸는지는 눈으로 못 본다. 이제 같은
모양이라 대조가 성립한다. 표가 깨지면 조용히 다른 톤으로 떨어지는 대신
`check_tone_policy` 가 그 자리에서 FAIL 한다 — **미측정을 통과로 보이게 하지 않는다**는
규약과 같은 방향이다.

**`jinja2` 선언도 같은 종류였다** — 코드가 어디서도 import 하지 않는데 네 단위
`requirements.txt` 에 남아 있었다. mirror 에 없는 패키지 하나가 `pip install -r` 을
세우면 **코드가 쓰지도 않는 이유로** 배포가 통째로 막힌다(지금 `lxml` 로 겪는 그것이다).

**같은 훑기에서 문서의 거짓 서술 하나를 찾았다** — 위 "`lpdetect` 를 `validate_direction`
이 쓴다". 코드가 아니라 **문서만** 틀린 경우라 점검으로는 영영 안 잡힌다.

### 설정 부재가 네 단위에서 제각각이었다 (2026-08-14)

**배포 환경변수(`GENOS_URL`/`LLM_SERVING_ID`)를 안 넣은 상태**가 단위마다 다른 얼굴로
나가고 있었다. 셋 다 "예외를 던지지 않고 조용히 틀리는" 종류이고, 공통 증상은 하나다 —
**몇 번을 다시 눌러도 같은 자리에서 실패하는 배포 실수인데 "잠시 후 다시 시도해 주세요"
가 나가고 캔버스가 재시도를 건다.** 원인이 화면에도 로그에도 드러나지 않는다.

| 단위 | 그전 | 지금 |
|---|---|---|
| 번역 | 200 + `translation_error="CONFIG_MISSING"` (2026-08-14 이전 수정분) | 그대로 |
| 글다듬이 | `_resolve_client()` 의 `RuntimeError` → `except Exception` → `ERR_INTERNAL`(`POLISH_INTERNAL_UNCLASSIFIED`) | `ERR_CONFIG_MISSING` |
| FAQ | `is_transport_error=False` 라는 이유로 `FAILURE_EXECUTION` → 502 재시도 가능 | `FAILURE_CONFIG` → `ERR_API_CONFIG_UNAVAILABLE` |
| 006 | 같은 이유로 `ERR_CHAT_UPSTREAM_EXECUTION`(00020002, retryable=True) | `ERR_CHAT_CONFIG_MISSING` |

**`CONFIG_MISSING` 문자열을 각 `llm.py` 의 상수로 올렸다.** 호출부가 이 값으로 분기하는데
리터럴이 두 곳에 있으면 한쪽만 고쳐도 **예외 없이 조용히 분기가 죽고**, 그 상태는 정확히
고치기 전 증상으로 되돌아간다.

### 그런데 서빙에서 갈라도 **스텝이 되돌리고 있었다** (같은 날, 더 큰 건)

스텝 9개는 재시도 여부를 **상태코드로만** 정했다 — `_RETRY_STATUS`(502·503·504)면 통신
실패, 나머지 4xx·5xx 는 전부 `UPSTREAM_EXECUTION`(**retryable=True**). 그래서 서빙이
`retryable=False` 로 갈라 둔 응답이 경계에서 통째로 뒤집혔다.

**FAQ 프롬프트 부재가 그 증거다.** 2026-08-13 에 `ERR_API_PROMPT_UNAVAILABLE`(500,
retryable=False)로 떼어내면서 "502 로 나가면 캔버스가 재시도를 건다" 고 적었는데,
**스텝이 그 500 을 502 와 같은 칸에 넣어 캔버스에는 여전히 retryable=True 로 나갔다.**
서빙 쪽 `ErrorCode.retryable` 만 보는 점검은 통과하므로 아무도 못 잡았다 —
`translated_markdown`·`stats` 와 **같은 종류의 경계 유실이고 세 번째다.**

- **상태코드가 아니라 응답 본문의 `error_code` 분류로 본다** (`_upstream_kind`).
  가이드 3.9.2 의 `00020003` 은 통신 실패도 실행 실패도 아닌 나머지 전부이고, 네 서빙이
  거기에 `retryable=False` 를 붙여 뒀다. **상태코드로는 이 판정을 복원할 수 없다** —
  006 은 `ERR_API_INTERNAL`(00020002, 재시도 가능)도 500 이라 500 ≠ 최종 실패다.
- **판정 못 한 응답은 예전 그대로 실행 실패로 둔다** (본문이 JSON 이 아니거나 dict 가
  아닐 때). 모르는 것을 재시도 불가로 올리면 일시적 장애가 최종 실패가 된다.
- **특례가 먼저다.** 006 스텝 1의 404(`TEMPLATE_MISSING`)도 00020003 이라, `upstream_final`
  을 앞에 두면 "템플릿을 찾을 수 없습니다" 안내가 통째로 사라진다.
- 스텝은 서빙의 안내문을 옮기지 않는다(§3.8) — 자기 오류표의 `UPSTREAM_FINAL`
  ("요청을 처리하지 못했습니다. 관리자에게 문의해 주세요.", retryable=False)로 낸다.

### 그물 — **이 층을 보는 점검이 하나도 없었다**

`check_workflow_run.py` 에 `_check_upstream_final`(9개 스텝 전부: 분류 4갈래 + 오류표)과
`_check_polish_upstream_final`(HTTP 응답 → 매핑 → `result` 이벤트까지 한 번에)을 넣었다.
뒤엣것이 따로 필요한 이유는 **분류 함수와 오류표가 둘 다 맞아도 매핑 분기를 안 걸면
앞의 둘만으로는 통과하기 때문**이다. 매핑 분기를 되돌려 FAIL(`02-00020002 retryable=True`)
이 나오는 것을 확인하고 넣었다. 48건 → **67건**.

서빙 쪽은 `check_unit_endpoints.py`(44 → **49건**)와 `check_chat_turn.py`(20 → **22건**).
FAQ 판정은 **`llm.py` 부터** 태운다 — `generate_faqs` 에 대역을 꽂으면 분류 **뒤**만 보게
돼 `_record_failure` 가 `CONFIG_MISSING` 을 실행 실패로 되돌려도 통과한다. 그때 환경변수가
아니라 `Config` 속성을 비우는 것도 같은 이유다: FAQ·번역의 `Config` 는 **import 시점에 값을
굳히므로** 지금 환경을 지워도 이미 읽은 값이 그대로 쓰이고, 점검이 조용히 무의미해진다.
