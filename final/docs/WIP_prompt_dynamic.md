# 톤 프롬프트를 동적으로 — **닫힘** (2026-09-07)

> 이 문서는 2026-09-03 에 "다음에 무엇을 하면 되나" 로 적어 둔 것이고, **그 전제가
> 없어져 착수하지 않는다.** 기록으로 남긴다.

## 1. 무엇을 하려던 것이었나

톤마다 다른 시스템 프롬프트를 프롬프트 라이브러리에서 받는데(`system_<tone>`),
**톤 → 프롬프트 대응이 코드에 있었다**(`config.TONE_PROMPT_IDS`). 그때는 톤 **목록**이
동적이었으므로(관리자가 올린 JSON 정책 문서), **관리자가 톤을 추가하면 그 톤에는 전용
프롬프트를 걸 방법이 없었다** — 오류 없이 내장 `system.j2` 로 떨어지고, 관리자는 자기가
만든 프롬프트가 안 쓰이는 줄 몰랐다.

해결안은 "정책 JSON 에 `prompt_id` 를 함께 적게 한다" 였다.

## 2. 왜 닫혔나

**2026-09-07 에 JSON 정책 문서 경로 자체를 걷어냈다** (요구 변경: 프롬프트는 전부
라이브러리에서 당겨 쓰되 코드서빙 안에서 JSON 을 해석하지 않는다).

그래서 **톤 목록이 다시 코드 표 하나가 됐다**(`tone_presets.TONE_PRESETS`). 톤을 늘리는
것은 개발자 일이고, 그때 `TONE_PROMPT_IDS`(또는 등록 화면의 `POLISH_PROMPT_IDS`)에
이름=ID 를 함께 적으면 된다 — **"목록에는 있는데 대응이 없는 톤" 이라는 상태가 아예
생기지 않는다.** 이 문서가 풀려던 문제가 그 상태였다.

덤으로 그때 걱정하던 함정 하나도 사라졌다: **TTL 이 둘이라 겹치는 문제**(정책 60초 +
프롬프트 60초 → 새 톤이 한 텀 동안 `system` 으로 떨어진다). 지금은 캐시가 프롬프트
한 벌이고 `POST /policies/reload` 는 `POST /prompts/reload` 의 별칭이다.

## 3. 되살아난다면

관리자가 **톤을 추가**할 수 있어야 한다는 요구가 다시 오면 그때 이 문제가 함께 돌아온다.
그 경우 고칠 자리는 셋이다 — 목록의 출처(`tone_presets`·MCP 사본), 이름=ID 매핑을
그 출처가 함께 내게 하는 것(`Config.prompt_ids_raw`), eval `TONE_RULES`.

지금 상태의 정본은 [`SERVING_REGISTRY.md`](SERVING_REGISTRY.md) §2-2 와
[`../prompt/README.md`](../prompt/README.md) §3 이다.
