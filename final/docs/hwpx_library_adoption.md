# python-hwpx — 쓰지 않는 이유와 대조에서 남은 것

> 상대 저장소: `hwpx-genon` (= `python-hwpx` 6.x 포크, Apache-2.0).
> 대상: SFR-006 (`final/SFR-006/request/template_fill/`), eval (`Test/eval/`).
> 이 문서는 **배포 단위가 이 라이브러리를 쓰지 않는 이유**와, 라이브러리와 대조하면서
> 우리 코드에 남긴 규칙의 근거를 다룬다. 환경변수·배포 규약은 `final/docs/README.md` 가 정본이다.

## 1. 한 눈에 보기

**우리가 만든 것의 핵심은 이 라이브러리로 대체되지 않는다.** 슬롯 문법, 세션·대화,
본문 블록, 근거 검증은 대응물이 없거나 요구사항이 우리 쪽이 더 구체적이다.

**배포 단위(006)는 이 라이브러리를 쓰지 않는다** — pip 로도, 사본으로도. 라이브러리가
줄 수 있는 층은 *검증*(개봉 안전 게이트)과 *측정*(표 셀 넘침)인데, 실제 배포 템플릿이
전부 표 없는 1~2쪽짜리라 두 층 다 아무 판정도 하지 않는다(§4).

대조에서 얻은 것은 코드가 아니라 **규칙 둘**이다(§3) — 파트 XML 선언과 누름틀 안내문.
둘 다 006 코드와 eval 지표에 반영돼 있고 `check_output_safety.py` 가 지킨다.

eval 만 라이브러리를 pip 로 쓴다 — **다른 파서로 같은 문서를 다시 읽는 것**이 목적이다(§5).

## 2. 대체 가능성 판정

| 우리 구현 | 라이브러리 대응 | 판정 |
|---|---|---|
| 슬롯 문법 `{'제목', 16pt, 고딕, 볼드}` (`hwpx_fields.py`) | 없음 (`{{token}}`·누름틀·라벨셀만) | **대체 불가 — 우리 고유 도메인** |
| 세션·대화·근거 검증 | 없음 (문서 라이브러리다) | **대체 불가** |
| 서식 `charPr` 파생 (`hwpx_style.py`) | `body_patch._materialize_restyled_charpr` (동형 로직) | 부분 — 슬롯 결합부는 우리 것 |
| 본문 블록 문단 복제 (`hwpx_blocks.py`) | `body_patch` 의 `insert_paragraph_by_clone` op | 부분 대체 가능 |
| hwpx→markdown 추출 (hwpx 파싱 코어 사본들) | `export_markdown` 하나 | 대체 가능 — **하지 않는다**(§4) |
| 누름틀 스캔·채움 | `doc.fields.add/all/fill` | 대체 가능 |
| 산출물 패키지 검증 | `validate_package` | **쓰지 않는다**(§4) |
| 재개봉 검사 | `HwpxDocument.open` | **쓰지 않는다** — 우리 파서로 하면 항등식이다(§4) |
| 값 넘침 판정 | `form_fit.measure` | **쓰지 않는다**(§4) |
| eval 무결성 지표 | `doc_diff` (`doc-diff-v1`) | **pip 로 쓴다** — 제3 구현인 것이 존재 이유(§5) |

## 3. 대조로 고정한 규칙 둘

### 3.1 파트 XML 선언에 `standalone="yes"` 를 남긴다 — `hwpx_fields.serialize_part`

한/글이 쓴 원본 파트는 `<?xml version="1.0" encoding="UTF-8" standalone="yes" ?>` 로
시작한다. `etree.tostring(root, xml_declaration=True)` 는 standalone 을 빼고 쓰므로,
그대로 두면 **원본과 다른 파일을 내보낸다.** OWPML 패키지 검사기는 이것을 파트 오류로
잡되 advisory 로 분류한다 — 실한컴이 그래도 열어 주므로 화면에서는 드러나지 않는다.

재직렬화 diff 를 뜨면 **다른 차이는 0** 이다 — lxml 이 나머지는 바이트 그대로 보존한다.
즉 재직렬화 경로의 손실은 이것 하나이고 인자 하나(`standalone=True`)로 닫힌다.

재직렬화는 `hwpx_fields.serialize_part` **한 함수**만 한다(`hwpx_fields`·`hwpx_style`·
`hwpx_blocks` 가 모두 이것을 부른다). 모듈마다 `tostring` 을 부르면 한 곳만 고쳐지고
나머지는 남는다.

### 3.2 누름틀 안내문은 `Direction` 파라미터다

실한컴 CLICK_HERE 필드는 파라미터가 둘이고 **원시 명령 블롭이 먼저** 온다:

```xml
<hp:stringParam name="Command">Clickhere:set:51:Direction:wstring:9:이름을 적으세요 HelpState:…</hp:stringParam>
<hp:stringParam name="Direction">이름을 적으세요</hp:stringParam>
```

"한/글 버전마다 name 이 다를 수 있으니 첫 것" 으로 잡으면 Command 블롭이 안내문이 되고
결과가 둘로 샌다:

1. `Clickhere:set:51:…` 이 그대로 LLM 프롬프트·화면의 안내문이 된다.
2. **미입력 필드가 입력됨으로 판정된다.** `filled` 는 `현재텍스트 != guide` 인데, 빈
   필드의 현재 텍스트는 안내문("이름을 적으세요")이고 guide 는 블롭이라 둘이 늘 다르다.
   `missing_field_names` 가 그 필드를 빼면서 **사용자에게 묻지도 않고 안내문이 값인 채로
   문서가 나간다** — 부분 초안 계약이 무너진다.

그래서 006 `hwpx_fields._first_string_param_text` 는 `Direction` → Command 가 아닌 첫
파라미터 → 첫 파라미터 순으로 고른다.

**같은 규칙이 `Test/eval/eval_mcp/structure_metrics.py` 의 `_guide_text` 에도 있다.**
"파서를 공유하면 파서 버그를 함께 놓친다" 는 규칙으로 두 벌을 유지하지만, 두 벌을 같은
가정으로 쓰면 **지표가 결함을 승인한다.** 규칙을 지키는 것만으로는 목적이 지켜지지 않아,
그 위에 제3의 구현으로 교차검증을 붙였다(§5).

## 4. 쓰지 않는 것과 그 이유

### 4.1 개봉 안전 게이트·넘침 측정 — 판정할 대상이 없다

- **개봉 안전 게이트**(`validate_package`)는 산출 바이트의 OPC 패키지 계약을 본다.
  006 이 템플릿을 고치는 방식은 문단 텍스트 교체·`charPr` 추가·문단 복제뿐이고,
  패키지 구조(mimetype·manifest·파트 목록)는 건드리지 않는다. 깨질 수 있는 자리는
  `itemCnt`/`fontCnt` 재계산과 파트 XML 선언인데, 앞의 것은 `hwpx_style` 이 다시 세고
  뒤의 것은 §3.1 이 닫는다.
- **넘침 측정**(`form_fit`)은 폭이 고정된 **표 셀**에서만 의미가 있다. 본문 문단은
  넘치면 다음 줄로 흐를 뿐이다. 실제 배포 템플릿에 표가 없어 측정이 늘 0건이다.
- 둘 다 붙이면 매 다운로드에 판정 없는 검사가 돌고, **"검증됐다" 는 인상만** 남는다.
  표가 든 슬롯 템플릿이 실제로 배포되면 그때 넘침부터 다시 따진다(§7).

### 4.2 재개봉 검사 — 우리 파서로 대신할 수 없다

이 검사의 가치는 *다른 코드베이스가* 우리 출력을 파싱한다는 데 있다. 우리 writer 의
출력을 우리 파서로 다시 여는 것은 구조상 통과하는 항등식이고, 그런데도 "재개봉 통과"
라는 이름이 붙으면 없는 것보다 나쁘다. 라이브러리로 하려면 `HwpxDocument`(문서 모델
40k 줄)를 코드서빙 이미지에 넣어야 한다. 독립 파서로 산출물을 열어 보는 판정이 필요하면
그 자리는 eval 이다(§5) — 이미 제3 구현을 쓰고 배포 제약도 없다.

### 4.3 pip 의존 — 검증 여부를 배포 환경이 정하게 된다

배포 단위가 이 라이브러리를 pip 로 쓰면, 폐쇄망 registry 에 wheel 이 없을 때 검사가
스스로 꺼지고 **그 환경에서는 산출물이 검증 없이 나간다.** 꺼진 사실은 로그에만 남아
운영이 검증되고 있다고 착각하기 쉽다. 상류가 Alpha 이고 6.x 에서 파사드 표면이 크게
움직인다는 것(루트 멤버 102 → 34)도 같은 방향의 위험이다.

### 4.4 추출기 통합 — 보류

hwpx→markdown 추출은 `export_markdown` 으로 대체 가능하다. 단순 문단 문서에서는 우리
출력과 **완전히 같고**, 병합 셀이 든 표에서만 갈린다(우리는 빈 칸, 라이브러리는
`rowspan` HTML — 둘 다 열 밀림은 없다). 합치면 중첩 표·각주·이미지 fidelity 가 덤으로
따라온다.

하지 않는 이유는 **파급 대비 리스크**다. 번역·FAQ 의 운영 입력 경로를 건드리는
리팩터링이고 실패해도 조용하다. 지금 hwpx 파싱 코어는 전처리기
(`final/preprocessor/final_preprocessor.py` PART 2)가 정본이고 코드서빙 사본과의 일치는
`Test/check/check_table_grid.py` 가 출력으로 대조한다 — 통합을 한다면 그 구조 위에서 한다.

## 5. eval 은 pip 로 쓴다 — 교차검증

`Test/eval/requirements.txt` 에 `python-hwpx>=6.0,<7` 이 있다. eval 은 **배포 단위가
아니라** 폐쇄망 이미지 제약을 받지 않는다.

`hwpx_text_crosscheck` 는 `hwpx_document_integrity` 와 같은 것을 **다른 파서**
(`doc_diff`)로 다시 잰다. 둘이 어긋나면 둘 중 하나가 문서를 잘못 읽고 있다는 뜻이다 —
한 벌만 있을 때는 알 수 없다. §3.2 처럼 두 벌이 같은 가정을 공유하는 경우를 잡는 장치다.
그래서 이 구현을 사본으로 우리 트리에 들여오면 목적이 사라진다.

라이브러리가 없으면 `available=False` 를 돌려주고, 스위트에서는 `not_measured` 로 남는다.
**미측정을 통과로 위장하지 않는다** — eval 의 기존 규율 그대로다.

## 6. 검증

`Test/check/check_output_safety.py` 가 006 쪽 §3 의 두 규칙(파트 XML 선언·누름틀
안내문)을, `Test/check/check_eval_metrics.py` 가 eval 쪽 누름틀 안내문 스캔을 본다.
기준 건수는 `Test/run_all.py` 의 `EXPECTED` 한 곳이 갖는다.

점검 픽스처에서 지킬 것: **Command 파라미터를 Direction 보다 먼저 둔다.** 순서를 뒤집으면
"첫 파라미터" 구현도 통과해 검사가 무의미해진다.

## 7. 남은 확인

- **표가 든 실물 슬롯 템플릿이 없다.** 넘침 측정을 다시 따질지는 그런 템플릿이 배포될 때
  정한다. 그때 가장 강한 확인은 한/글이 기록한 `lineSeg/@horzsize` 와 폭 추정을 대조하는
  것이다. 한 셀에 슬롯이 둘 이상이면(`{'소속'} {'성명'}`) 항목별이 아니라 합친 길이로
  재야 한다.
- **누름틀이 든 실물 한컴 템플릿이 없다.** §3.2 의 파라미터 순서는 라이브러리가 재현한
  한컴 계약으로 확인했고, 한/글이 직접 저장한 파일로는 대조하지 못했다.
- **006 산출물을 eval 스위트에 태우는 경로가 없다.** 독립 파서로 산출물을 열어 보는
  판정(§4.2)이 필요해지면 그 경로를 만드는 편이, 코드서빙 이미지에 문서 모델을 넣는
  것보다 낫다.
