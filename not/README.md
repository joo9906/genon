# `not/` — **폐쇄망에 반입하는 판본** (코드 서빙 네 단위)

> **여기가 올라간다.** `onprem/codeserving/` 은 기능 설계의 **정본**이고, `not/` 은 그것에
> **`openai` SDK 전송 + 스트리밍 셋**을 얹은 반입본이다.
>
> 기능 설계를 여기서 새로 정하지 않는다 — 고칠 것이 생기면 정본에서 정하고 여기로
> 옮긴다. 갈리는 자리는 목록으로 못박혀 있고(`check_not_units.py` 의 `EXPECTED_DIFF`),
> **목록 밖이 갈리면 그물이 FAIL 한다.**

## 이 판본이 무엇인가 (2026-09-09 요구 변경으로 성격이 뒤집혔다)

처음에는 "사내 mirror 에 **`lxml` 이 없어** 깎아낸 한시 판본" 이었다. 그 뒤 mirror 에
**`lxml`·`openai` 가 들어와** 깎아낼 이유가 없어졌고, 방향이 반대가 됐다 — **기능이
가장 많은 판본**이다.

| | 그전 (2026-09-08) | **지금** |
|---|---|---|
| 성격 | lxml 없이 깎아낸 한시 판본 | **반입 판본. 기능 최대** |
| LLM 전송 | `httpx` 직접 (정본과 같다) | **`openai` SDK** (`AsyncOpenAI`) |
| 006 산출물 | `.txt` (hwpx 를 되쓸 수 없었다) | **`.hwpx`** (정본과 같다) |
| hwpx 직접 업로드 | 006 만 | **번역·FAQ·006 셋 다** |
| 글다듬이 스트리밍 | 있다 | 있다 |
| 번역 스트리밍 | 없다 | **있다** |
| FAQ 스트리밍 | 없다 | **있다** |

> 📦 옛 `not/openai/` 는 **이 판본으로 흡수됐다** — `archive/not_openai_absorbed/` 에
> 보관본이 있다. 등록하지 않는다.

## 정본과 갈리는 것은 셋뿐이다

**나머지 파일은 정본과 바이트까지 같다.** 그래서 정본의 그물(`onprem/test/*`)이 지키는
것을 이 판본도 그대로 물려받는다 — 두 벌로 검사하면 정본을 고칠 때 이쪽만 옛 판정을
들고 남는다.

### 1. LLM 전송 계층 — `openai` SDK

네 `llm.py` 가 `AsyncOpenAI` 로 부른다. **정본이 `httpx` 판에서 얻은 셋을 그대로
유지한다**(SDK 로 바꾸면서 잃기 쉬운 것들이다):

1. **전역 클라이언트 없음** (§D.2) — 호출마다 열고 닫는다. 전역에 캐시하면 토큰이
   회전돼도 옛 값을 쓰게 되어, 그것을 막는 **캐시 키 방어 코드**가 따로 필요해진다.
2. **4xx 는 재시도하지 않는다** — `openai.APIStatusError.status_code` 로 가른다.
   400·401·404 를 상한만큼 두드리면 같은 결과를 반복하며 대기시간만 늘고, 로그에서
   일시적 장애와 구분되지 않는다.
3. **SDK 자체 재시도를 끈다** (`max_retries=0`) — 켜 두면 우리 재시도와 **곱해지고**
   그 추가 호출은 우리 로그에 남지 않는다.

**정본과 갈리는 유일한 설정**: `Config.llm_model_id()` (`LLM_MODEL_ID`, 기본
`"default"`). SDK 는 `model` 없이 요청을 만들지 않는다. 정본은 서빙 경로가 모델을
정하므로 싣지 않는다.

> ⚠ 정본이 2026-09-07 에 SDK 를 걷어낸 이유는 **"실환경에서 SDK 때문에 호출이
> 실패했다"** 였다. 그 실패가 SDK 자체 문제였는지 그때의 배선 문제였는지는 **가려지지
> 않았다.** 되돌릴 자리는 **네 `llm.py` 뿐**이다 — `onprem/codeserving/*/llm.py` 를 옮겨
> 적고 `requirements.txt` 에서 `openai` 를 뺀다.

### 2. 스트리밍 셋

```
POST /polish/stream        (SSE)  다듬어지는 대로 흘린다
POST /translate/stream     (SSE)  번역문이 문서 순서대로 흐른다
POST /translate/finalize   (JSON) 하이라이트 재료 + 내려받기 링크
POST /generate/stream      (SSE)  FAQ 를 **항목마다** 흘린다   ← 2026-09-09 신설
```

#### 캔버스 스텝이 실제로 이 경로를 부른다 (2026-09-09)

서빙에 라우트를 만드는 것과 **화면에 닿는 것은 다른 일**이다. 2026-09-09 오후까지
번역·FAQ 스텝은 비스트리밍(`/translate/markdown`·`/generate`)을 부르고 완성된 글을
조각내 흘리고 있었다 — `emit` 뒤 `sleep(0)` 은 스케줄러 양보라 조각이 수 ms 안에 다
나가고, 화면에서는 "한방에" 와 구분되지 않는다.

지금은 **정본 스텝 셋이 SSE 를 먼저 시도한다**(`_stream_serving`). 스텝은 `onprem/`
것 그대로이고 사본을 만들지 않았다 — 정본 서빙에는 이 라우트가 없어 SSE 아닌 응답이
오고, 그러면 **비스트리밍으로 되돌아가** 예전 동작 그대로 돈다. 흐르는 것은 이 판본을
올린 배포뿐이다.

**세 경로 모두 비스트리밍 경로가 폴백으로 남는다.** 게이트웨이가 `stream=True` 를
받는지 폐쇄망에서 확인되지 않았고, 안 받는 배포에서 기능이 통째로 죽으면 안 된다.
되돌아간 사실은 응답의 `stream_fallback` 과 로그가 말한다 — 조용히 넘기지 않는다.

- **흘리는 것은 정본 텍스트다.** 하이라이트 사본(`<mark>`)을 흘리면 ① 하이라이트가
  스트리밍 중에 먼저 나타나 요구가 말한 순서와 어긋나고 ② 태그가 조각 경계에서 갈려
  `<ma` 같은 부스러기가 남는다.
- **전량 실패에서는 한 글자도 흘리지 않는다.** 흘린 뒤 오류로 갈아엎으면 사용자에게는
  **답이 나왔다가 사라지는** 것으로 보인다.

#### FAQ 스트리밍은 토큰을 그대로 흘리지 않는다

FAQ 항목은 **스키마·근거 대조·중복 기각**을 지나야 화면에 나갈 자격이 생긴다. 그래서
프롬프트가 `근거 → 질문 → 답변` 순으로 쓰게 하고, 검증을 **접두어 연산**으로 한다:

| 그 시점에 | 할 수 있는 것 |
|---|---|
| 근거가 닫히면 | **원문 대조** — 실패면 그 항목은 한 글자도 화면에 안 나간다 |
| 질문이 닫히면 | **중복 판정** · 몫 확인 |
| 답변 첫 델타 | 위 둘을 통과했으므로 항목을 **열고** 토큰 그대로 흘린다 |

화면 첫 글자까지 = 근거 + 질문(≈100~200토큰)이다. 항목 전체를 기다리는 것의 절반 이하.

**프레임 넷** — 셋은 `generator` 가 만들고 `done` 만 라우트가 만든다:

```
data: {"type":"item_open","index":0,"question":"…"}
data: {"type":"delta","index":0,"text":"…"}
data: {"type":"item_close","index":0,"question":…,"answer":…,"evidence":…}
data: {"type":"done", …비스트리밍 `/generate` 와 같은 payload…}
```

`done` 의 payload 는 **`/generate` 와 같은 조립 함수**(`_store_and_payload`)를 지난다.
각자 조립하게 두면 `markdown`·`download_url`·`download_ready`·세션 저장 넷 중 하나가
한쪽에만 붙고, 그 어긋남은 오류가 아니라 **화면에서만** 드러난다.

**FAQ 는 비스트리밍 경로도 같은 마크다운 형식을 쓴다** (이 판본 안에서만). 형식이 둘이면
증분 파서가 스트리밍 요청에서만 돌아 **거의 검증되지 않는 갈래**가 된다. JSON 판은
`onprem/` 에 그대로 있다.

## 등록

**코드 서빙 네 개**를 각각 등록한다. 등록 칸에 적을 값은 `onprem/docs/SERVING_REGISTRY.md`
가 정본이고, 저장소 경로만 `onprem/codeserving/<단위>` → **`not/<단위>`** 로 바꾼다.

```
not/SFR-006_template_fill/     006 HWPX 템플릿 채우기
not/SFR-018_text_polish/       글다듬이
not/SFR-018_translation/       번역
not/SFR-018_faq/               FAQ 생성
not/prompt/                    네 단위의 프롬프트 (배포 단위 **밖**이므로 이미지에 함께 넣는다)
```

**MCP 넷·전처리기 2벌·워크플로우 스텝 9개는 이 판본과 무관하다** — 그쪽은 표준
라이브러리만 쓴다. 바꾸는 것은 **코드 서빙 네 단위의 저장소 경로**뿐이다.

> ⚠ **`minio.py` 는 우리 코드가 아니다.** GenOS 에서 받은 **동작하는 MCP 예제**이고,
> 내려받기 링크(presigned URL)를 어떻게 얻는지 확인하려고 옮겨 둔 참조본이다.
> **등록하지 말 것** — `mcp` 전역을 shim 없이 쓰고, import 하는 순간
> `ensure_packages()` 가 **`pip install python-docx` 를 실행한다**(가이드 p.19 금지사항).
>
> 이 파일로 확인한 것: 업로드 URL·멀티파트 필드(`hostname`+`file`)·응답 경로
> (`data.presigned_url`) **넷이 우리 `file_store.py` 와 같다.** 링크 모양은 추측이 아니다.

## 점검

```
export PYTHONIOENCODING=utf-8
SSL_CERT_FILE= python not/check_not_units.py      # 91건 — 게이트웨이·LLM 불필요
```

층은 다섯이다:

1. **전송 규약** — 네 `llm.py` 가 같은 규약인가 (전역 없음·`max_retries=0`·`model`·
   `stream` 명시·4xx 미재시도·경로 한 곳)
2. **정본과 갈리는 자리** — `EXPECTED_DIFF`(17) · `EXPECTED_EXTRA`(3) · **정본에만 있는
   파일 0**. 마지막 것이 `lxml` 로 되살린 파일 넷을 지킨다
3. **의존 선언** — 위 표대로인가 + `jinja2` 가 없는가
4. **기동·라우트** — 네 단위가 뜨고 스트리밍 셋 + hwpx 업로드 둘이 실제로 등록되는가
5. **동작** — 번역 스트리밍(순서·무손실·전량 실패에 원문 미유출·폴백·finalize 좌표) ·
   FAQ 스트리밍(근거 기각 항목이 화면에 안 나가는가·흘린 순서 == 최종 목록·중복·
   폴백·라벨 사본 대조)

**여섯 갈래를 되돌려 FAIL 을 확인했다**: FAQ 스트리밍 라우트 제거 · 목록 밖 파일
드리프트 · hwpx 파서 파일 누락 · 근거 기각 항목 흘려보내기 · `lxml` 선언 제거 ·
중복 판정 제거.

## 폐쇄망에서 확인할 것

- **게이트웨이가 `stream=True` 를 받는지** — 안 받으면 세 경로가 각자 비스트리밍으로
  되돌아간다(설계된 폴백).
- **중간 프록시가 SSE 를 모아 보내지 않는지** — 모으면 "한방에" 로만 보이고 오류가
  없다. 그래서 세 경로 모두 `X-Accel-Buffering: no` 를 실어 둔다.
- **SDK 경로가 실제로 뜨는지** (위 ⚠). 되돌릴 자리는 네 `llm.py`.
- **`model` 값을 게이트웨이가 어떻게 다루는지.**
- **MinIO 업로드** — 안 되면 `download_url` 이 비고 옛 `POST /download`(018) ·
  `POST /generate`(006) 폴백이 그대로 산다.
